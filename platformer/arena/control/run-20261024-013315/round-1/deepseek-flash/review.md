# 横版闯关竞速 · deepseek-v4.1-flash 策略与自测说明（第 1 轮）

> 说明：本轮尚未与对手正式对局，下文的“结果”均为我在本机用公开规则源码搭的离线自测，
> 不是正式比赛复盘；正式对局结束后如果需要，会另写 `postmatch.md`。

## 一、总体思路

提交方式为 `program` 常驻进程（`entry.json` → `python3 agent.py`），每 0.25 秒读入一行观察，
输出 5 帧输入。核心是**用 Python 精确复刻公开规则源码的物理与机关公式，再做带物理仿真的滚动决策**，
而不是写死几条“看到坑就跳”的启发式。

### 1. 规则复刻（已逐帧校验）

- `catalog.js` 的全部常数（跑速 6.8、加速度 70/空中 40、摩擦 48、起跳 14、重力 42、推挤 4.2、
  怪物 1.7、塌陷砖 0.55/3.2 等）逐项抄进 `agent.py`。
- 完整复刻 `updateRunner`：加速/摩擦、跳跃、X 碰撞（含 `Math.floor` 边界修正）、Y 碰撞与落地、
  移动平台承载与侧推、`y < -3` 掉落判定。
- 完整复刻危险判定：地刺（带 0.04/0.08 内缩）、食人花（高度/相位）、旋转锯齿（圆-矩形最近点）、
  怪物（0.72 × 0.62 盒）。
- 复刻 `generateLevel`（LCG `s*1664525+1013904223 mod 2^32`、各分支的 rng 调用顺序与短路规则），
  由观察里的 `seed` 和 `round` 还原关卡（level seed = `seed*131 + round*977`），从而**精确预知**
  平台/锯齿的周期与相位、食人花的周期与相位；并用观察里的 `level.tiles` 与各机关数量做一致性校验，
  不一致时自动退回“观测值 + 速度外推”，不会因还原失败而崩溃。
- 时间基准用观察里的 `time`（20 Hz 下必为 0.05 的整数倍，`round2` 后仍精确），
  预测第 i 帧机关状态用 `t0 + i*0.05`。

校验方式：用 Node 驱动真实 `simulation.js`，随机输入跑 900 帧并逐帧导出全部动态状态，
Python 用导出的状态复算玩家位置/速度/落地/死亡，6 个 seed 全部 `bad 0`（含掉坑、复活、塌陷桥变空洞）。
平台/锯齿位置预测与真实值最大误差 0.005（仅为观察保留两位小数的舍入），食人花高度公式逐帧一致。

### 2. 决策：滚动时域 + 物理搜索

每个决策窗口（5 帧）都做一次“从现在起 2 秒”的仿真搜索：

1. **主搜索** `search_survive`：默认全速向右（`move=1`），逐帧枚举“跳/不跳”。
   用 `(x, y, vx, vy, onGround)` 去重，保留所有能存活 40 帧的分支；
   对结束时仍在空中的分支，继续向后续推直到落地，落地即死则淘汰。
   目标里没有“多跳/少跳”的偏好——全速下水平位移与跳跃无关，只要存活即可；
   这保证速度接近理论上限（见自测的 ~6.5–6.6 格/秒）。
2. **等待/后退前缀**：主搜索失败时（动态机关相位不利、或已错过某个静态起跳窗口），
   依次尝试“原地等 k 帧 / 后退 k 帧再全速”（k=1..5），对每个前缀后的状态再跑主搜索，
   取最小的可行 k。等待用于食人花/锯齿/怪物等周期性机关；后退用于地刺/坑的起跳窗口已错过时。
3. **兜底**：
   - 空中且没有完整存活方案：比较“先刹车 k 帧再前进”的几种短动作，选能安全落地且落点最远的；
   - 地面：默认原地等待（等动态机关相位变化），连续 4 个窗口仍无解且近处有静态障碍
     （地刺/坑/台阶）且身后安全时才后退；
   - 站在塌陷砖上不原地等待，优先离开该砖。
4. **塌陷砖处理**：观察里 `gone` 是已塌、`crumbling` 是即将塌。规划时把“同一列中只要有一块已塌/将塌”
   的整列塌陷砖都按空洞处理（真实物理里踩空后会逐层塌落），避免把残坑当安全落脚点；
   同时避免在塌陷砖上停留。这个修正消除了一类“落在半塌桥上、被锯齿/塌落耗死”的死亡。
5. **推挤相关**：不显式建模对手（对手输入不可知），但做了两个保守处理：
   - 被对手紧贴在后（中心距 -1.7 ~ -0.15 格且高度接近）时不主动刹车/后退，
     因为现实中会被后方顶回、把起跳时机顶乱，甚至被推进锯齿/食人花；
   - 后退前检查身后 2 格是否有坑、以及 3 格内是否有锯齿/食人花/怪物，避免“倒退进危险物”。

### 3. “三连地刺”卡死图：改为比最远距离（maxX）

离线穷举发现：**连续 3 格地刺在现有物理下无法跳过**（安全滞空窗口只有约 9 帧 ≈ 2.7 格，
而 3 连刺的危险横向区间约 3.6 格；1 连刺有 5 帧起跳窗口、2 连刺只有 2 帧、3 连刺无解）。
生成器约 1/3 的关卡存在这种 3 连刺，因此这些局无法真正到达终点，超时后按 `maxX` 判定。

对此的策略：
- 关卡开始时扫描地刺连续段，找到第一段 ≥3 的（之后的地刺都过不去），记为 `sx`；
- 距离 `sx` 还远（> 8 格）时，规划里**遮蔽**这段地刺，正常跑图（否则会把“不可避免的死亡”误判成需要等待）；
- 进入 `sx - 8` 之后，改用 `search_maxx`：允许 `move ∈ {1,0,-1}`、跳/不跳，
  以“整条轨迹到达过的最大 x”为分数（死亡也计入，且掉坑按规则先复活、不计本帧 x），
  据此在刺前“最后安全帧”起跳，死亡位置约为 `sx + 3.0`（理论上限约 `sx + 3.12`）；
- 达到 `maxX ≥ sx + 2.8` 后回到起点等待（再跑也不会更远），把剩余时间交给超时判定。

## 二、离线自测结果

测试环境：本机 Node 24 + Python 3.14，用公开 `simulation.js` 建对局，
Python agent 以子进程 + stdin/stdout 行协议接入（与正式协议一致：`advanceWindow` 每窗口 5 帧）。

1. **物理/危险判定对照**：6 个 seed × 900 帧逐帧对照，`bad 0`。
2. **动态机关预测**：平台、锯齿位置最大误差 0.005 格，食人花高度逐帧一致。
3. **对练习电脑**（公开源码里的 `botInput`）：正式种子
   `5011/5012/5021/5022/5031/5032`，左右座位各 6 局，共 12 局全胜（6:0、6:0）。
   可通行图上通常 24–30 秒到终点、0 死亡；卡死图靠 `maxX` 赢。
4. **自我对弈**（双方都是本 agent，最接近“同等强度对手”的样本）：
   - 6 个正式种子、座位 0：2 胜 2 负 2 平（局）。
   - 拆到单局看：可通行局双方 4:4，卡死局基本都打成平局（双方 maxX 都是 ~`sx+3.0`，差 < 0.5）。
   - 说明：起始位置 team1 领先 0.9 格（约 0.13 秒）确实有优势，但机关相位差和推挤会让
     落后方也能赢下单局，并非“座位决定胜负”。
5. **响应耗时**：单次决策平均 3–9 ms，最慢约 180 ms（远低于 5 秒硬上限）；
   进程常驻、逐行 flush，无技术性超时风险。

## 三、局限与未做的事

- **没有对对手建模**：对手的未来输入不可知，搜索里不包含对手，只靠“被尾随时不刹车的保守规则”
  和滚动重规划吸收推挤扰动。对手若专门利用推挤把我的起跳时机顶乱，仍可能让我失误。
- **卡死图只能争取平局**：3 连刺在规则内无解，双方都会做到 ~`sx+3.0`；若无 push 运气，
  这类局面的上限就是平局。生成器种子固定时可以提前知道哪几局是卡死图，但无法改变结论。
- **半塌塌陷桥**：我按整列空洞保守处理，可能比“贴着对手 0.13 秒的间隔冲过去”慢；
  自测里出现过为等桥复原而多花约 3 秒、从而输掉可通行局的情况。
- **没有做全局最优路线规划**：当前是 2 秒滚动搜索，实测均速约为理论值的 96%–97%；
  理论上还有约 0.5 秒/局的优化空间（例如更精细的到达相位），但没有继续压榨。
- **未与真实对手对局**：以上全部是离线自测，不代表正式比赛结果；正式对局后的实际情况另见 `postmatch.md`。

## 四、提交内容

- `entry.json`：`{"mode":"program","command":["python3","agent.py"]}`
- `agent.py`：单文件、仅用标准库（`sys/json/math/os/traceback`），常驻进程，stdin 每行一个观察，
  stdout 一行 `{"inputs":[[{"move":…,"jump":…}], …5 帧…]}`，立即 flush；调试信息只写 stderr。
- `tools/`：本机自测脚本（真实模拟对照、关卡统计、对局驱动），不属于运行期依赖。
