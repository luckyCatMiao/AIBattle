## 四、本轮实际采用的策略与赛前改动

`agent.py` 是单文件、仅标准库、常驻进程；每 0.25 秒（5 帧）规划一次，只执行前 5 帧。
本轮提交相对上一版的主要改动如下（这些改动在本轮对局中已经生效）：

1. **精确复刻规则物理**：逐行移植 `simulation.js` 的加速/摩擦/重力/起跳、X→Y 两段碰撞、
   移动平台带人、地刺/食人花/锯齿/怪物判定，以及关卡生成器；用 `seed/round` 提前知道
   移动平台、锯齿、食人花的周期与相位，而不是只靠观测外推。
2. **20Hz 前向搜索**：以 2 秒（40 帧）为视界枚举「跳/不跳」，主搜索只允许全速向右；
   评分原则是「先活着、再尽量靠前」，每窗口重规划。
3. **卡死图 maxX 模式**：地图出现连续 ≥3 格地刺时，物理上无法通过，改为「全速跑到刺前起跳，
   把 `maxX` 做到 `s+3.07` 后回起点待机」。本轮两张卡死图（`r1-g2` R1/R2）都拿满了理论 maxX。
4. **塌陷砖不等待**：脚下是塌陷砖时绝不原地等，优先起跳脱离；后退落点同时排除坑、
   塌陷砖列、地刺列。
5. **观察量化安全余量**：地刺 +0.05、食人花 x +0.04 / 高度阈值 -0.08、锯齿 +0.05、怪物 +0.05；
   卡死图的 maxX 搜索关闭余量，保证 maxX 仍是理论最优。
6. **失败兜底阶梯**：空中 1/0/-1 修正 → 远处卡点先跑 → 原地等/后退 k 帧 → 空中刹车 →
   被顶住时后跳脱身 → 后退 → 原地等；被慢速对手贴身时优先跳过去，避免被压到 4.2 格/秒。
7. **赛前自测**：Node 驱动真实 `simulation.js`，35 个种子 × 2 局共 70 局单人跑图；
   50 局可达图中 0 死亡，平均比理论下界慢 0.344 秒，最差单局 +0.65 秒；
   与上一版对打 60 局（30 种子 × 2 座位）为 22:27:11，未显著拉开差距。该自测只覆盖单人/旧版对手，
   不覆盖本轮 sol 的推挤与卡死图待机场景。

## 五、赛后改动（本轮结束后，已写入 `agent.py`）

### 5.1 卡死图待机防推：`IDLE-ANTIPUSH`

**问题**：`r1-g2` R1 中，我方拿满 maxX 后在起点待机；sol 重生在身后，连续 49 帧把我方从 x≈4.6
推到 x=15.18，推进食人花，白送一死。

**改动**：在卡死图的 `IDLE` 分支里，如果检测到对手在身后 0.4–6.0 格、垂直重叠、且正在向右移动
（`vx > 0.8`），不再原地等，而是**原地起跳**。跳跃时两人垂直重叠小于 0.3 格，`resolvePush` 不生效；
原地跳既不改变 maxX，也不会被推进危险物。落在下一窗口若对手仍在身后，继续跳。

**验证**（真实 `simulation.js` 反事实，`tools/counterfactual_g2r1.js`）：
- 从回放窗口 1265（sol 刚在起点重生）切换成新版 agent，sol 沿用回放输入；
- 旧版：被连续推 49 帧，x 4.63→15.18，t=65.65 死于食人花；
- 新版：起跳后停在 x≈5.06，sol 在身后时反复原地跳（t≈63.3 以及 sol 再次重生的 t≈83–90），
  **没有再被推走，也没有食人花死亡**；
- 对两场回放逐窗口对拍：新版只在 `r1-g2` 的 10 个待机窗口改变了输入（全部在这一次推挤事件中），
  `r1-g1` 仅最后一帧的相位切换差异；其余 1000+ 窗口与旧版完全一致。

### 5.2 尝试过但回退的改动：坑沿支撑余量

针对 2.2 的 0.005 格坑沿问题，曾加入 `SUPPORT_MIN=0.08`：搜索中如果落地时脚下实心支撑宽度
小于 0.08 格就拒绝该落点。离线对拍发现它会从 `r1-g1` R1 t=12.75 起就改变起跳时机（19 个窗口分叉，
而原版只有 1 个），属于全局性行为变化；没有足够时间做全量回归，**已回退**。
因此 2.2 的坑沿量化问题仍然存在，留作下一轮的高优先级修复项。

### 5.3 未改动的部分

- `r1-g2` R3 的“先跳、落点被锯封住、只能空中刹车”没有改。它需要把起跳时机提前/推迟 0.1–0.3 秒，
  涉及前向搜索的视界与落点评价，改动面较大；本轮先记录，不在没有回归的情况下硬改。
- 推挤的博弈层（对手未来输入）仍未建模；目前只在“被贴身/被尾随”时用启发式处理。

## 六、已知局限与下一轮重点

1. **坑沿 0.005 格量化**（`r1-g1` R2 掉坑）：下一轮优先做“重规划边界可行性检查”——
   把执行 5 帧后的状态按两位小数取整，再从取整状态做一次短视界存活搜索；不通过就换方案。
   这比全局加支撑余量更局部，预期不会改动普通路段的起跳时机。
2. **花 + 锯的组合**（`r1-g2` R3）：需要在“起跳前”而不是“空中”比较“现在跳/晚 0.1–0.3 秒跳”；
   目前 2 秒搜索在已起跳状态下只能刹车保命。下一轮尝试在落点评价里加入“落地后 0.5 秒内的
   速度保持”项，或在花/锯 8 格内把视界延长到 3 秒。
3. **卡死图待机**：防推补丁已解决“被推入花”的问题；但如果对手能超过 `s+3.07`（理论上不能），
   待机仍会输。当前两张卡死图的 maxX 都是理论满分，平局是预期结果。
4. **怪物**：两场 18 只怪 0 击杀，现有“出现后再规避”足够；仍不预测刷新点。
5. **推挤**：后方被压到 4.2 格/秒是硬规则，追在对手后面接触就是负收益；本轮 8 帧 `r1-g1` 推挤
   全是这种负收益。下一轮在追击时优先保持 1 格以上距离，只在能跳过对手时才贴近。

## 七、数据口径与复算脚本

- 回放：`../../r1-g1.json.gz`、`../../r1-g2.json.gz`（相对本工作区，即运行目录根下）。
- 复盘数据提取：`tools/postmatch_r1.py` → `tools/postmatch_r1.txt`（每轮 maxX、死亡、推挤、怪物）。
- 逐窗口对拍 agent 决策：`tools/replay_agent.py`（把回放观察喂给 `agent.py`，与实际输入逐帧比较）。
- 推挤反事实：`tools/counterfactual_g2r1.js` → `tools/counterfactual_g2r1.txt`（真实 `simulation.js`，
  sol 用回放输入，deepseek 在指定窗口切换新版）。
- 公开战报的 `deaths` / `maxX` 只反映最后一个子局：`r1-g1` 最后一局（R2）的死亡与我方 1、sol 0
  一致，所以整场也是这个数；`r1-g2` 最后一局（R3）是 0:0，所以战报写 `[0,0]`，
  但整场是 sol 2 死、deepseek 3 死。
  战报的 `duration` 字段（7.45 / 32.8）与回放时间轴（50.35s / 205.70s）不是同一口径，本文以回放帧数为准。
