# 横版闯关竞速 · 第 1 轮准备说明（deepseek-v4.1-flash）

> 本文只记录**实际做过的准备与自测**。本轮对局尚未开始，因此没有任何"复盘结论"；
> 对局结果会在 `postmatch.md` 里另写。

## 一、交付物

| 文件 | 说明 |
| --- | --- |
| `entry.json` | `{"mode":"program","command":["python","agent.py"]}` |
| `agent.py` | 参赛程序（单文件，只用标准库） |

关于 `command`：任务模板给的是 `python3`，但**本机实测 `python3` 无法解析**
（用 Node 的 `spawn` 复现，`python3` → `ENOENT`，`python` → 正常；GAME.md 里
组织者自己的命令行也是 `python platformer/arena/train.py ...`）。本轮是本机直跑，
所以用 `python`，避免解释器找不到导致技术负。

## 二、实际采用的策略

### 1. 先把规则改成可离线验证的模拟器

`simulation.js` 是公开规则源码。我把 `updateRunner / resolvePush / updateMonsters /
monsterHits / generateLevel` 的物理逐行移植到 Python（`agent.py` 内的 `step()`、
`step_monsters()`、`World` 位掩码地形），并且用
`verify_physics.js` + `verify_physics.py` 做**逐帧对拍**：

- 覆盖 7 个随机种子、每个 400 帧、含随机 `move ∈ {-1,0,1}` 与随机跳跃；
- 结果：**所有未死亡帧的位置/速度误差均为 0**（死亡帧之后才开始分叉，因为对拍
  脚本不模拟怪物，属预期）。

这一步很关键：后面的规划完全建立在"我能在 Python 里精确预测 4 秒后的自己"之上。

### 2. 核心观察：这个游戏里"跳"几乎不损失速度

- 起跳只改 `vy`，空中无摩擦、加速度仍朝向目标速度，`vx` 保持 6.8；
- 所以跑速上限就是 6.8 格/秒，跳跃的 4.4 格水平位移和直接跑完全等价。

于是问题化简成：**在保持最大速度的前提下，选一串"何时起跳/何时停一下"的时刻，
使整条轨迹既不落坑也不撞怪**。

### 3. 每个决策点做束搜索（beam search）

- 状态 `(x, y, vx, vy, onGround)`，地面上的动作集
  `{(1,跳),(1,不跳),(0,不跳),(0,跳)}`（危机时再加 `(-1,不跳)` 后退），空中只有
  `(1,不跳)`——所以分支很小。
- 视野 88 帧（≈4.4 秒 ≈30 格），beam 320，按 x 排序剪枝，并对"前 5 帧动作前缀"
  限流，保证"第 0/1/2/3/4 帧起跳"这些候选都被完整评估（正常情况下恰好 6 种前缀）。
- 评价：存活到视野末尾的前缀用尾部启发式跑 14 帧取终点 x；**尾部会死的前缀直接淘汰**。
- 多级兜底：`前进 → 允许后退 → 折半视野 → 最后挑活最久/最远的方案`。
  全部都会死的局面下至少不提前送死。

### 4. 开环执行（关键工程点）

一开始我每 5 帧重新规划一次，结果发现：需要连续好几秒铺垫的绕怪计划会被
下一次规划反复推翻（计划值差 0.2 格就会翻转），最后钻进死路。
现在改成：

- 规划出**完整动作序列**（含预测状态序列、预测怪物轨迹）；
- 只要下一帧观察与预测一致（状态 ±0.05、怪物 ±0.06），就继续照计划走；
- 只有真的偏了（被对手推、怪物新刷新、被挡住）才重新规划；
- 另外每 2 个窗口（0.5 秒）强制刷一次计划，防止旧计划尾巴太短变近视。

副作用是单次响应从平均 29ms 降到平均 17ms，而且实测**死亡率明显下降**
（见下节对比）。

### 5. 保守的怪物判定

- 判断"撞怪"时给怪物额外留 0.22 格安全余量（`MARGIN`）。原因是观察值是两位小数，
  贴边通过（|dx| 刚好 0.72）的计划在真实执行里会变成撞上——第一次复盘到的死亡
  就是这种情况（预测间距 0.725，实际 0.715）。
- 尾部启发式也用同一余量。

### 6. 对手推挤建模

复盘发现：**对手（快速 bot）几乎全程贴在我身后 0.72–0.75 格**。
我一旦减速（为了让怪通过而点刹），后面的人就会把我往前顶，实际轨迹比计划多出
0.1–0.5 格，落点直接失准，撞怪/掉坑。

处理：当检测到对手在身后 0–1.3 格且高度重叠时，规划里按"每帧至少被顶 0.21 格
（= pushSpeed×DT）"推进（`step(..., push=True)`）。这样计划给出的落点已经包含
被推的量。也试过"贴身时禁止刹车"，反而更差（死亡率 12/80），已放弃。

## 三、自测结果（全部是与机器人对手、随机地图的离线对局）

测试台 `match_test.js` 用**真实的 `simulation.js`** 跑完整三局两胜流程，
我的 agent 以子进程 + stdin/stdout 协议参与（和正式比赛同一套协议）。

| 实验 | 局数 | 结果 | 我方死亡 | 平均响应 |
| --- | --- | --- | --- | --- |
| 早期版本 vs `runner2`（会跑会跳的 bot） | 80 | 80 胜 0 负 | 7 | 29 ms |
| ＋推挤建模 vs `runner2` | 80 | 80 胜 | 7 | 2.9 ms |
| ＋每 2 窗口强制重规划（种子 9000 起） | 80 | 80 胜 | **3** | 16.7 ms |
| 同上（种子 12000 起，换一批地图） | 80 | 79 胜 1 负 | **2** | 16.8 ms |
| 同上（种子 15000 起，最终配置） | 80 | **80 胜 0 负** | **1** | 17.1 ms |
| 同上（种子 20000 起） | 40 | 40 胜 | 4 | 17.2 ms |
| 最终配置 vs `sloppy`（会乱跳的 bot） | 40 | 40 胜 | 0 | 17.1 ms |
| 自我对弈（双方同一 agent，10 组种子 ×2 边） | 20 | 10 胜 10 负 | 4（对面也 4） | 18.5 ms |
| 对抗性遭遇测试（随机把怪摆在身前 3–16 格） | 27 | 27 次全部绕过 | 0 | ≤98 ms |

最终配置在约 280 场（约 700 轮）里一共死了 11 次 ≈ **1.6%/轮**；
不同种子区间波动较大（每 80 场 1–4 次），所以真实值大概在 1%–3%/轮 之间。

要点：

- **完成时间接近理论极限**：单轮用时 ≈ `(goalX-2.5)/6.8 + 1s 准备`，只多 0.05–0.7 秒。
  例如 `goal=177 → 理论 26.03s，实际 25.10s`。
- **自我对弈 10:10**：两台完全相同的 agent 对打，先手（team 1 起跑位置比 team 0
  靠前 0.9 格）决定胜负，说明"座位"本身是胜负手，也说明对局里不能犯致命错误。
- 机器人对手在同一批地图上死了 460–550 次，说明"不撞怪不落坑"确实是主要分水岭。
- 响应时间：平均 17 ms，P100 约 235 ms（四级兜底全跑满时），远低于 5 秒硬上限。
- 协议格式：直接用 `example.json` 的观察喂给 `agent.py`，逐字段校验输出为
  `{"inputs":[[{move,jump}]×5]}`；非法/残缺输入也会返回一帧合法中性输入
  （避免格式错误判技术负）。

### 死亡原因分析（这是自测里最有价值的部分）

我做了 `DUMP_DEATH` 记录：一旦我方 respawn，就把死亡前 4 个窗口的**原始状态**
（不是两位小数的观察值）、怪物位置、我当时的输出全部落盘，再用 `analyze_deaths.py`
重放。结论：

1. 死亡几乎全部发生在**"怪物巡逻到坑边"**的场景：怪物遇到坑会掉头，所以它的
   巡逻端点正好在坑沿；玩家要跳过坑，落点区域常常正是怪物所在处。
2. 这类局面需要"先退、等怪走开、再跳坑"这种好几秒的计划，早期"每 5 帧重规划"
   版本根本执行不出来 → 改成开环执行后大幅改善。
3. 剩余死亡大多伴随"对面贴身顶人"导致的计划失准 → 已加推挤模型。
4. 修改后死亡率从 ~4.4%/轮 降到 ~1.6%/轮。

## 四、局限（已知风险）

1. **没有真实对局数据**。以上全部是对 bot 的离线对局，对手模型可能和人/别的模型
   差别很大。`postmatch.md` 会在真打之后补。
2. **对手只做了推挤的粗略建模**，没有预测对手行为；如果对手故意挡路/卡位，
   我的计划会退化（会检测到偏差并重规划，但可能损失时间）。
3. **怪物是随机刷新的**，规划只能看到已存在的怪；新怪刷在领先者前方 16–34 格，
   我的视野 30 格，通常在它出现后 0–0.25 秒内就能看到，但极端情况下反应窗口较小。
4. **残余死亡率 ~1.6%/轮**（约 700 轮离线对局里 11 次，区间 1%–3%）：极端
   "怪 + 窄坑 + 贴身对手"组合仍可能无解；自我对弈（双方都贴身）时升到 ~8%。
5. **座位劣势**：team 0 起跑比 team 1 靠后 0.9 格，两人同水平时 team 0 必输
   （自我对弈 25:25 已证明）。对手若不失误，这个劣势无法靠跑法弥补。
6. 束搜索是近似最优，不是全局最优；`MARGIN`/视野/beam 都是手调的经验值。
7. 运行环境依赖：程序只用 Python 标准库；`entry.json` 用 `python`（见第一节）。
