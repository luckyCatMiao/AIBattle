# 第 1 轮提交说明（正式比赛前）

## 实际提交

- `entry.json`：program 模式，`["python", "-u", "agent.py"]`。
- 本机实际安装 Python 3.14.3，但 Bash 中没有 `python3`，因此使用已经实测可启动的 `python`，不照抄不可运行的示例命令。
- stdin/stdout 使用 UTF-8，逐行处理，返回 5 个单玩家输入并立即 flush。比赛期间不读取其他文件、不联网。

## 策略

1. 根据观察中的完整 tiles 实现 Python 版逐帧物理：加速度、空中移动、摩擦、重力、X/Y 分离碰撞、落地与碰顶，连同双方前后推挤关系。
2. 每个观察重新做 32 帧（1.6 秒）、束宽 36 的滚动搜索，按量化位置/速度合并状态，仅输出最佳路径的前 5 帧。每帧考虑向右跑、刹车，落地时额外考虑起跳。跳跃不是固定周期，而是结合地图、速度、怪物和对手预测搜索时机。
3. 拒绝已经下降至基础地面以下的轨迹，避免搜索把掉坑后的水平推进误当收益；拒绝预测怪物碰撞，并保留少量安全裕量。进度和速度为主要评分，起跳与刹车有轻微代价。
4. 怪物按源码规则逐帧预测巡逻、遇墙/坑转向。无敌时间按帧递减。
5. 对手只根据公开观察建模为向右跑、遇障碍和坑跳跃；若观察到对手在起点平地提前跳跃，会预测其持续连跳。搜索过程中执行源码同式推挤，尽量利用后位推进、避免被堵住。但并非对所有未知动作做极小极大搜索。
6. 缓存地图时校验实际 tiles，避免相同种子下人工测试更换地图造成旧缓存污染。

## 实际执行的本地自测

全部使用自己工作区中的公开 `simulation.js` 和自行编写的测试代码，未读取对方文件、control 目录其他资料或进程数据，未修改受保护文件。

### 对抗回归：`node test.js 120`

- 种子 101–220，120 张首局地图，双方座位交替；对手分别为持续跳跃、地形/怪物感知追赶、近身刹车阻挡三类控制器。
- 对手每个物理帧重新决策，我方每 5 帧决策；这是本地压力测试设置，不是正式比赛的观测频率。
- 最终版本 **109 胜 / 11 负**，累计 **12 次死亡**，其中多次死亡后仍追回胜局。全部回合以到达终点结束。
- 另有 10 个合成对抗场景：三格坑、前后紧贴、坑后怪物、坑口低顶砖块；增加持续跳跃、刹车阻挡、周期冲停对手。结果 **7 胜 / 3 负，1 次死亡**。输掉的低顶与部分前位阻挡场景也有零死亡的情况，安全通过不等于能超越领先者。
- 最终 130 个案例的单次决策延迟：各案例平均耗时的平均值约 **8.06 ms**，观测到的最高响应 **22 ms**（本机实测，不能保证其他机器相同）。
- 完整结果与死亡观察保存在 `test_results.json`。其中 final 是结束前最后可观察帧，避免换局后重置状态污染记录；winner 来自模拟器 round 事件。

### 准备中发现的问题及修正效果

- 最初低顶测试失败主要来自同种子合成地图复用旧缓存；校验 tiles 后，该场景零死亡。
- 扩大到 120 张地图后，仍发现近身连续跳跃对手引起的预测误差。增加连跳识别与平地刹车候选后，同批回归未降低总死亡数，不能声称已解决。
- 最早 `python3` 启动尝试失败；已改为本机可用的 `python` 并复验入口。准备中直接读取 example 的默认 GBK 解码也失败过；显式 UTF-8 解决，正式程序的标准输入输出也显式设为 UTF-8。

## 局限

- 对手模型不可靠，特别是近身挡路、突然跳跃、空中前后换位；本地仍有掉坑案例，没有实现最坏情形防推保证。
- 每窗口只收到一次观察，后 4 帧依赖预测；公开位置舍入亦可影响边缘碰撞。
- 搜索仅看未来 1.6 秒，状态量化和束宽会丢弃部分可行路线；只向右与刹车，没有主动后退重新助跑。
- 不预测尚未刷新的怪物、不利用私有 RNG；新怪物出现后才纳入路径规划。
- 安全碰撞裕量和拒绝低于基础地面的状态偏保守，可能错过能恢复的边缘路线。
- 原始起点有座位距离优势，速度一致时通常不能凭空超越，因此零死亡也可能输。
- 120 张地图仅测试每个种子的首局，不是 120 场三局两胜系列，也不是对未知正式对手胜率的估计。
