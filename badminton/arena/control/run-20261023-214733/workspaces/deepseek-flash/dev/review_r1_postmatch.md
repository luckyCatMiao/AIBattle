## 4. 我的改动：赛前做了什么，为什么没生效

### 4.1 赛前完成的改动（当前工作区 `agent.py`，SHA256 `951aa050…6265cc`）

1. **随机网高同步**：`engine_py.Match` 按 `seed*2654435761 + 97` 生成每局网高（1.35–1.95），`step_shuttle`、`strike`、`shot_trace`、`choose_shot`、`view().court.netHeight` 全部使用本局网高；`brain` 每次观察都用 `court.netHeight` 同步全局。
2. **发球抬角**：复刻引擎的 0.72 / 0.85 / 1.0 / 1.15 / 1.3 弧度逐档过网逻辑。
3. **`_trace_ok` 硬校验**：所有候选击球都用引擎同款 `shot_trace` 检查，过网高度必须大于 `netHeight + 0.05`、落点必须在对方场内，否则该候选 -400 分（分数转负即跳过），封死“假杀球”和挂网。
4. **深角诱饵发球防守**：发球前站到 **3.30 / 10.10**（阈值 3.05 外侧），诱使对手打深角，再用预排挥拍（下手挑高或上手回击）在对手触球后 2–6 帧内拦截；学习对手连续两次一致的触球点/帧偏移。
5. **每局状态重置**：进程检测到 `(id, seed)` 变化时，重置对手学习、`seen_event`、发球释放帧、`bait_hold_until`，避免两局换座位/换网高串状态。
6. **既有策略**：接发冻结期精确重建发球弹道，枚举触球帧/挥拍进度/上手或下手，逐帧模拟并验证真的碰到球；不蓄力；只有伺服确实需要超过基础速度时才冲刺；空挥有 0.85 秒冷却和 7 点体力消耗，所以每个方案必须先通过命中验证。

### 4.2 实战实际运行的是旧版

这一轮的实际行为与旧版 `dev/agent.r1bak.py`（SHA256 `37949385…bf758`，66,293 字节）高度一致，而不是当前 `agent.py`：

| 证据 | 观察 |

| 回放复现 | 把旧版接到两局回放前 500 帧上：**r1-g2 的 7 次挥拍全部与实况重合**（预测帧与实况差 1 帧的观测相位）；r1-g1 为 8/10 重合，剩余差异来自回放未带 `events` 导致的学习状态 |

| 网高 | 实况 1.66 / 1.67，旧版按 1.55 计算；g1 第 6 分的杀球正好在 **y=1.66** 撞网 |
| 发球防守 | 旧版没有深角诱饵；实况中我们 14 个发球分 0 保发、11 分被第一拍接死，符合旧版接发防守方案在快杀下的表现 |
| 进程时点 | 轮次目录 21:47 建立，最终 `agent.py` 22:21 才重建；如果裁判在轮次开始时就启动/冻结了 agent 子进程，进程加载的会是旧代码。engine 日志为 0 字节，无法直接看到启动时刻，因此这一条是“行为 + 代码比对”的推断，不是日志实证 |

## 5. 赛后诊断：三个直接问题

### 5.1 发球局结构性失守（首要问题）

- 14 个发球分 **0 保发**；11 个被 sol 第一拍接死。典型回合里我们 **0 次触球**，sol 只需 1 次杀球：g1 第 1/3/9/14 分，g2 第 2/4/6/8/10/16/19 分。
- 因为发球局必丢，**13 次破发全部被下一分立刻抵消**，全场没有一次连得 2 分。sol 只需要保住 8 个发球分就赢下两局。
- 旧版的问题不是“发球质量”单独造成的，而是**发球后的第一拍防守没有执行**：深角诱饵没上场，旧版的接发预判对 sol 的快杀不够快。回放里 sol 的接发杀球几乎每次都在我们触球前落地。

### 5.2 关键长回合体力崩盘

- **g1 2:2→2:5**：3 个回合（9/7/8）我们体力 **83.9→10.3（-73.6）**，sol **100→72.3（-27.7）**；仅第 5 分就 -33.7。
- **g1 第 11 分（19 回合）**：带着 15.6 体力进场，打完 0.6；下一分 4:8 时基本失去移动能力。
- **g2 6:5→6:8**：第 13/14 分两回合我们体力 **73.0→1.8（-71.2）**，sol **83.8→50.3（-33.5）**；第 14 分结束只剩 1.8。
- 两局终局体力 **6.1 / 12.9**，对手 **16.4 / 26.6**。体力见底后我们只能靠接发第一拍偷分，无法再打多拍，也无法保住发球局。
- 旧版在体力 >18 时只要伺服需要就冲刺（`dev/agent.r1bak.py` 的 `can_sprint` 条件），回放里出现单分 -33.7、-55.6 的消耗；同时缺少“提前拦截/放弃低概率球”的体力预算。

### 5.3 进攻转化率低

- 击球 60:60、杀球 32:24，但得分 13:22。g1 我们 19 个杀球只换 5 分，sol 12 个杀球换 11 分；g2 我们 13 个杀球换 8 分，sol 12 个换 11 分。
- 说明问题不在“杀球数量”，而在**落点、时机和体力**：很多杀球被 sol 防起，或者我们在低体力/低击球点强行下手，出球质量下降。
- 旧版偏好杀球，但在对手已经站好深角时仍连续杀同一区域，缺少吊球/高远球来拉开对手。

## 6. 下一轮改动计划（建议，按优先级）

1. **P0：保证“实际运行版本 = 最终构建版本”。**
   - 在 agent 启动时向 stderr 打一行版本标记（如 `AGENT_VERSION=<hash> BUILD=<time>`），不污染 stdout 的 JSON。
   - 赛前重新构建并在进入比赛前确认进程是新建的；如果裁判在轮次开始时启动进程，必须在那个时点之前完成构建。
   - 赛后用回放/版本标记核对，避免再出现“改了但没上场”。

2. **P0：把发球局从 0% 保法拉起来。**
   - 先确认深角诱饵在真实进程里生效；用“快杀接发”机器人做离线对照，而不是只对 r1 大脑自测。
   - 对照三种接发防守：深角诱饵 3.30 / tie 3.05 / 近网 2.90，以“对快杀机器人的保发率”选型。
   - 如果发球弧线可控，优先发高远/深角，逼对手挑球而不是直接杀；如果不可控，至少要让第一拍防守能稳定碰到球。

3. **P1：体力预算。**
   - 长回合默认关闭持续冲刺，只在“预测触球点确实超出基础速度可达范围”时短冲刺。
   - 给候选方案加体力成本惩罚；对明显追不到且不值得的球主动放弃，保留体力给下一个发球/接发。
   - 目标：6:6 时体力不低于 30；避免再出现单局 -70 的连续两分。

4. **P1：提高终结效率。**
   - 杀球落点优先深角/追身/对手反方向，避免连续杀同一区域；对手站深角时改用吊球或高远球。
   - 对“过网高度 < netHeight + 0.15”的杀球降级为高远/挑球，减少挂网和低质量杀球。
   - 用离线对照测试 `smash_lover` 开/关、吊球比例、落点候选权重，不要只凭感觉调。

5. **P2：安全余量。**
   - 当前 `_trace_ok` 的 0.05 格余量偏小；实际触球点与预测差 0.1–0.3 格时仍可能挂网。建议把余量提高到 **0.12–0.15**，并对上手杀球额外检查网口高度。
   - 保留“落点必须在对方场内”的硬校验；对贴网/贴边球降级处理，不要用 -400 分后的软选择。

6. **P2：复盘数据留档。**
   - 每分结束记录：发球方、回合数、双方击球/杀球、双方体力、结束原因、最后触球点。
   - 本轮 engine 日志为 0 字节，只能靠回放反推，下一次应直接留结构化 per-point 日志。

## 7. 数据口径与复现

- 比分、座位、`duration`、`errors`、`frames`、`windows`、`longestRally`、`hits`、`smashes` 来自公开战报；实际网高、逐分回合、体力、触球点来自回放 `r1-g1.json.gz` / `r1-g2.json.gz`。
- 回放帧率 20 Hz；体力是每帧采样值，文中保留 1 位小数，可能有四舍五入。
