## 2. 本轮最重要的发现：网高是随机的，而旧的 Python 移植把它写死成 1.55

`simulation.js` 的 `createMatch` 用种子决定网高：

```js
netRng = makeRng(seed*2654435761 + 97)
netHeight = round(netMin + netRng()*(netMax-netMin), 2)   // 1.35 ~ 1.95
```

- 上一次运行的种子 **7011/7012 恰好是 1.55/1.56**，所以“写死 1.55”的旧移植没暴露问题，
  上一轮真实对局也没有出现网高相关的异常。
- 本轮若沿用相邻种子，网高会是 **7021/7022 → 1.68/1.69**，更后面甚至 1.81/1.94。
  在 1.9 的网下，按 1.55 预测的杀球会直接挂网。
- 引擎还有一个危险兜底：`chooseShot` 在所有角度都过不了网时，会**不做任何校验**地返回
  固定 0.30 弧度的“假杀球”。在“我方后场高点杀向对方中场”的几何下，这个球会挂在网上
  并落回自己半场——等于白送一分。

本轮修复：

1. `engine_py.Match` 每局按同一公式随机网高；`step_shuttle`、`strike`、`shot_trace`、
   `choose_shot`、`view().court.netHeight` 全部使用本局网高。
2. 发球抬角：网越高，引擎会依次尝试 0.72/0.85/1.0/1.15/1.3 弧度直到过网；`planner.predict_serve`
   复刻了这套抬角逻辑。
3. `brain` 每个观察都用 `court.netHeight` 同步全局网高，规划器的弹道、出球解算全部跟随。
4. 所有候选击球增加 `_trace_ok` 硬校验：调用引擎同款 `shot_trace`，过网高度必须
   `> netHeight + 0.05`（实际撞网阈值是 `netHeight + 0.07`），且落点在对方场内；
   否则该候选 -400 分并跳过。这条直接封死了“假杀球”自杀。
5. 进程可能连续处理同一轮的两局（换座位、换网高），因此检测 `(id, seed)` 变化时重置
   对手学习、`seen_event`、发球释放帧等状态。

**对拍验证**：把 `simulation.js` 复制到 `dev/simref/`（仅删掉两个未定义导出名），用同一组
160 个窗口的随机输入跑 JS 与 Python，对比 frame/phase/比分/发球计时/球速/球位/体力等字段，
**种子 7011(1.55)、7021(1.68)、7041(1.94)、8005(1.37) 各 57 窗口，全部 0 处不一致**。

## 3. 实际采用的策略

### 3.1 接发（进攻）
沿用上一轮验证过的方案：发球冻结期用 `serveLeft` 精确重建发球出手帧与弹道；枚举
“第 t 帧、挥拍进度 e、上手/下手”的所有候选触球，由球的子步位置反推所需 x，用引擎
`update_player` 逐帧模拟自己的移动并**逐帧验证是否真的碰到球**；按出球价值打分，
过滤会挂网/出界/落回自己半场的球。本轮接发仍然是对手最难受的一环。

### 3.2 发球防守（本轮核心改动：深角诱饵）
关键几何：接发方上手杀球的落点由**我方的 x** 决定——离网方向的近网角（5.1）或深角（1.0），
取离我方更远的那个。分界点是 **3.05**（右侧镜像 10.35）。

- 站在 3.05 以内 → 对手打慢速近网球（约 5–6 格/秒），但球落在身前 2 米多，很难追上。
- 站在 3.05 以外 → 对手打深角；`solveSpeed` 对深角饱和，高网时还会退化成 13–18 格/秒的平球，
  球会从我们身边低空飞过。

本轮采用后者的“深角诱饵”：发球前就站到 **3.30 / 10.10**，用对手触球点的投影（以及从
`events` 里学习到的连续两次一致的触球点/帧偏移）预测出球，提前排好这一窗的挥拍
（下手挑高或上手回击，两种都试，由逐帧命中验证决定），命中后立刻转入正常回合逻辑。
学习机制让对手连续两次用同样节奏接发后，第三次起按他的真实触球点排拍。

### 3.3 回合
仍是“候选 + 逐帧命中验证 + 出球打分”：优先对手够不到的落点，其次安全的高远/挑球；
球会出界时不碰（白送的分不要送回去）。所有击球都过 `_trace_ok` 安全校验。
一般回合防守站位保持 `mid`（4.0 / 9.4）；对照过 `tie`（2.95）——见 4.2，得失不明显，未采用。

### 3.4 体力
默认**不蓄力**（蓄力易出界）；冲刺只在伺服确实需要 > 基础速度时开启；空挥会进 0.85 秒冷却
并耗 7 点体力，所以每个方案都必须先通过“真的能碰到球”的验证。

## 5. 局限与风险

1. **本轮没有任何真实对局数据**。所有对手都是自己写的（r1 参考大脑/脚本），不能代表 sol；
   “保发率 40%”只是对 r1 大脑的离线数字。
2. **深角诱饵依赖对对手触球时机的预测**：球被对手击出后只有 3–5 帧就到我们身边，
   必须在上一窗提前排拍；预测差 1–2 帧就可能空挥。学习机制要求对手连续两次触球点
   接近（<0.35 格、帧偏移差 ≤3），对手若混用不同接发节奏，可靠性下降。
3. **高网（≥1.9）容易打成长时间对拉**：双方都能把弱杀/高远接回来，一分可能打满 240 秒，
   胜负由时间到时的比分决定（自测里出现过 2:1、5:2 这种低比分）。没有实现起跳高点进攻，
   这是下一步最值得做的能力。
4. **7021/7022 种子下对 r1 大脑总体落后**，且长回合把体力打到 0，说明体力分配与终结能力
   仍有明显短板；样本只有 4 局、且自对弈高度混沌，不能按自测比分做细调。
5. 网高随机化后，之前所有基于 1.55 的旧结论（包括上一轮复盘里的落点数字）只在 1.55 附近成立；
   本轮已改为按观察里的 `court.netHeight` 现算。
6. 本机只有 `python`（3.14），`where python3` 为空；提交命令仍按本轮规定写
   `["python3","agent.py"]`（上一次运行的同一命令在现场可以正常启动，故保持规定写法）。
