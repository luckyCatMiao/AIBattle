## 4. 核心诊断：杀球落点分支与“中点陷阱”

### 4.1 引擎规则

`simulation.js:230-255`（我们的 Python 移植在 `engine_py.py:403-430`）在判断为杀球后，会在两个落点中二选一：

```js
shortX = netX + dir * 1.6;          // 近网 1.6 格
deepX  = dir > 0 ? 12.4 : 1.0;      // 深角
target = Math.abs(shortX - opp.x) >= Math.abs(deepX - opp.x) ? shortX : deepX;
```

也就是说，**落点不是由我们决定，而是由击球瞬间对手的 x 决定**。两个落点的中点是：

- 我们在左半场（g1）：`(8.3 + 12.4) / 2 = 10.35`
- 我们在右半场（g2）：`(5.1 + 1.0) / 2 = 3.05`

`chooseShot` 从最陡的 −0.42 开始逐档尝试；一旦走**近网分支**：

- 从 0.87–0.99 格的一传接触点（y≈2.15–2.20），第一个能过网的角度是 +0.06～+0.16，求解速度被压到下限 **5.0**——这是一记 5 格/秒的软推/短吊，不是杀球。
- 从 2.9–3.5 格的后场接触点（y≈2.12–2.70），所有下压角都过不了 1.92 的网，`chooseShot` **回退到固定 +0.30**；球先升到 2.37 再下落，0.55–0.65 秒后以 y=1.54–1.89 撞网。

走**深角分支**时，同样的接触点解出 12.7–15.8（sol 更高更靠网的接触点是 14.0–21.9，多数 17.5–21.9）。

### 4.2 我们的 34 次 `smash` 分解

| 分支 | 次数 | 出球速度 | 结果 |
|---|---:|---|---|
| 近网（shortX = 8.30 / 5.10） | **27** | 21 次 5.00；6 次 5.78–6.44 | 21 次 5.0 软推（**全部是一传**）；6 次 fallback +0.30 **撞网**，直接送 4 分 |
| 深角（deepX = 12.40 / 1.00） | **7** | 12.68–15.75 | 只有 2 次 ≥14（f103 15.75、f276 15.12，均为起跳）；全部被 sol 接回 |

`results.json` 里的 `smashes` 是“`kind == 'smash'`”的计数，发生在 `chooseShot` 之前，
所以这 34 次全部被记为杀球，**包括 21 次 5.0 软推和 6 次撞网**。公开战报的“我们 23 / 11 次杀球”
（g1 23、g2 11）并不代表 34 次有效下压；真正 ≥14 的只有 2 次。

### 4.3 毫米级翻转（已用真实 JS 引擎逐帧复现）

把回放的 `windows` 原样喂回 `simulation.js`，在 `strike()` 处打印击球瞬间的 `opp.x`，得到：

| 对局/帧 | 接触点 | 击球瞬间对手 x | 与中点差 | 目标 | 出球 |
|---|---|---|---:|---|---|
| g1 f67 | (3.793, 2.231) | sol x = **10.352170** | +0.002170 | 8.300（近网） | **5.781，+0.30，撞网** |
| g1 f1628 | (3.781, 2.182) | sol x = **10.344989** | −0.005011 | 12.400（深角） | **12.697，-0.06** |
| g1 f1653 | (4.150, 2.147) | sol x = **10.348043** | −0.001957 | 12.889（深角） | **13.108，-0.06** |
| g2 f249 | (7.565, 2.202) | sol x = **3.045888** | −0.004112 | 4.831（近网） | **5.001，+0.06** |

同一场比赛里，sol 的 x 只在中点两侧 **1–5 毫米**，就从“12.7 的深角杀”变成“5.8 撞网”。
我们的 `_eval_contact`（`brain_py.py:356-402`）只用 `opp_x_at()` 的一个预测值：

```python
def opp_x_at(opp, t):
    x = opp["x"] + opp["vx"] * t * DT
    ...
```

在 t≈0.5 s 的预测里，这点误差无法避免。模型只要预测 sol 在 10.34（中点偏深一侧），
看到的就是 12.57 的有效深角杀；实际 10.352，引擎给出 5.78 撞网。**6 次撞网、4 个丢分，
本质上是这个分支在毫米尺度上的不可预测性，而不是“击球点不够高”。**

| | 我们接 sol 发球 | sol 接我们发球（g1 f30） |

| 距网 | 0.87–0.99 | 0.865 |

两边的一传接触高度、距网距离几乎一样，速度却差 3.2 倍。差别只在**对手站在哪**：
sol 站在中点，我们的一传被分到近网分支；我们站在 4.40，sol 的一传被分到深角分支。
这不是“sol 的击球点更高”，而是“sol 的防守站位让引擎替它把我们的球变成了软推”。

即使走深角分支，我们的 7 次后场杀球也只有 12.68–15.75；sol 的深角杀是 14.0–21.9（多数 17.5 以上）。差别在接触几何：

| 我们（g1 后场） | 2.6–3.5 | 2.15–2.70 | 12.68–15.75 |
| sol（g1/g2） | 2.2–2.55 | 2.42–2.68 | 14.01–21.93 |

第 3 轮加的起跳本来是为了解决“高度”，但后场起跳（f142 接触 2.703）仍然走短角 5.87 撞网——
**高度不等于下压，必须同时靠近网**。

## 7. 下一轮改动建议（按优先级）

### P0：按“最坏分支”评估杀球，而不是单点预测

`_eval_contact` 目前只对 `opp_x_at(opp, t)` 的一个值调用 `shot_from_contact`。
在 `brain_py.py:356-402` 里，对 `ox` 取一个小集合（例如预测值 ±0.15，且强制包含中点两侧
`(shortX + deepX) / 2 ± 0.05`），分别计算 `shot_from_contact`；只要**任一分支**出现
`shot["kind"] == "smash"` 且（`netHit` 或 `speed < 10`），就扣 300–400 分或直接丢弃该候选。
这样 f67 这种“预测 10.34 看到 12.57、实际 10.352 得到 5.78 撞网”的候选会在计划阶段被拒。

### P1：高网 + 后场，不要选“会被分到近网”的杀球接触

在 1.85 以上的网高、接触点距网 >2.6、且对手接近中点时，主动放弃上手杀球：

- 让球再降 0.1–0.2 格，使 `t = (sy-1.8)/0.55 ≤ 0.5`，引擎自动改判 `clear`（目标 11.9，7–9 格/秒）；
- 或者改用下手挑高（`swingType=-1`，目标 11.4），把球送到 sol 的端线，而不是送到它手里。

这两种球的绝对速度不高，但**不会撞网、不会送 5.0 软推**，能把“三拍处刑”拖成中性回合。

### P2：一传先判断分支，再决定要不要“杀”

一传接触点在 0.87–0.99 格、y≈2.17 时，若预测到近网分支（速度 <10），不要用上手 `smash`。
可以：

1. 等球降到 1.5 左右用下手挑高到 11.4，逼 sol 后退；
2. 或者把接触点让到更深（x 更小），用 `clear` 到 11.9。

关键是**不要把 5.0 的短吊记成“杀球”**。`KIND_BASE`（`brain_py.py:17`）里 smash=100、lift=22，
而 `_eval_contact` 只按 `kind` 给分，不看实际速度，所以 5.0 的“smash”仍然拿到 100+ 分。
建议在 `brain_py.py:363-370` 加一条：`if kind == "smash" and shot["speed"] < 12: score -= 80`
（或按 `speed` 线性加权），让“名义杀球、实际软推”不再占优。

### P3：高网防守站位——站到中点之后，逼对手走短角

sol 的杀球之所以是 18.5，是因为我们站在 x=9.4（g2）/ 4.0（g1），离近网落点 1.1 格、离深角 3.0 格，
引擎因此选择深角。若我们站到**中点之后**（g2 x≥10.4，g1 x≤3.0，即离网约 3.7 格），
sol 的落点会翻到近网（8.3 / 5.1）；从它的接触点（2.2–2.5 格、2.4–2.7 高）打近网，`chooseShot`
会给出 5.0 的短吊（接触点低时甚至直接撞网），而不是 18.5 的深杀。我们再用 5.0 的飞行时间
（约 0.9 s）从 10.4 冲到 8.3。
这是一个**用站位换分支**的防守方案，需要在 1.90–1.95 网高上做 A/B 验证（对手可能会改吊/高远）。

### P4：体力死区改成“站定回体”

现在 62–66% 的帧落在 0.8–3.2 的死区，回体帧只有 33%。在 `servo_inputs` / `plan_control` 里加
0.10–0.15 格的死区：目标距离小于阈值时 `move=0`，把死区帧转成回体帧。目标是把回体帧从
33% 提到 55% 以上；按 g1 的 99 秒算，这相当于多回 130–200 点体力。

### P5：0 体力 / 球在对方半场时的空挥守卫

g2 的 7 次空挥里，有 5 次是球在 x=8.73、我们站在 9.49 的“差 0.76 格”挥拍。加一条：
若 `me.stamina < 3` 或预测接触点不在拍面半径内，禁止起手；宁可丢这一拍，也不要多花 7 点体力
并锁死下一次挥拍窗口。

### P6：A/B 要加入“中点防守”对手

下一轮的自测至少加一个场景：对手每次回位都站在两个杀球落点的中点（`(shortX + deepX) / 2`，
即 `netX ± 3.65`）。
否则我们还会用“对手是我们自己”的 A/B 得到 55%，然后在正式比赛里被同一个分支陷阱打 0:22。

## 8. 数据与复现

以下命令在工作区根目录（本文件所在目录）执行：

```bash
# 计分、回合、体力、空挥、网前失误、一传几何
python -I -X utf8 dev/analyze_r3.py ../../r3-g1.json.gz ../../r3-g2.json.gz > dev/analyze_r3.txt

node dev/replay_probe.js ../../r3-g2.json.gz 0 99999 2> dev/probe_g2.txt
```

- `dev/analyze_r3.py` 只读回放，不写文件；所有比分按“我们:sol”输出。
- `dev/replay_probe.js` 在 `dev/` 下生成一个临时 `simulation.js` 副本并注入日志，**不修改**
  工作区的冻结文件；用它重放 g1 得到 `score [0,11], frame 1988, net 1.92`，g2 得到
  `[11,0], frame 1254, net 1.93`，与回放完全一致，说明复现的是同一场比赛。
- 逐帧快照：`dev/r3_tailevents.txt`（最后 60 条事件，含精确接触点和速度）、
  `dev/r3_frames_serve.txt`（发球前后逐帧球路）。

## 9. 局限

1. 只有两局、各一个种子；对 sol 的“意图”只能从站位推断，不能从代码确认。
2. 落点分支的结论是确定性的：用回放的原始 `windows` 重放真实引擎，f67 / f1628 / f249 的分支
   与出球都能逐项对上，不是统计猜测。
3. 两局合计 0:22 是极端比分；并非每一分都由分支造成——g1 P09、g2 P06 是 sol 的高远球直接落地，
   与我们的追球/体力也有关。
4. P3 的“站到中点之后”是本文最重要的待验证假设：它能解释 sol 的 18.5 为什么总是打到深角，
   但还没有在 A/B 里证明我们站过去之后能稳定接到 5.0 的短吊。
5. 本轮没有改 `agent.py`；以上 P0–P6 是下一轮的改动清单，不是已经生效的提交。
