# 横版羽毛球 · deepseek-v4.1-flash 第 1 轮 review

> 说明：本轮**尚未与真实对手对局**。下面所有数字都来自我本机的离线自测（用公开规则源码 `simulation.js` 搭的对战台），不包含任何对局复盘。

## 一、最终提交

- `entry.json`：`{"mode":"program","command":["node","agent.js"]}`
- 运行方式：常驻 Node 进程，stdin 逐行读观察、stdout 逐行写 10 帧窗口并立即 flush。
- 依赖：只用标准库。因为工作区里的 `simulation.js` 末尾导出了两个未定义标识符（`canSwingNow`/`predictContact`），直接 `require` 会抛错，所以我把**同一份公开源码原样复制**成 `engine.js`（只去掉导出里那两个未定义名字），作为本地预测/自测用的引擎副本。物理逻辑与公开源码逐字一致。

文件分工：

| 文件 | 作用 |
|---|---|
| `agent.js` | stdin/stdout 协议层；任何异常都兜底输出中立窗口，避免技术负 |
| `brain.js` | 决策：局面重建 → 候选方案前向模拟 → 打分选优；预判对手回球 |
| `core.js` | 观察重建为引擎状态、纯弹道预测、复刻 `strike()` 的出球解算 |
| `engine.js` | 公开规则源码副本（供离线前向模拟） |
| `dev/` | 对战台与自测脚本（`arena.js`、`probe.js`、`profile.js`、`eval2.js`、`rr.js`、`e2e.js`） |

## 二、我理解到的关键机制（都靠自测验证过）

1. **出球不是按键决定的，是击球点决定的。** 上手挥拍时 `t=(sy-1.80)/0.55`、`near=clamp(1-(离网距离-3.2)/2.5)`，`t*near>0.55` 才是杀球；否则 `t>0.5 且对手在后场 且 离网>2.6` 变成吊球，其余一律是高远球。所以"打什么球"实际上由**我在哪、在多高碰到球**决定，我的规划器就是围绕这一点做的。
2. **判定半径 0.38 格，但拍面是一段扫掠弧线。** 上手在第 2–6 帧从 1.911 扫到 1.533 格，配合起跳（+0.51 格）可覆盖 ~1.15–2.80 格高。因此"能打到"= 在 5 帧窗口内球经过拍面轨迹附近，而不是站到球旁边。
3. **体力只在 |vx| > 3.2 时消耗**（跑动 −9/s），0.8 < |vx| < 3.2 既不耗也不回。这条是最大的隐藏收益：把常规移动目标速度压在 **3.18 格/秒**，整局跑动几乎免费。自测里对手（以及我早期的版本）满速乱跑，打到第 8 分体力就见底、明显够不到球；改成 3.18 后我的体力长期保持在 60–100。
4. **发球是固定的**：发球点固定（左方 x=3.8 / 右方 x=9.6，y=1.35），角度 0.72、按落点解速度，落点在中场（约 9.9 / 3.5）。所以接发球方可以提前 0.8 秒起跑、在网前高点直接杀球——这是最稳定的得分手段。
5. **每个窗口 10 帧、5 帧挥拍窗口**意味着真正要做的是"把起拍帧对准球到拍面的那一帧"，误差超过 ±2 帧基本就空挥，还要吃 0.85 秒冷却。

## 三、实际采用的策略

### 1. 局面重建 + 前向模拟（核心）

每个窗口我把观察（x/y/vx/vy 都是 round2 的近似值）重建成一个引擎状态副本，然后：

- 纯弹道预测球未来 95 帧（含球网反弹、出界、落地）；
- 对候选击球帧 k 和候选动作（上手/下手、是否起跳、起拍帧），在克隆局里用真实的 `step()` 跑一遍，看**实际**会不会碰到球；
- 命中后用 `strikeModel`（逐字复刻引擎的 `strike()`/`chooseShot()`）重算真实出球速度，再预测落点；
- 用 `evalShot` 给这一拍打分：下网/出界/落回自己半场是大负分；否则估计"对手要跑多远、还剩多少时间"，接不到就是高分，再叠加快球奖励和落点远离对手的奖励。
- 取分数最高的方案输出前 10 帧。

因为克隆局就是引擎本身，规划里"能否击中"的判断与实际比赛一致（观察只有 0.01 的舍入误差）。

### 2. 接发球：冲网高点杀球

发球轨迹是确定的，所以接发时我会预测球在网前的高度，冲到离网最近的位置、起跳、在最高点起拍，把发球直接杀下去。自测里这条几乎 100% 成功，是主要得分来源。

### 3. 发球后的"预判拦网"

对手接发也大概率会冲网杀球，而这一拍只有 0.15–0.25 秒，等我看到球再反应必然来不及。所以我加了一条**预判**：在我刚发完球、球还在对方半场时，用"浅层自己"模拟对手接下来 3 个窗口的出球；如果预测到对手要杀球，就提前 16 帧内移到拦截位（离网约 2.8–5 格区间），按预测的触球帧提前起拍。拦到之后球会飞向对手后场深处，而他刚冲在网前，通常回不去。

这条是有代价的：如果对手其实是打高远球（不是杀球），我会白挥一拍并站在偏前的位置。所以我把它限制为"预测到杀球 且 对手触球在 16 帧内"才启用，其余情况交给常规追击。

### 4. 体力与站位

- 常规移动目标速度 3.18（免费区），只有明确追不到球时才放开到满速（`hard` 参数，目前基本不触发）；
- 得分间隙（`phase==='point'`）站定回体力（+6/s）；
- 常规站位离网 2.8 格。

## 四、自测结果（本机离线，确定性引擎，无随机）

自测台 `dev/arena.js` 用公开引擎跑完整对局；因为引擎没有随机数，同一个策略组合的结果是**唯一确定**的，所以下面是单局结果而不是胜率统计。

**对局结果（左边是 team0 的比分）**

| 对手 | 我作为 team0 | 我作为 team1 |
|---|---|---|
| `noAnt`：同一套 brain 关掉预判（强追球型） | **11:6** | 我 **11:5** |
| `simple`：预测球路 + 高远球回球 | **11:2** | 我 **11:4** |
| `simpleU`：只用下手挑高 | **11:0** | 我 **11:0** |
| 完全不动 | **11:0** | 我 **11:0** |
| 伪随机乱动 | **11:0** | 我 **11:0** |
| 自己的镜像 | **14:12**（打到加分） | — |

**参数选择**：对四组参数（预判提前量 T × 常规站位）做了交叉循环赛（`dev/rr.js`），按"两个座位都赢"计数，选定 `T=16 帧 / 离网 2.8 格 / FREE_SPEED=3.18`。

**端到端协议测试**（`dev/e2e.js` / `dev/e2e2.js`，真实子进程 + stdin/stdout 喂观察）：

- 我坐 team0：102 个窗口、870 帧、比分 11:6，全部窗口格式合法，单窗口最长 49 ms，整局 256 ms；
- 我坐 team1：153 个窗口、1530 帧、比分 14:12（镜像局），单窗口最长 41 ms，整局 460 ms；
- 两次都远低于 5 秒/次的硬上限。

**其它检查**

- 未出现"出界"失分（自测对局里失分原因只有"落在对方半场"和一次"落在自己半场"），说明出球落点评估没有把自己打崩；
- 受保护文件（`RULES.md`/`GAME.md`/`simulation.js`/`catalog.js`/`example.json`）未改动。

## 五、局限与风险

1. **预判依赖"对手像我"这个假设。** 浅层模型用的是我自己的打法；对手如果风格差异大（例如接发一律高远球），预判会误判并让我白挥、站位偏前。自测里对 `simple` 仍能 11:2 / 11:4 取胜，但对真正的强敌这是最脆弱的一环。
2. **引擎里存在一个利用漏洞，我没有使用。** 规则写明"接发球方必须先回球"，但引擎没有把发球方锁住：发球方可以自己冲到网前把**自己的发球**直接扣死（实测 x=6.29 起拍、球落 11.65，对手完全够不到），而且 `p.lastHitFrame` 不记录发球，连冷却都没有。这会让"谁发球谁赢"、比赛完全退化。我认为这与 RULES.md 的明文规则冲突，属于漏洞利用而不是打法，所以**没有实现**；如果对手使用，我这边没有有效的合法反制（拦网时机要在同一帧对上，扫描下来基本不可行）。这一点如实记录在此。
3. **接发球杀球是双刃剑。** 我接发必杀，但对手如果也会"预判拦网"，局面就会回到"发球方占优"。自测镜像局 14:12 说明双方都成熟时胜负非常接近。
4. **规划用的是 round2 的观察。** 落点预测误差约 0.01–0.05 格；对 0.38 的判定半径够用，但对"压线出界"这种边界球有极小概率误判（自测中未出现）。
5. **没有针对具体对手做任何适配**，所有参数都是对自测对手族折中选出来的，换一个风格完全不同的强敌可能需要重新调 `T` 和站位。
6. **没有做过 240 秒满时长对局的压力测试**：自测最长 1526 帧（约 76 秒）。按 49 ms/窗口外推，480 窗口约 24 秒，仍在预算内，但未实测。

## 六、下一步（若进入第 2 轮）

- 用"对手实际移动轨迹"替换"对手像我"的预判模型，降低误判率；
- 对拦网/不拦网做在线决策：观察对手前两次接发是杀球还是高远球，再决定是否压上；
- 补 240 秒满时长与低体力场景的回归测试。
