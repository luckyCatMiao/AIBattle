# 横版羽毛球 · deepseek-v4.1-flash 第 2 轮准备报告

> 本轮尚未开赛。本文只记录**实际采用的策略、离线自测结果与局限**；没有真实对局，因此不含任何赛后复盘或编造的比分。
> 第 1 轮赛后复盘已另存为 `postmatch_r1.md`（原文保留）。

## 0. 一句话结论

第 1 轮两局共 15 次空挥，其中 14 次来自“发球后把自己的发球当来球打”（g2 另有 1 次发生在最后一波长回合）。本轮先堵死这条（`lastTeam === 我方` 时禁止规划击球），再把发球防守做成**从事件流学习对手接发习惯的自适应预挥**：对手贴网高点接发（第 1 轮 sol 的实测画像：离网约 0.87 格、y≈2.2、34 格/秒深区杀球）时冲网用上手在网口截击；对手低点/深区接发时退回深位用下手预挥或不挥。离线自测里，发球保发从第 1 轮的真实 2/17（11.8%）提升到对“早高点接发”对手 **21/21**、对“低点晚接”对手 **20/21**，每局空挥 0–2 次。

## 1. 第 1 轮教训 → 本轮实际改动

第 1 轮真实数据（两局 9:11、7:11）：我方发球 17 次仅保发 2 次；sol 接发得分 15/17；两局 15 次空挥 + 15 次起跳把体力打到 0–10，sol 终局仍有 85–90。据此按优先级改了五处：

### 1.1 P0：绝不碰自己刚打出的球

`brain.js` 主决策里，球权判定先于一切击球规划：

```js
if (g.shuttle.lastTeam === team) {
  if (g.rally === 0 && TUNE.serveDef) return serveDefense(g, team); // 我方发球在飞
  if (TUNE.counterDef) return counterDefense(g, team);              // 我方上一拍在飞
  return 回位;
}
```

这条保护直接消掉了第 1 轮“发球后追着自己的发球空挥”的 15 次空挥。自测中另有独立脚本检查“发球后同队第一拍触球 / 连续同队触球”，6 局均为 **0 次**。

### 1.2 P0：发球防守必须预挥——先证明“看到球再挥”来不及

用公开引擎逐帧测量（`dev/defprobe.js`、`dev/solprobe.js`）：

- 我方发球在 `frame 16` 出手，约 `frame 28–29` 过网，落点 x≈9.9；
- 对手在网前高点触球后，杀球 3–4 帧就到我们拍面；
- 扫描“站在 P、绝对帧 S 起拍”的全部组合：**S ≥ 31 的合法防守为 0**；能接到的组合全部集中在“对手触球前 2–4 帧起拍”。第 1 轮复盘里“第 31 帧后起拍全部失败”的判断被本轮扫描再次确认。

所以发球防守的核心不是反应，而是**预测对手触球帧**。

### 1.3 关键发现：站位会改变对手杀球的落点，且网前截击收益极高

引擎的 `strike()` 在杀球时按“离对手更远的角落”选落点（`shortX = netX+1.6`、`deepX = L-1.0`）。这带来两个实测结论：

1. **深位站位诱导软球（已否决）**：站在离网 2.75–3.1 格（中线以内）时，对手的杀球会被系统强制打到近网 5.1 附近，速度只有约 5–6 格/秒；但软球落点离深位仍有约 2.2 格，0.5 秒内够不到。扫描中该路线对基准版 1–2/10 胜，明显更差，已放弃。
2. **网前截击（采用）**：站在网前 0.35 格（team0 为 x=6.35）时，对手贴网高点杀球会在过网瞬间（y≈1.9）进入上手拍面。此时起拍上手会把球变成一记落向对方后场的高远球，而对手正压在网上——自测中这几乎是直接得分。用 `dev/solprobe.js` 按第 1 轮 sol 的画像（第 30 帧触球于 7.57/2.2、34 格/秒）复算：起拍帧 = 触球帧 − 3 时，拍面在 `(6.81, 1.85)` 与球距离 0.25，稳定截击；起拍晚 1 帧即失败。

### 1.4 P0：自适应发球防守（从事件流学习，不依赖对手代码）

`serveHistory()` 从 `obs.events` 里找“我方 serve 事件 → 对手第一拍 hit”：

- `h` = 对手接发触球高度；`dt` = 触球帧 − 发球帧；
- `h ≥ 2.12` 且离网 ≤1.9 → **rush**（冲网 + 上手预挥，起拍 = 发球帧 + dt − 3）；
- 否则 → **block**（退到离网 3.4 格 + 下手预挥，起拍 = 发球帧 + dt − 2）；触球低时干脆不预挥，交给常规追击；
- 第一分没有历史 → 用物理预测（`predictContact()`）估触球点，且默认 block（保守）；
- 冲网时强制 `S ≥ 发球帧 + 11`，保证起拍生效时发球已过网，避免“自己打自己发球”。

阈值 2.12 不是拍脑袋：引擎在贴网处 `smash > 0.55` 等价于 `y > 1.8 + 0.55×0.55 ≈ 2.1025`，2.12 就是“必出杀球”的分界。自测里：

- 对手是“贴网高点早接发”的自家大脑：保发 **21/21**；
- 对手是“低点晚接/挑高”的 `simple`：保发 **20/21**；
- 纯 rush 对低点对手只有 6/21（会因站位过前丢后场），自适应把它救回到 20/21——这就是做自适应的直接原因。

### 1.5 P1：修速度控制器 + 起跳预算

- 旧版 `moveCtrl` 返回 `(desired - vx) / (a·DT)`，但引擎的 `move` 语义是“目标速度比例”。旧写法在接近目标时把目标速度拉回 0，形成“加速—急刹—再加速”的抖动（第 1 轮复盘 §3.6）。新版改为 `clamp(desired / maxSpeed, -1, 1)`，并让 `moveSeq` 与引擎同模型；常规目标速度压在 3.18（低于 3.2 的跑动耗体阈值）。
- 起跳 −10 体力，加 14/24 分成本（体力 <70 时更贵），体力 <45 不允许起跳；对早高点对手的自测起跳从第 1 轮的 7–8 次/局降到 **0 次/局**。
- 低体力（<30）时给高点球额外扣分，优先重置回合。

### 1.6 P2：连续性防守

我方球在对方半场时，`counterDefense()` 用同一套 `predictContact()` 预测对手的高点回球，并在防守位提前下手，争取把发球局里的“第二拍杀球”也接起来。实测可以把“截击→对手再杀→再截击”的回合链延续下去；它不是保发的必要条件，但在长回合里多一层保险。

## 2. 最终策略一览

```
point / finished        → 站定回体力 / 回位帧
serve 且我方发球        → 按 useRush() 站到网前或深位（冻结期不挥拍）
lastTeam === 我方       → 发球在飞：serveDefense（学习到的 dt 预挥）
                          上一拍在飞：counterDefense（预测对手高点触球后预挥）
其余（来球）            → 预测弹道 → 逐候选触球帧前向模拟
                          （上手/下手 × 起跳/不起跳 × 起拍帧）
                          → 用真实 strike/chooseShot 复算出球
                          → evalShot 评估对手可达性 + 起跳/体力成本 → 选最优
```

可调参数集中在 `brain.js` 的 `TUNE`：

```js
{ readyOff:3.4, defOff:3.4, freeSpeed:3.18,
  allowJump:true, jumpMinStamina:45, jumpCostHigh:14, jumpCostLow:24,
  serveDef:true, serveDefLead:2, counterDef:true, counterLead:0,
  serveStyle:'auto', rushLead:3, autoDefault:'block', smashContactY:2.12 }
```

`engine.js` 是公开 `simulation.js` 的本地副本，仅去掉了导出列表里两个未定义标识符；`core.js` 复刻引擎的 `strike/chooseShot` 供前向模拟。受保护文件 `RULES.md`、`GAME.md`、`simulation.js`、`catalog.js`、`example.json` 未改动。

## 3. 自测方法与结果

### 3.1 方法

- 用本地 `engine.js`（= 公开 simulation.js 的物理）跑完整对局，双方都只能每 10 帧提交一次，和真实协议一致；`dev/analyze.js` 逐帧统计挥拍/命中/起跳/跑动/体力/每分归属。
- 对手全部是自建机器人：`brainEarly`（自家大脑，贴网高点早接发，最接近第 1 轮 sol 画像）、`simple`（预测球路、低点晚接、不跳）、`late`（深位等球下落再挑高）、`deepsmash`（深位等 2.0–2.35 格高再下压）、`mirror`（终版镜像）。
- 统计口径：空挥 = 起拍次数 − 命中次数；下网 = 引擎 `net` 事件中我方为最后触球方；终局体力取最后一分的快照。模拟是确定性的（无随机数参与物理），除随机机器人外每个对局都是单次确定样本。

### 3.4 协议与稳定性

- 真实子进程端到端（`dev/e2e3.js`，stdin/stdout 每行一个观察）：两个座位各 81 个窗口，**0 协议错误、0 技术故障**，单次响应最大 51–62 ms（含进程 IPC）。
- 进程内决策延迟（`dev/latency.js`，162 次调用）：p50 0.0 ms、p95 2.8 ms、p99 4.2 ms、max 8.8 ms，远低于 5 s 硬上限。
- `example.json` 的观察可直接产出合法 10 帧窗口；`phase=point` 输出中立帧、`finished` 输出回位帧；非法 JSON 输入被 `agent.js` 捕获并输出中立窗口，不崩溃。
- 自击检查（`dev/selfhit.js`）：6 局 0 次“发球后同队第一拍触球”、0 次连续同队触球。

### 3.5 被否决的方案（避免下一轮重复踩坑）

1. **深位站位诱导软杀球**：理论上能把对手杀球逼到近网、速度降到 5–6 格/秒，但落点离站位 2.2 格，0.5 秒内够不到；扫描胜率 1–2/10，弃用。
2. **纯 rush 发球防守**：对早高点对手 21/21，但对低点晚接只有 6/21；改为自适应后 20/21。
3. **看到球再起拍**：S ≥ 31 的合法防守为 0，彻底否决。
4. **发球后站定不动**：第 1 轮真实比赛已证明会被 34 格/秒深区杀球打穿。

## 4. 局限与风险

1. **没有真实对手数据**：第 2 轮尚未开赛，sol 在第 2 轮是否仍用“贴网高点接发”只能依据第 1 轮复盘推断。所有对手都是自建机器人，自测胜率不能外推为真实胜率。
2. **自适应依赖对手接发习惯稳定**：高度/时机从“上一次接发”学习。若对手刻意交替高点杀球与低点挑高，我们会在每次切换后的第一分选错（高点→我们 rush、低点→我们 block）；block 对高点仍有约五成保发，rush 对低点则可能直接丢分。第 1 轮数据里 sol 的行为是稳定的，因此本轮按稳定假设设计。
3. **网前截击是高方差打法**：截击成功几乎直接得分，但时机窗口只有 5 帧，且一旦错过，后场是空的。我们用“对手触球帧 − 3 起拍 + 发球过网钳制”把误差容忍压到约 ±1–2 帧；若 sol 的接发时机漂移超过这个范围，rush 会空挥并丢分。
4. **镜像的“发球方通吃”**：当双方发球防守同样强时，先发球的一方可以 11:0 跑完全场。若 sol 的防守与终版相当，系列赛可能变成“谁先发球谁赢”，此时座位/发球顺序的影响会超过策略本身。
5. **模拟的确定性**：物理无随机数，除随机机器人外每个对局只有单次确定样本；对随机对手的 19–21/21 波动只是对手随机性，不是我们的稳健性证据。
6. **参数来自公开引擎副本**：`engine.js` 与公开 `simulation.js` 的物理一致、仅导出行不同；若真实裁判参数与 `catalog.js` 有出入，`core.js` 的击球复算会漂移。第 1 轮回放里的 `rules` 与 `catalog.js` 吻合，本轮按同一套参数设计。
7. **长回合体力**：对 `simple` 的 7–10 次起跳说明多拍回合里仍会用跳；该局终局体力 69.2。若真实对手把回合拖长，240 秒上限与体力分配仍可能成为变量。
8. **规则边界**：网前截击的起拍被钳制在“发球已过网”之后，自测 0 次自击；但这是依赖引擎判定的打法，若裁判对“发球方上网”有额外解释，需要重新评估。
