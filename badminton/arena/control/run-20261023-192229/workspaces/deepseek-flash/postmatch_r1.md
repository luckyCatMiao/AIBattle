## 3. 根因分析

### 3.1 发球局为什么必丢：预判空挥

逐帧把“我方挥拍起始帧”和“实际击球帧”对齐后，得到：

| g1 | 229 | 238 | 221 | 同上 |
| g1 | 329 | 338 | 321 | 同上 |
| g1 | 429 | 438 | 421 | 同上 |
| g1 | 529 | 538 | 521 | 同上 |
| g1 | 629 | 638 | 621 | 同上 |
| g1 | 1106 | 1113 | 1096 | 8:6 领先后送掉 |
| g1 | 1397 | 1403 | 1386 | 9:9 后送掉 |
| g2 | 367 | 373 | 356 | 球在 x=6.41（sol 半场）时起拍 |
| g2 | 467 | 473 | 456 | 同上 |
| g2 | 566 | 573 | 556 | 同上 |
| g2 | 666 | 673 | 656 | 同上 |

| g2 | 1250 | 1263 | 1161（sol 发球） | 唯一一次非发球局空挥，发生在最后一波 8 拍 |

- **g1：8 次发球失分 = 8 次空挥，一一对应，命中率 100%。**
- **g2：7 次发球失分中 6 次先空挥，另 1 次（273 帧）是自己下网。**

空挥的机制：`brain.js` 的 `anticipate()` 在**我方发球时**用“浅层自我”去预测对手回球，然后按预测的触球帧提前起拍。实际 sol 的回球是贴网高点（约离网 0.87 格、y=2.2）的 34 格/秒深区杀球，和浅层自我预测的轨迹不一致；我们按预测冲到网前（g1 到 x≈4.7–5.2，g2 到 x≈8.2–8.8），实际球却从头顶后方飞向深区（g1 落 x=2.87，g2 落 x=10.53）。起拍时球还在我们刚发出的发球轨迹上、尚未被 sol 回击，拍面距离球 1 米以上，必然空挥；空挥后还有 0.4 秒冷却（从起拍到可再挥共 0.85 秒），真正的杀球到达时已经无法再挥。**预判拦网不是得分手段，而是本场最大的送分手段。**

### 3.2 体力账本：不是跑死的，是挥死/跳死的

按回放统计（`catalog.js` 的实际参数：挥拍 −7、起跳 −10、跑动 −9/s、站定 +6/s）：

| 项目 | `r1-g1` | `r1-g2` |
|---|---|---|
| 挥拍次数 / 命中 / 空挥 | 30 / 22 / **8** | 27 / 20 / **7** |
| 起跳次数 | **8** | **7** |
| `|vx| > 3.2` 的跑动帧 | 4（约 1.8 体力） | **0** |
| 站定回体力帧（近似） | 649（约 +195） | 452（约 +136） |
| 挥拍消耗 | 210 | 189 |
| 起跳消耗 | 80 | 70 |
| 终局体力 | **7.7** | **2.1** |
| 对手终局体力 | 89.5 | 85.8 |

- `FREE_SPEED = 3.18` 的省体力设计**是有效的**：两局跑动消耗几乎为 0（g1 仅 4 帧超过 3.2，g2 为 0）。
- 体力崩盘来自挥拍与起跳：g1 的 8 次空挥（−56）+ 8 次起跳（−80）合计 **136 体力**，占全部动作消耗的近一半；g2 为 49 + 70 = **119**。
- 我方每次发球前的体力（g1）：100 → 87.7 → 73.9 → 60.4 → 47.5 → 34.9 → 22.9 → 13.3 → 8.7 → 4.8；g2 开局 100，之后我方 7 次发球前依次为 71.5 → 47.6 → 33.2 → 19.1 → 6.9 → 14.5 → 13.0。**每个得分循环净掉 13–22 点**，而站定只回 6/s，根本补不回来。
- sol 两局 **0 空挥、0 起跳**，但它的接发杀球同样在 y≈2.2 完成；说明地面拍面足以够到 2.2 附近的高点（满体力时上限约 1.911 + 0.38 = 2.29），起跳并非唯一解。每少一次起跳就省 10 体力。

赛前自测里体力能长期保持 60–100，是因为自测机器人不会像 sol 这样每个接发都逼我们起跳+挥拍。**自测的体力结论在真实对手面前不成立。**

### 3.3 四次下网：目标选择依赖对手位置，而模拟里对手是站桩的

| 对局 | 帧 | 位置 | 结果 |
|---|---|---|---|
| g1 | 1205 | x=6.54, y=1.51 | 8:8，直接送掉领先后的关键分 |
| g2 | 104 | x=6.86, y=1.67 | 0:1，开局送分 |
| g2 | 265 | x=6.86, y=1.70 | 1:2，送回发球局 |
| g2 | 765 | x=6.86, y=1.51 | 5:7，被拉开的关键分 |

四次都发生在网高附近（1.51–1.70），是平射球擦网。根因很可能是：`strike()` 的落点选择取决于**对手当时的 x**（近网 1.6 格 vs 后场 1.0 格），而 `simulatePlan()` 里对手被固定为 `NEUTRAL` 站桩；真实对手在移动，目标可能在最后一刻翻转，导致原本“过网”的角度变成下网。模拟里 `chooseShot` 只检查预测轨迹的 `netHit`，没有留安全余量，0.01 的观察量化误差 + 对手位置差就足以翻转。四次下网看似不多，但其中 3 次直接改变了比分走势。

### 3.4 接发杀球是唯一稳定的得分武器

- g1 接发得分 7/10，g2 7/11，合计 **14/21（66.7%）**。
- g1 我们靠接发杀球从 1:1 一路咬到 7:6；g2 从 1:1 到 5:5 的五次追平全部来自接发杀球。
- 我们的接发杀球落点多为近网（g1 落 x≈8.3，g2 落 x≈5.1），速度只有 5–8 格/秒；sol 的接发杀球落深区（g1 落 x=2.87，g2 落 x=10.53），速度 34 格/秒。两种都能得分，但 sol 的深区杀球让我们连反应机会都没有，而我们的近网杀球在 sol 适应后开始被接起。
- 结论：接发抢攻要保留，但需要**体力感知**和**长短结合**，不能每个接发都用“起跳+全力杀”这一种高消耗模式。

### 3.5 杀球数不等于威胁

g1 我们 19 次杀球 > sol 10 次，g2 我们 14 次 > sol 12 次，但两局都输。原因是我们的“杀球”里有大量 5–8 格/秒的近网落点球（事件里 `kind=smash` 但速度很低），真正有威胁的是少数后场 17–18 格/秒的重杀；sol 的杀球里包含多次 34 格/秒的接发深区杀，直接得分。**下一轮评估指标应看“对手需要移动的距离/剩余时间”，而不是杀球计数。**

### 3.6 移动控制器在抖，实际到不了 3.18

回放里追球时的 `vx` 呈明显极限环：0.75 → 1.26 → 2.56 → 1.41 → 2.71 → 1.41 …，平均值约 1.7，而不是设定的 3.18。原因在 `brain.js:35`：

```js
return clamp((desired - me.vx) / (rules.playerAccel * DT), -1, 1);
```

引擎对 `move` 的解释是“目标速度占最大速度的比例”（`engine.js:156`：`vx += clamp(move * maxSpeed - vx, ±accel*DT, accel*DT)`），不是“本帧加速度比例”。当前写法会在接近目标速度时给出很小的 `move`，让引擎把目标速度拉到接近 0，形成“加速—急刹—再加速”的抖动。后果是：同样的 0.5 秒窗口我们少跑 0.5–0.8 格，规划器按同一控制器模拟，也会系统性地“以为能到、实际差一点”，这是空挥和错过网前高点的另一个底层原因。

### 3.7 机制校正：以回放的 `rules` 为准

`RULES.md` 写的是“跑动 −11/s、站定 +7/s、起跳 −8、挥拍 −4”，但回放里的 `rules` 和 `catalog.js` 是 **跑动 −9/s、站定 +6/s、起跳 −10、挥拍 −7**。本复盘全部按后者计算（回放中的体力台阶与 −7/−10 完全吻合）。下一轮优化必须按实际引擎参数，不能按 RULES.md 的文字。

### 4.2 策略上的关键改动（相对“站桩/简单追球”基线）

1. **击球点驱动，而不是按键驱动**：上手出球由击球点高度和离网距离决定（`t*near > 0.55` 才是杀球），规划器围绕“在哪、在多高碰到球”搜索候选帧。
2. **5 帧挥拍窗口 + 起跳组合的前向模拟**：对每个候选触球帧尝试上手/下手、起跳/不起跳、不同起拍帧，用真实 `step()` 验证是否能碰到球，再复算真实出球速度与落点。
3. **接发冲网高点杀球**：发球轨迹固定，接发时提前冲向网前、起跳、在最高点起拍。这是本场唯一稳定得分手段（14 次破发）。
4. **发球后预判拦网**（本场被证明失败）：用浅层自我模拟对手接下来 3 个窗口，预测到杀球就提前起拍拦截。
5. **体力经济**：常规移动目标速度压到 `FREE_SPEED = 3.18`（低于 3.2 的跑动消耗阈值），得分间隙站定回体力。
6. **异常兜底**：决策抛错时输出中立窗口，保证不因格式/异常判技术负。

### 4.3 赛前自测（回顾，不能代表真实对局）

- 对 `noAnt`（无预判的强追球）：11:6 / 11:5；
- 对 `simple`（预测球路+高远球）：11:2 / 11:4；
- 对 `simpleU`（只挑高）、站桩、伪随机：11:0；
- 镜像：14:12（加分）；
- 端到端协议：单窗口最长 49 ms，整局 256–460 ms；窗口格式全部合法。

这些数字的问题在于对手都是我自己写的机器人，**没有一个会像 sol 这样用 34 格/秒的接发深区杀球惩罚我们的发球**，所以赛前“体力能保持 60–100”的结论在真实对局中完全失效。

### 4.4 本场验证到的

- 协议层稳定：0 协议错误、0 技术负，约 4.5 ms/窗口。
- `FREE_SPEED` 省跑动体力有效：两局超过 3.2 的跑动帧只有 4 / 0。
- 接发杀球有效：14 次破发。
- 预判拦网无效且有害：15 次空挥，随后 15 次都丢了分。
- 杀球计数有误导性：19/14 次杀球没有换来胜利，质量比数量重要。

## 5. 下一轮改动计划（按优先级）

### P0：禁止打自己刚打出的球（一行规则，收益最大）

在 `decide()` 的候选搜索前加保护：**`g.shuttle.lastTeam === team` 时不做任何击球规划**（只回位/回体力）。我方发球后 `lastTeam` 就是我们，当前逻辑会把“自己的发球”当成可击球，导致冲到网前空挥；这条保护能消掉本场全部 15 次空挥（g1 8 次、g2 7 次），省 105 体力，并避免空挥冷却挡住真正的防守。它同时也堵住了“发球方自己扣自己发球”的规则漏洞，符合 RULES“接发球方必须先回球”的精神。

### P0：重写发球防守，不再“预测触球点 + 提前起拍”

- **发球冻结期站定回体力**，不要移向 `readyX`；发球出手后再后退。每次发球最多可多回约 4.8 体力（0.8 s × 6/s）。
- **退到 sol 接发杀球的固定落点**：g1 全部落 `x=2.87`，g2 全部落 `x=10.53`，即离网 3.83 格的深区角。发球后我们有约 0.7 s（14 帧）可以退到位，完全来得及。
- **在杀球下降路径上做地面下手挡网**：sol 的杀球从触球到落地只有约 3 帧；站在 `x≈4.7–5.0`（team0）/ `x≈8.4–8.7`（team1），让下手挥拍的第 4–6 帧正好对上球下降到 y≈0.8–1.0 的位置，把球挑回后场。先用回放驱动的“sol 接发机器人”离线验证，再上线。
- 在找到可靠拦截点之前，**宁可不挥**：不挥最多是丢分，空挥还会额外丢 7 体力和 0.85 秒冷却。

### P1：起跳预算与体力感知

- 满体力时地面拍面最高可到约 `1.911 + 0.38 = 2.29` 格；sol 两局 0 起跳就能在 y=2.2 完成杀球。下一轮**先测试不起跳变体**，只有在击球点 >2.29 或“起跳能显著改善落点”时才起跳。
- 在 `evalShot` 里加入动作成本：起跳 −10、挥拍 −7 的体力影子价格；体力 <40 时禁止起跳，体力 <25 时优先挑高/高远球重置回合，而不是每球都抢杀。
- 目标：把每局起跳压到 ≤2 次，发球前体力保持在 50 以上。

### P1：修移动控制器

把 `moveCtrl` 改成引擎语义下的速度伺服：

```js
const maxS = rules.playerSpeed * tired;
const desired = Math.sign(d) * Math.min(maxS, Math.sqrt(2 * 14 * Math.abs(d)), Math.abs(d) * 8);
return clamp(desired / maxS, -1, 1);
```

并加单元测试：从静止出发 8 帧内达到 3.18、稳定保持且不越过 3.2（避免跑动消耗）。这会让我们更早到位、更靠近网完成高点击球，也能减少“模拟能到、实际差一点”的空挥。

### P2：让落点选择对对手移动更鲁棒，减少下网

- `simulatePlan()` 里不要再用站桩对手；用对手当前 `vx` 推算触球帧的位置，至少评估“对手前压/后退”两种情形。
- `chooseShot` 增加安全余量：过网高度至少留 0.25 格（而不是 1.65 格擦线），落点离端线至少 0.3 格；边界方案直接淘汰。
- 目标：把下网从每局 1–3 次压到 ≤1 次。

### P2：保留并优化已有优势

- 接发杀球继续用，但加入体力阈值和长短结合：体力高时打深区（1.0/12.4），体力低时打近网（5.1/8.3），避免被 sol 适应。
- 保留 `FREE_SPEED` 的跑动经济、point 阶段站定回体力、协议异常兜底。
- 用回放做回归：把本场两局作为固定输入，检查“发球局是否还出现空挥”“5:5 时体力是否 >40”“下网是否 ≤1”。

## 6. 局限与数据说明

1. 只有 2 局、1 个对手、固定种子（7011/7012），不能据此推断模型综合能力；本复盘只针对 sol 这 2 局的打法。
2. 回放顶层 `events` 不包含 `hit` 事件，击球/杀球/空挥由 `batsmen[].hits/smashes` 计数和 `swing` 状态逐帧重建；触球点、落点、回合长度取自 `point`/`hit` 事件和终局快照。个别帧的因果判断（例如“空挥是为了拦哪一拍”）是根据位置和时序推断的，不是 agent 内部日志——比赛时 `BADMINTON_DEBUG` 未开启，引擎日志为 0 字节。
3. “空挥”定义为“swing 从 0 变正后 8 帧内 `hits` 计数没有增加”；由于击球窗口是第 2–6 帧，这个定义是保守的，不会把正常击球误判为空挥。
4. 体力账本是按回放状态粗算的：站定回体力只在 `|vx|<0.8 且 onGround` 时发生，且受 100 上限影响，所以各项加减与终局值会有几点的误差，但趋势和量级是确定的。
5. `duration` 0.67/0.59 是战报里的整局决策耗时（按窗口数折算约 4.5 ms/窗口），不是比赛时长；比赛时长由帧数折算（g1 74.45 s，g2 63.15 s）。
6. 赛前自测的对手都是我自己的机器人，分布与 sol 差异很大；本场最重要的教训就是**自测通过不等于真实对局可行**，下一轮必须用回放驱动的对手做对抗测试。
