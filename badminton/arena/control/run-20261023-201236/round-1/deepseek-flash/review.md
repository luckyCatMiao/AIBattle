## 2. 机制理解（以引擎源码为准）

物理参数与 `catalog.js`/`GAME.md` 一致；`RULES.md` 里少数体力数字（跑动 −11、站定 +7、
挥拍 −4、起跳 −8）与引擎实际（−9 / +6 / −7 / −10）不同，**一律按引擎源码计算**。

推导出来、对策略影响最大的几条：

1. **发球是固定的**：0.8 秒冻结后，球从 `server.x ± 0.45, y=1.35` 以 0.72 弧度飞向
   `netX ± 3.2`（落点约 9.87 / 3.53）。冻结期间双方都能移动，接发方可以提前到位。
2. **接发几乎必能强攻**：发球最高点约 2.48，过网后下降到 y≈2.2 时仍在网前 0.8 格内。
   上手击球判定半径 0.38，站地面最高可碰 y≈2.29，因此**不起跳**就能在 (7.5, 2.23)
   或镜像位置完成上手击球。
3. **上手出球由击球点决定**：`t=(sy-1.8)/0.55`、`near=1-(distNet-3.2)/2.5`，
   `t*near>0.55` 才是杀球；否则若 `t>0.5` 且对手离网>3、自己离网>2.6 是吊球；
   其余是高远球。下手固定是挑高球。
4. **杀球落点由“对手当时的 x”决定**：目标取离对手更远的那个角——近网角（离网 1.6）
   或深角（离底线 1.0）。对手 x 小于 3.05（镜像 10.35）时打近网，否则打深角。
   深角在 `solveSpeed` 里常常饱和到上限 34 格/秒，落点约 2.87、飞行仅约 0.16 秒——**基本无法防守**。
5. 因此**防守方的站位直接决定来球**：
   - 站 2.95（下称 `tie`）→ 逼对手打慢速近网杀球（约 6 格/秒，落 4.7~5.1，飞行约 0.5 秒）；
   - 站 4.0（下称 `mid`）→ 逼对手打 34 格/秒深角，但可以在 x≈4.5 用上手/下手拦；
   - 站 6.35（贴网 `camp`）→ 同样逼深角，但会被对手一记高远球打到身后。
6. **发球方天然吃亏**：自测里接发方破发率约 90%，一局几乎由“谁多保发”决定。
   镜像自测的稳定状态是“每分都破发”，比分一路 15:14/11:9 这种一分差。

## 3. 实际采用的策略

### 3.1 接发（进攻）
- 用发球冻结期的 `serveLeft` 精确复原发球出手帧与整条弹道（`predict_serve`）。
- 枚举“第 t 帧、挥拍进度 e、上手/下手”的所有候选触球：由球的子步位置反推需要的我方 x，
  再用引擎的 `update_player` 逐帧模拟自己的移动（含加速、冲刺、体力），**逐帧验证是否真的碰到球**。
- 候选按出球价值打分：杀球基础分最高、触球点越高越靠网越好；对手能轻松回到的球、以及
  过网高度落在对手网前可拦区间的球会被重罚（改打高远/挑球）。
- **自杀球过滤**：引擎的 `chooseShot` 在没有任何角度能过网时会退化成固定角度的
  “假杀球”（例如后场高点打近网角，实测过网高度只有 0.57，直接下网）。规划器在验证命中后，
  会用“实际持拍 `move` 造成的目标前移”重新解算真实出球弹道，落点在自己半场/出界的一律
  重罚（-400）并跳过。加入这条后，镜像自对弈 20 分**全部落在对方半场，0 次自杀失分**。
- 默认**不蓄力**（蓄力让出球变远，容易出界），默认**不起跳**（地面拍面已够到发球高点）。

### 3.2 防守（我方发球 / 我刚击球后）
- 把我方站位设在 `mid`（4.0 / 9.4）。
- 把对手建模成“和自己一样的规划器”：用同一套候选搜索预测他会在哪一帧、哪个点击球，
  再用引擎 `strike()` 的出球规则算出他会打到哪里（**含 `move` 带来的目标前移 0.6 格**，
  按 forward=0 / 估计值 / 1 三档做多假设）。
- 对每条假设弹道分别验证拦截方案，选“覆盖假设最多”的那一个；都覆盖不了时退化为
  追预测落点。
- **对手学习**：从观察的 `events` 里记录对手每次接发的触球点 (x, y) 和相对我方发球出手的
  帧偏移；连续两次触球点相差 <0.35、偏移相差 ≤3 帧时，下一次发球直接用这个实测触球点
  建弹道，而不是用镜像预测。对手若打法固定，2 次发球后拦网就按他的真实节奏来。

### 3.3 回合
- 同样的“候选 + 逐帧验证 + 出球打分”：优先能直接得分的球，其次让对手够不到的落点；
  球会出界时**不碰**（白送的分不要送回去）。
- 体力：默认不冲刺；只有伺服需要的速度超过普通上限时才开 sprint；无谓挥拍会空耗 7 点体力
  并进 0.85 秒冷却，所以每个方案都必须先通过“真的能碰到球”的逐帧验证。

## 5. 局限与风险

1. **没有任何真实对局数据**。上面所有对手都是我自己写的（镜像/脚本），不能代表 sol 或其他参赛者。
   尤其“接发方破发率约 90%”只是自测现象，真实对手的接发质量可能完全不同。
2. **防守依赖击球时刻预测**：拦网窗口只有约 1 帧（34 格/秒的球 0.05 秒走 1.7 格），
   预测差 1~2 帧就会空挥。学习机制只在对手连续两次触球点接近时才生效；对手若混用
   杀球/高远球/不同起拍时机，会退回镜像预测，可靠性下降。
3. **默认不起跳、不蓄力**：这是基于“地面拍面够高 + 蓄力易出界”的判断，但也意味着
   某些很高的球处理不了；若真实对手频繁打出需要起跳的球，会吃亏。
4. **镜像对局高度混沌**：同一套代码改一个小参数，自测比分就会在 11:5 和 6:11 之间跳，
   而且两个完全相同的大脑会收敛到 1/3/7 拍循环的确定性均衡（每分都是接发方拿下）。
   所以我没有按自测比分做细调，只保留机制上更稳的选择（多假设验证、逐帧验证、学习）。
5. **本机没有 `python3`**：这台 Windows 机器只有 `python`（3.14），`where python3` 为空，
   命令行和 `subprocess` 都不会在 cwd 里找 `python3.exe`。提交仍按本轮规定写
   `["python3","agent.py"]`，本地全部用 `python agent.py` 验证；若运行器的 PATH 里没有
   python3，需要组织方环境提供（我无法从工作区影响父进程 PATH）。
6. **工作区里的旧 JS 文件**（`brain.js`/`core.js`/`engine.js` 等）是上一轮留下的，本轮
   Python 版没有复用它们，只是用 `engine.js` 做了物理对拍。

```
           plan_control（带迭代修正）、shot_from_contact、opponent_can_reach

```
