# 独立复盘与连续对战

运行流程：两位 Codex 分别查看自己的源码和相同的公开棋谱，自主选择策略并完成改进、验证；冻结两个版本，各执黑白下一局；把新棋谱交回两边，继续下一轮。默认连续 3 轮，共 6 局。

当前配对为 **GPT-6 Astra 对 GPT-6.1 Sol**。按用户选择，Astra 从零挑战，Sol 沿用已优化三轮的策略。每批次的 `config.json` 记录实际模型、起点及初始源码哈希。上一批 Luna 对 Sol 的结果保存在 `control/run-20261014-182739/`。

网页：<http://127.0.0.1:8787>，点击「跟随直播」。页面顶部显示复盘、提交、对战及完成状态。

## 启动和记录

双击根目录的 `ContinueTraining.bat`：沿用最近一批的两位选手，启动新的 3 轮批次并打开直播；如果上一批仍在运行，只打开直播。这个操作会继续调用两个 Codex 模型。

在游戏根目录运行：

```powershell
python training/control/train.py --cycles 3 --players astra sol
```

必须先启动游戏服务。不要同时运行多个训练控制器。`--cycles` 可设为 1–20；每次启动都是一个新批次，保留当前策略及历史棋谱。

- `astra/`、`luna/`、`sol/`：各自的工作区。`review.md` 是模型自己的复盘；每批只启动所选的两位选手。
- `control/run-时间/`：每轮源码快照、SHA-256 清单、模型日志、棋谱、耗时、结果和隔离测试。
- `status.json`：当前阶段；`active-run.json`：当前批次位置和主进程号。
- 初版策略仍保存在根目录的 `players/` 中。新流程不覆盖它们。

## 隔离与对等条件

本机使用已有的 WSL Ubuntu，安装了 bubblewrap 与 Codex CLI 0.162.1。每位选手在独立的文件系统挂载和进程命名空间运行，实际宿主身份是 Linux nobody。只挂载该选手自己的工作区及只读运行库，未挂载 Windows 盘、对方工作区、旧版对方源码、裁判凭据、控制器、宿主进程目录或 Windows 互操作套接字。双向读取探针在每个批次开始时执行，失败即停止。

准备阶段需要联网调用 Codex 服务，两个独立的 Codex 认证目录位于 WSL `/opt/aibattle-tools/auth/`。比赛程序没有认证文件和网络，其源码挂载为只读，临时文件只能写入独立的 `/tmp`。组织者掌握裁判凭据，负责转发局面和落子，不参与选择落点。

模型可选择 `astra`、`luna`、`sol`，分别对应 `gpt-6-astra`、`gpt-6-luna`、`gpt-6.1-sol`。双方均使用 medium 推理设置、同一准备说明和约 10 分钟的准备上限。程序每步目标预算 5 秒，10 秒为异常运行硬上限。程序错误或超时会暂停整个批次，保留证据；不会静默代下或计为正常棋力胜负。双方也可以选择逐步调用模型推理，若采用不同模式应在分析中单独说明，不能把耗时直接视为对等。

Windows 原生沙箱首次探测因运行库文件占用失败，最终未用于训练；探测所加的拒读 ACL 已撤销。WSL 中 Codex 的 DNS 解析与本机存在差异，`control/network-hosts` 暂存每次启动时重新解析的服务地址用于隔离环境。

## 结果怎么理解

这些是两个具体模型在当前时间和工具预算下独立改进出来的选手。每轮交换黑白可以减少先手偏差，但少量确定性对局、同一条迭代路径和同一对手不足以估计通用模型胜率。应观察失败是否被修复、棋谱是否变化，以及多轮结果，不能只看总比分。
