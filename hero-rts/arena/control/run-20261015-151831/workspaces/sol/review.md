# 第 1 轮策略与自测

## 提交与策略

入口为 `entry.json`，执行 `node agent.js`，首发英雄为合法 ID `druid`（森之先知）。程序持续逐行读取 stdin，每个状态输出一行 JSON；通过 Node.js stdout 写出，不积攒多轮输出。仅使用标准库，不访问网络或对手文件。

开局两名盾卫分别前往北、南外围圣坛，其余主力取得本侧圣坛。占点可持续提供金币、木材和超时积分，因此优先维持地图控制。主力在条件允许时清理附近野怪升级英雄，形成规模后处理远古巨像、内圈圣坛和敌方基地。

经济目标约 18 名农民，随木材储量调整采集分配。扩大人口、建设多个靶场和奥术圣所，主力采用弓手、牧师以及后续招募的霜语先知、烬焰法师、星辉祭司、逐风游侠。中期升级时代，补充迫击炮与军备科技。保留资源和人口检查，英雄阵亡后满足等待时间即考虑复活。

战斗中使用治疗、树灵、范围控制及伤害技能，弓手开疾射、盾卫开盾墙。远程单位在攻击间隔内尝试后撤，躲避敌方范围预警；正常情况下保留攻击前摇和正在进行的施法。所有单位、建筑与资源 ID 从当前状态读取，根据己方大厅位置适应东西换边。

## 实际自测事实

公开历史 `public_results.json` 为 `[]`，没有正式历史对局可复盘。以下均为使用公开 simulation.js 的本地测试，不代表正式比赛结果。

最终版本的结果保存在 `selftest-results.json`：

- `node integration.js 0`：真实启动 entry.json 指定的子进程，经 stdin/stdout 连续交互直到摧毁被动对手大厅。西侧 180.85 游戏秒结束，724 次响应；最多 19 条命令，最大响应约 13.96 毫秒，非法命令 0。
- `node integration.js 1`：东侧 197.25 游戏秒结束，789 次响应；最多 19 条命令，最大响应约 16.50 毫秒，非法命令 0。上述两项均包含进程启动与序列化开销，远低于每次 5 秒限制。
- `node test.js rush 0`：面对自行编写的简易盾卫进攻策略，171.25 游戏秒摧毁敌方大厅；我方非法命令 0。测试对手自身存在队列满、空编队错误，故此项只作基础压力测试。
- `node test.js mirror 0`：另一席运行相同控制程序、首发游侠，195.80 游戏秒结束，我方获胜，双方非法命令 0。
- `node test.js mirror 0 druid`：双方均首发森之先知并运行相同程序，278.40 游戏秒结束，西侧获胜；共 1114 次决策，双方非法命令 0。

测试中发现并修正了新建筑挤住单位、建筑间距影响寻路，以及施工农民阵亡后残留工地阻塞补建的问题。准备阶段早期版本曾在内部对抗中西侧失利；最终版本上述测试已重新执行。未测试真实对手，也没有据此推断真实对手战术。

## 已知弱点

外围占点盾卫单独作战，容易被集中清除。主力采用启发式目标选择，局部阵型、集中治疗、追击与撤退仍较粗糙；大范围技能或飞行部队集中突袭可能造成较大损失。建筑间距和避让降低了堵路风险，但无法保证所有复杂战场下的寻路。科技与兵种组合预设较多，针对性转型有限。自测覆盖完整胜负流程，未证明对未知策略的胜率或 20 分钟超时局表现。
