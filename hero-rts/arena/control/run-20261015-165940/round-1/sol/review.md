# 本轮复盘与提交

提交入口为 `entry.json`，持续运行 `node agent.js`，首发英雄为 `druid`（森之先知）。仅使用 Node.js 标准库；按行读取状态、立即写出一行 JSON，单次最多20条命令。程序无需网络或写入工作目录，单位和出生方向均从状态识别。

## 最新公开比赛复盘

本轮准备时，公开结果全部为 `history-` 记录。最新系列是 `run-20261015-155359` 的 Opus 对 Sol，两场分别于276.70秒、213.40秒由 Sol 摧毁对方大厅获胜，结果记录均无命令错误或技术负。更早的 Luna 系列未混入这两场统计。压缩回放内部都使用 `r1-g1/r1-g2`，本次按文件名和 `source_run` 区分系列。

我重新抽取了最新两份压缩回放的经济、单位和英雄状态，并阅读了 `previous-postmatch.md`。上一版两局均在约25秒建立三个圣坛的收入，但存在实际缺陷：第一局175至185秒弓手从25名减少到12名；180秒附近长期缺金，木材却超过两千。第一局120秒为87金、1438木，18名工人中7名采木。第二局120秒也有968木。两局60秒首发英雄仍是1级。获胜并不能说明这些损失和资源配置合理。

## 实际保留的改进

1. 木工目标随剩余库存连续调整，木材充裕时将更多工人转为采金；修正空闲工人改派时错误增减木工计数的问题。
2. 在已有基础远程兵力后，为前两位追加英雄保留金币，避免每次立即补弓手而一直攒不到招募费用。占稳近点后，更早利用主力与树灵清理附近营地。
3. 将敌方范围预警避让放在普通战斗指令之前，紧急时允许中断攻击前摇；搜索24个出口方向，同时考虑地形、建筑、其他预警和敌军射程，并暂存撤离点。近处直线技能弹道出现时尝试侧移。
4. 合并同目标的攻击、驻守和采集指令，轮转普通部队的指挥顺序，给经济保留指令空间。英雄残血时先考虑自救、护盾和位移。
5. 牧师及祭司按条件驱散控制和负面状态；祭司也会考虑驱散密集召唤物。所有移动坐标夹在合法边界内，修复侦察兵退到地图外的问题。

保留三点开局、弓手与牧师、多英雄以及后续迫击炮体系。没有修改规则、目录、公开回放或对手文件。

## 失败实验与局限

仅调整经济的中间版曾在东侧输给上一版；之后才加入避让、指挥轮转等改动。最终版与另一中间版进行同英雄换边内战是一胜一负，东侧在231.50秒落败。因此最终版并非支配所有已知变体。另试过按在途投射物分摊集火，以及缩窄驱散条件，两者均出现较差的完整对抗结果，未保留。对应原始失败记录纳入汇总，不能将最终选出的六场胜利解读为未知对手胜率。

落单占点兵仍容易遭到集中清除。避让可能损失输出、拉散阵形；被控、地形拥堵或大量重叠预警时不能保证脱离。英雄与科技仍采用启发式预算，长期消耗、资源枯竭及扩张处理有限。尚未验证正式对手本轮改动，也没有完成1200秒超时场景的专项测试；本轮提交后的正式结果尚未知。
