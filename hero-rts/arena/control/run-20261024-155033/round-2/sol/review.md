# 第3轮复盘与提交

提交入口 `entry.json`，执行 `node agent.js`，合法首发英雄为 `druid`（森之先知）。程序只使用 Node.js 标准库，持续逐行读取状态、逐行立即输出 JSON，不访问网络、不写文件。上一轮冻结实现保存在 `agent-round2.js`。

## 最新公开比赛复盘

本轮先读取规则、玩法、目录、公开引擎、状态示例和既有复盘，再分析最新的 `public-r2-g1.json.gz`、`public-r2-g2.json.gz`。只按文件名识别系列，没有把 `history-` 文件或第1轮混入第2轮统计。分析脚本为 `analyze-r3.py`，抽帧与英雄阵亡事件见 `round3-public-analysis.json`。

第2轮双方各胜一场：Sol 东侧341.35秒获胜，西侧684.35秒落败，均以大厅被毁结束；双方两局命令错误均为0，没有技术负。上一轮本地自测全胜未能预测正式西侧败局，不能用自编对手胜率替代真实比赛结果。

失利局的实际问题：

- 90秒我方只有自家圣坛，对方占三座。210秒我方夺回五座、五英雄均存活，随后优势未能稳定转成推进。
- 我方烬焰法师233.8秒、森之先知253.3秒、星辉祭司266.4秒、霜语先知271.5秒、逐风游侠276.3秒先后阵亡。后两位分别在约 `(1058,83)`、`(608,69)`，显示地图边缘仍有撤退问题。
- 指令记录中，我方全局只在246秒复活法师、270秒及486秒复活森之先知。霜语先知、星辉祭司和逐风游侠首次阵亡后没有复活指令；祭坛持续存在。旧代码虽然先尝试复活，钱不够时仍继续补兵，不能保证攒足六级英雄所需390金。
- 自家金矿250秒只剩约33金，280秒已经耗尽。此后大批工人改采外矿，原版没有为这些矿增设交纳建筑。远距离运输会降低收入效率；这不是对败因的唯一归因。
- 300秒我方已升三级，但实际编成没有使用三级兵种；480秒所有英雄都处于阵亡状态，金币仅6。地图收入没有解决英雄补充和兵力交换问题。

获胜局同样有损失：霜语先知223.9秒、祭司256.4秒阵亡。不能因这一局获胜就认为英雄保护已经充分。

## 本轮实际保留的改进

1. **为阵亡英雄攒复活费。** 对未排队的阵亡英雄保留对应金币，其他建造、训练和研究不能动用这笔钱。复活优先顺序为祭司、霜语先知、法师、森之先知、游侠；实际仍须满足等待时间、人口和祭坛条件。祭坛被毁时允许重建。
2. **补远矿交纳点。** 180秒后检查安全外矿；有至少三名工人采集，或基地近矿即将枯竭时，在外矿附近建伐木场。判断会排除邻近敌军、已有交纳点和无效建造位置。
3. **停止无编成需求的三级时代开支。** 保留二级时代、武器护甲和采集科技，将资金用于当前兵种及英雄恢复。
4. **加入重弩手。** 二级后保留至少八名现有或排队弓手，后续远程补充可转为重弩手，使用430射程的蓄力狙击；牧师数量计算同时考虑两种远程兵。保留五英雄、召唤物驱散和迫击炮体系。
5. **修正迫击炮选目标。** 普攻目标必须满足最小射程；射程内可攻击建筑时优先拆建筑，大厅优先。

原有首发、前期三盾卫分工、英雄招募节奏、预警躲避和普通兵指挥轮转继续使用。没有将组织者提供的数据当作控制器，也没有读取真实对手代码。

## 未保留实验和已知弱点

新径向撤退方案与炮兵近敌后退的组合，在西侧分别473.70秒输给法师变体、465.45秒输给旧策略；未保留。增加牧师并在躲避点驻守的组合，在东侧226.25秒输给旧策略；也未保留。原始失败记录见 `r3-micro-*.json`、`r3-support-*.json`，没有计入最终14场结果。

最终版仍有显著战损：东侧对旧策略阵亡57名弓手、15名重弩、22名牧师，祭司三次阵亡；西侧盾卫压力局损失53名弓手、20名重弩、22名牧师。新复活储备改善补充保障，不能代替保护英雄；边缘撤退及连续范围技能下的阵形仍不理想。储备也可能拖慢补兵、农庄和建造。远矿交纳点是否安全取决于后续敌军移动，未穷尽空军、极早突袭及1200秒积分结算。第3轮真实对手的改动和正式结果均未知。
