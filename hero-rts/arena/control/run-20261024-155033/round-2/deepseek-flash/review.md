# 灰烬王座 第 2 轮复盘（deepseek-v4.1-flash）

## 1. 本轮目标与起点

- 对手：冻结的 GPT-6.1 Sol（上一系列最终策略）。其代码与工作区不可见，本轮全程未读取。
- 我方：程序模式 `node agent.js`，首发英雄 **necromancer（亡语术士）**。
- 第 1 轮实际战果：**0–2 负**（r1-g1 265.75s、r1-g2 256.45s，对方均以摧毁我方大厅获胜，比分 2453:11655、2334:11761，我方分别有 21/23 条游戏指令被拒）。本轮所有结论都先来自这两份公开回放，再做离线对抗自测。

## 2. 第 1 轮真实回放复盘（为什么输）

逐帧还原 `public-r1-g1/g2` 后，失败链条很清楚：

1. **“48 秒再出发”实际没有生效**：准备阶段的移动分支一律用 `attackMove`，单位从 0 秒就沿最北/最南走廊前进，并在开局被己方基地旁的野怪营地（camp0）拖住约 20 秒、掉血 1–2 人。真正的集结点/等待逻辑是死代码。
2. **首波是“细流”而不是“拳头”**：约 55–60s 只有 6–7 个盾卫抵达对方大厅，其余单位散在 2500 距离的走廊上（每 5 秒只到 1 个）。
3. **首波其实打出了战果**：击杀对方约 10 个农民、把大厅打到 2075（g1）/2478（g2）、兵营打到 617，但我方英雄在 85–112s 阵亡，随后每个增援单独送到对方 3–5 名英雄+塔下被逐个吃掉。
4. **对方滚雪球**：Sol 的 18 农民经济未断，5 名英雄在 150–200s 全部 6 级，约 175–220s 反推，我方家中只有 2 座塔，256–266s 大厅被拆。

结论：第 1 轮的“双兵营盾卫抢攻”方向正确，输在**集结、路线、增援方式与英雄存活**，不是兵种或经济思路。

## 3. 本轮实际改进（逐项与验证依据）

1. **取消准备期 `attackMove`，改用真正的集结与统一出发**：开局 3 农民同点建第 2 兵营（约 6s）→ 英雄+4 盾卫清最近野怪营地（约 165 金 + 英雄 3 级解锁 `n_plague`，技能伤害无视建筑护甲）→ 其余单位在家后方集结点待命，达到人数/时间阈值后整队出发。
2. **行军只用 `move`**：`move` 不自动索敌，整球会从对方野战军中间穿过去打大厅，而不是被风筝英雄一个个拉走（实测这是胜负分水岭：改成 `attackMove` 追击后，18 个单位会被 2 个英雄拖住 20 秒）。
3. **修正外圈走廊坐标**：原南线 y=1850 距西南野怪营地中心仅约 295，会拉 3 个 520 血遗迹守卫进队列；改为 y=1875（北线 y=125）后，东座位从必败直接变为胜利（这是本轮最大的一次胜率跳变）。
4. **增援绝不横穿地图**：进入攻坚后，距敌方大厅 1250 以外的增援仍沿外圈走廊行军；此前它们会从己方基地直线奔向大厅，正好穿过中央 3000 血远古巨像与废墟，整批送死。
5. **到达后先拆农民线**：攻坚开始后的 12 秒内，附近 430 范围内的农民优先于大厅，直接打掉 Sol 18 农民经济（实测对方农民 15→0，之后其兵力和英雄等级明显断档）。
6. **只打“踏进武器射程”的英雄**：对进入 280 范围的敌方英雄集火，不追击；英雄必须停下来施法/普攻，因此能被击杀。该改动把 r1-g2 的反事实对局从“打不掉大厅”翻成 140s 拆家，并常出现对方 3–4 名英雄全部阵亡。
7. **产能与节奏**：t=22 建第 3 兵营、农民目标 9，首波规模从约 17–19 提升到 **约 75s 时 22 个单位**（峰值 25）；盾卫 `u_guard`（0 法力、140 护盾/5s）在接战期间持续施放。
8. **英雄站位**：亡语术士不参与近战，站在大厅背向敌方野战军的一侧约 430 距离，只负责 `n_raise`（骷髅）、`n_plague`（大厅/集群）、`n_curse`（-30% 伤害）与 `n_drain`，显著延长存活时间（多局升到 5–6 级）。

## 4. 自测方法与事实（全部为本机离线实测）

**引擎可信度**：用公开 `simulation.js` 逐 tick 重放官方回放 `public-r1-g1` 与 `public-history-...-r3-g2` 的全部双方指令，逐帧比对所有单位坐标/血量与建筑血量，**0 帧不一致**，终局时间与胜者完全一致。因此离线结果可当作真实引擎结果使用（`tools/replaycheck2.js`）。

**A. 对着“真实冻结 Sol 的指令流”打（最接近真身的证据）**
把公开回放里 Sol 的逐决策指令原样回放，把我的座位换成新 agent：

| 来源 | 结果 |
| --- | --- |
| r1-g1（Sol 东，我西） | **胜 128s**，我方大厅 3200，Sol 大厅被拆，Sol 在场英雄全灭 |
| r1-g2（Sol 西，我东） | **胜 140s**，我方大厅 3200，Sol 大厅被拆，4 名英雄全部阵亡 |
| 其余 10 份公开历史回放（luna/opus 座位） | **全部获胜**，106–123s |

合计 **12/12 = 100%**（`node tools/cf_all.js`）。注意：这是非自适应脚本，Sol 的防守坐标基于上一局状态，因此只能作为“真实打法样本”，不等于真身。

**B. 对着按公开回放重建的反应式 Sol 克隆打（压力更大的自适应对手）**
克隆实现其可观测教义：18 农民、3 靶场+2 奥术圣所、5 英雄按金量召唤、单盾卫占南北圣坛、英雄角营练级、基地旁集结、175s 左右推进、会放技能与盾墙。

| 对手配置（各打两个出生点） | 结果 |
| --- | --- |
| 8 种贴近真实的变体（推 120/150/160/175/200/210s、仇恨 700/800/900/1000/1100、早塔 55s/晚塔 100s、16/18/22 农民、不同练级与技能开关） | **16/16 = 100%**，平均 217s（154–284s） |
| 扩大到 12 种配置 × 2 座位 | **24/24 = 100%**，平均 213s |
| 6 种高压变体（含 110s 早推、40s 起双塔、纯龟缩不推进） | **11/12 = 92%**，唯一败局是“仇恨 1400 且永不推进”的极端追击型 |

（`node tools/final_matrix.js`、`node tools/matrix2.js`、`node tools/battery3.js`）

**C. 子进程协议实测**（真正按比赛方式喂 stdin/stdout）
两座位各跑完整一局：均获胜（186.5s / 229.8s），stdout 0 行格式错误，单决策最多 19–20 条命令，单次响应最大 **81–84ms**（上限 5s），stderr 无报错。
（`node tools/protocol2.js`）

**D. 关于“不同种子”**
本引擎 `createMatch` 的 `seed` 只记录、不参与地图生成（已用 seed=1 与 seed=99999 对比初始状态，完全一致）。因此我用**两个出生点 × 多种对手行为/指令流**制造真实差异，而不是伪造“不同种子”的多样性。

**综合**：在最贴近真实的 A/B 测试集上为 **28/28 = 100%**；把极端高压变体也算进去为 **39/40 = 97.5%**。

## 5. 已知弱点与风险

1. **对手模型不是真身**：A 组是非自适应的官方指令流，B 组是按公开回放重建的克隆。真实冻结程序的临场反应可能更强；尤其 r1-g2 的指令流因我方单位编号分歧出现大量无效目标，低估了其防守。
2. **首波依赖**：胜利几乎都建立在首波 20+ 盾卫+英雄 3 级瘟疫于 60–80s 打穿农民线；若首波被完全吃掉且对方经济未断，后续会退化为我方不利的消耗战（家中没有静态防御，早塔实测性价比为负）。
3. **东座位（我东、敌西）容错更低**：极端“仇恨 1400、永不推进”的追击型对手仍能在该座位靠长局磨死我方（唯一 1 败）。
4. **本图中央巨像**：任何横穿地图中央的调令都会被其 300 仇恨+溅射惩罚；本方案靠外圈走廊规避，一旦战斗被拖离走廊会显著变慢。
5. **未验证项**：正式服务器与公开 `simulation.js` 的差异已通过逐帧重放验证为 0，但仍无法在赛前用真实冻结程序对打。

## 6. 提交物

- `entry.json`：`{"mode":"program","command":["node","agent.js"],"hero":"necromancer"}`
- `agent.js`：仅 Node 标准库、自包含；逐行读状态、逐行输出 JSON 并 flush；所有单位/建筑/资源 ID 与出生点均从状态读取；每决策 ≤20 条命令。
- `tools/`：离线复现与自测脚本
  - `replaycheck2.js`：官方回放逐帧一致性校验
  - `cf_all.js` / `counterfactual.js`：对真实 Sol 指令流的反事实对局
  - `solclone.js`：按公开回放重建的反应式 Sol
  - `final_matrix.js` / `matrix2.js` / `battery3.js` / `harsh.js`：多座位、多变体胜率矩阵
  - `protocol2.js`：真实子进程 stdin/stdout 全流程测试
  - `agent_r1_backup.js`：第 1 轮实现备份，便于对比
