# 灰烬王座 第 1 轮复盘（deepseek-v4.1-flash）

## 1. 本轮目标与起点

- 对手：冻结的 GPT-6.1 Sol（上一系列最后一轮策略；其代码与工作区不可见，全程未读取）。
- 我方：从零准备，程序模式（`node agent.js`），首发英雄 **necromancer（亡语术士）**。
- 本轮尚未进行正式对局；以下全部为准备期离线自测，不冒充正式战果。

## 2. 从公开回放中读到的对手行为

公开历史（`public-history-*`）内含逐决策双方指令与逐帧状态，可据此还原 Sol 的冻结打法：

- 开局立刻在祭坛排队 **frost**，随后约 46s / 71s / 89s 依次排队 pyromancer / oracle / ranger；
- 首发英雄 druid 带 2 名盾卫先打东北野怪营地，约 27s 转东南营地；另派 2 名盾卫分赴南北圣坛长期驻守；
- 经济：农民持续补到 18，先伐木场、靶场（约 22s）、奥术圣所（约 30s），随后多靶场 + 农庄；
- 约 150s 后补铁匠铺/守望塔并升城堡时代，主力弓手 + 牧师 + 多英雄抱团，约 150s 起推进，后期转迫击炮/重弩。
- 关键窗口：**约 40–100s 其基地只有城镇大厅、农民和少量英雄，主力英雄在野外营地/圣坛**。城镇大厅 3200 血、armor=fortified：普通近战对建筑只有 0.55 倍伤害，但**技能伤害不吃护甲减免**，因此召唤物和 AoE 技能拆家效率很高。

## 3. 我方策略（程序，非直接模型调用）

核心：**双兵营盾卫全押，绕远北/远南走廊直扑其基地**，在 Sol 弓手群成型前结束比赛。

1. 开局 3 名农民同时施工第二兵营（引擎允许多农民同点建造、进度叠加），约 6s 完成；
2. 双兵营持续出盾卫，农民补到约 7 名后停止（金币全部转化为兵力）；
3. 约 48s（约 14–17 名盾卫 + 英雄）沿“远离地图中心走廊”进军：西家走 y≈150，东家按 180° 旋转走 y≈1850，避开中央 3000 血远古巨像的仇恨圈与四座野怪营地；
4. 行军使用 **move** 而非 attackMove：`move` 不会自动索敌，部队不会被中立野怪/巨像拖住（这是实测中最大的翻车点）；
5. 抵达后**集火城镇大厅**：约 16–22 名盾卫 + 亡语术士的骷髅（每次 4 只）与凋零疫地，约 50–60s 拆掉大厅；只在敌人贴身（<270）时清掉最近的牧师/弓手，绝不追击风筝英雄；
6. 新生产单位按各自路点进度分段跟进，不会横穿中央送死；大厅血量 <1000 后全体只打大厅。

亡语术士的作用：`n_raise` 每 24s 召唤 4 只骷髅（合计 64 点/秒的额外输出与肉盾），`n_drain` 造成伤害并自愈，3 级后的 `n_plague` 对建筑与集群每秒 55 点（技能伤害无视护甲）。

## 4. 实际改进（按自测发现的问题）

1. **命令优先级**：最初每个空闲农民一条 gather 指令会占满每 0.25s 的 20 条上限，导致部队移动指令被截断；改为移动→生产→建造→技能→补采集。
2. **召唤物阻塞**：骷髅/树灵的 `attack` 状态曾让“有人正在攻击就不重新下令”的判断永久为真，全军停摆；改为只用非召唤单位判断。
3. **地图对称性**：双人地图是绕 (1600,1000) 的 **180° 旋转对称**，不是左右镜像；最初只镜像 x，导致东家路线/建造点偏移、两座位表现差异很大；改为统一旋转坐标后两座位首次命中时间只差约 1s。
4. **补兵横穿中央**：进入攻坚后新生产的单位曾直接 `attack` 敌方大厅、横穿地图被巨像打死；改为“前线（<900）集火、后方沿路点行军”。
5. **拆迁速度**：多农民同点施工后兵营/农庄成型更快，首波规模从约 14 提升到约 18–22。
6. **建筑卡死**：引擎无法“续建”被放弃的工地（同点再下 build 会被自身建筑判为阻挡），因此只统计“确有农民在施工”的农庄，避免一个废弃农庄永久锁死人口。
7. **英雄选择**：用同一打法跑完 10 位英雄；guardian 在常规对手下稳定，但在“对手经济大幅富余、5 英雄 + 弓手群”的压力测试中多次失手；necromancer 的骷髅与疫地在压力测试中显著更稳，最终改用 necromancer。

## 5. 自测事实（离线，公开 simulation.js 引擎）

对手为按公开 r3 回放重建的“教义复刻”机器人（相同开局/英雄时序/营地路线/抱团推进），并做多组变体：

| 对手变体（每项 3 个种子 × 2 座位） | 结果 | 平均/最慢 |
| --- | --- | --- |
| sol-r3（frost@0，两营地） | 6/6 | 111s / 112s |
| sol-r3 农民队列更凶 | 6/6 | 110s / 111s |
| sol-r1 风格（frost 较晚） | 6/6 | 115s / 118s |
| sol 龟缩（兵力全程守家） | 6/6 | 114s / 124s |
| sol 80s 提前推进 | 6/6 | 111s / 112s |
| 参数扰动（进攻 48±4s、农民 11/13） | 8/8 | 111–114s |

- **常规自测合计：38/38 = 100%**，全部在两个座位、三个种子下获胜；最早约 110s、最慢 124s 摧毁对方大厅。
- **压力测试**（给对手远超真实曲线的经济：+20 金/6 木每秒；+35 金/12 木每秒；以及预支 2500 金 + 30 金/10 木每秒；含对手全程龟缩）：**6/6 全胜**（最慢 397s 为极端龟缩局）。
- **真实子进程协议测试**：`node agent.js` 作为独立进程，逐行读状态、逐行输出 JSON；两座位均胜（110.8s / 112.1s），单次响应最大 28ms / 79ms（远低于 5s 上限），0 行格式错误，stdout 无调试输出（日志只走 stderr）。
- 每决策最多 16 条指令（≤20）；整局被引擎拒绝的指令仅约 25 条“金币不足/正在施法”（同一决策内资源竞争，无害），无非法单位或越权指令。
- 说明：本引擎 `createMatch` 的 seed 只记录、不参与地图生成，因此“不同种子”实际是同一张图；为避免虚假多样性，我改用不同对手变体、座位与策略参数做重复自测。

## 6. 已知弱点与风险

1. **对手模型是复刻而非真身**：自测对手依据公开回放重建，无法证明与冻结程序逐决策一致；若真实 Sol 的早期防守（拉农民、提前回防、英雄走位）明显更强，第一波可能被拖住。
2. **单波依赖**：胜局多在 110–125s；若首波被完全吃掉且未重创其经济，后续主要是沿路补兵，缺少成规模二波与家中塔防（金币优先给兵，实测 90s 时金币常年 <140，塔造不出来）。
3. **中央巨像**：任何穿越地图中央的路线都会吃 300 仇恨；本方案靠远北/远南走廊规避，一旦被逼离走廊会显著变慢。
4. **未验证项**：真实比赛服务端与公开 simulation.js 若有细微差异（建筑判定/仇恨/路径），结果可能变化；正式对局前无法消除该风险。

## 7. 提交物

- `entry.json`：`{"mode":"program","command":["node","agent.js"],"hero":"necromancer"}`
- `agent.js`：自包含（仅 Node 标准库），从 stdin 逐行读取状态，输出一行 JSON 并 flush；所有单位/建筑 ID 均从当前状态读取，不硬编码座位或出生点。
- `tools/`：离线复刻与自测脚本（sim.js、solbot.js、tourney.js、stress.js、protocol-test.js、final-validate.js），可复现上表结果。
