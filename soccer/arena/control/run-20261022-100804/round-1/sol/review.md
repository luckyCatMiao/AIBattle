# 第 1 轮提交说明与准备期自测

## 状态

已生成 `entry.json`，入口为 `python3 agent.py`。Python 入口使用 `exec` 启动同目录的 `agent.js`，由 Node.js 持续读取 stdin 的 JSON 行，逐行输出并立即写出结果。运行时不写文件、不访问网络。仅使用本方文件以及公开的 `simulation.js`、`catalog.js`，未修改受保护资料。

**本文是准备期离线测试记录，不是正式比赛复盘。当前没有正式对局结果。** `public_results.json` 为空，不能据此推断对方打法。

## 实际策略

- 将任意座位镜像成向右进攻，人数完全服从当前 `teamSize`，每次输出 20 帧、每帧恰好该人数的合法输入。
- 从观察重建公开模拟状态，对未来 20 帧逐帧计算己方动作，并用同一策略预测对方动作，通过公开物理推进。这样能在一个窗口内安排拿球、转向、踢球和回撤；不假设能收到窗口内的新观察。
- 空闲球预测包含摩擦和边墙反弹，按移动距离与到达时间选择接球点。主要追球队员外，其余队员保持接应、压迫与后方保护位置。
- 多人局让 index 0 优先守门，根据来球轨迹预测拦截纵坐标；本方禁区内近距离来球可上前收球，控球后优先向前解围。单人局不把唯一球员永久留在门前。
- 控球时枚举精确角度，目标覆盖球门内部 y=10.65..15.35。估计球沿途的摩擦、到达时间、敌方可达距离以及近处队友阻挡，选择较安全的射门。
- 没有合适射门时向禁区外推进，必要时走侧翼；受压时评估向前传球或踢向空当。带球朝向尽量背离最近对手，降低球暴露给抢断的风险。
- 禁区避让留出额外安全余量，减少球员分离碰撞把本方推进禁区的风险。实际限制比规则更保守，禁区正面在 x=33 附近停止，侧面也留出约 1 格余量。

## 已实际执行的测试

### 1. 对抗基线：24 场

运行 `node test.js --full`，结果见 `test_results.jsonl`。

- 覆盖 1–6 人，每个人数交换座位。
- 两种自行编写的基线：多人追球压迫，以及守门员配合瞄准远角的进攻。
- 双方均每秒提交一次 20 帧输入；基线也从自己的预测状态生成窗口，没有读取实际未来动作。
- **最终版本：20 胜、4 平、0 负，本方累计 0 次犯规。**
- 每次策略响应最大记录约 **6 毫秒**，远低于 5 秒硬上限。
- 这些基线较简单，24 场也不是独立随机抽样，不能视为正式胜率估计。

早期较窄安全余量版本虽取得 24 胜，但追球压迫测试共出现 4 次本方犯规。最终增加余量后重新跑完整测试，犯规降为零，代价是出现更多平局；提交的是后者。

### 2. 强化反应压力：12 场

运行 `node stress.js`，结果见 `stress_results.jsonl`。

- 同样覆盖 1–6 人、交换座位。
- 本方仍一次性提交 1 秒窗口；对手使用本方策略但**每个物理帧都能根据真实状态重新决策**。这是故意给予对手额外反馈优势的压力测试，不是公平比赛配置。
- **最终版本：1 胜、9 平、2 负，本方累计 0 次犯规。**
- 负场为 1 人左座位 3:4，以及 6 人右座位 0:1（比分在原日志中按场上左右顺序记录）。
- 这说明窗口内对手动作预测错误仍有实际影响，尤其单人争抢与密集防守。

### 3. 状态与协议检查

- 额外 120 个确定性伪随机合法站位/球速/持球状态，覆盖所有人数与双方座位，全部通过公开 `submitWindow` 格式校验，最大响应约 **2.15 毫秒**。

- 测试实际执行了完整上下半场与部分金球阶段，不仅是静态输出检查。

## 已知局限

1. 对方窗口动作不可见，当前只使用同策略自对弈预测，没有建立多种对手模型或在线动作辨识。
2. 射门安全评估是启发式可达距离估计，不是穷举对手所有拦截动作；传球落点与反弹轨迹也存在近似。
3. 观察不公开部分内部锁定状态，重建时抢断锁和犯规锁只能近似；冻结期由公开字段恢复。
4. 多人局缺少复杂交叉跑位与主动换位，密集防守时容易僵持；保守禁区余量也减少了侧翼进攻空间。
5. 单人局没有独立守门员，需要在前压与保门间取舍，强化压力测试已有失利，不能声称稳胜。
6. 没有根据领先比分专门拖延或落后时增加风险；随机场景测试主要验证协议与计算时间，不等于覆盖所有战术边界。
