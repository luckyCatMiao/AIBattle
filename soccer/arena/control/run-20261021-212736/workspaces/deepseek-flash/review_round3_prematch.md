## 1. 本轮实际采用的控制策略

### 1.1 总体结构

程序每行读一个观察，输出 20 帧 × `teamSize` 的输入，逐行 flush。沿用前几轮验证过的结构：

- **20 帧前向模型**：每个窗口用观察里的位置/朝向/冷却，加上从 `catalog.js` 抄入的物理常量（移动 3.15 格/秒、球速 14、摩擦 0.97、墙反弹 0.72、控球半径 0.82、抢断余量 0.12、盘带距离 0.62、踢球冷却 7 帧、控球锁 6 帧、抢断锁 4 帧），在内部推演本窗口；在推演的每一帧上运行同一套策略，最后组装 20 帧输入。
- **观测驱动 + 兜底**：冻结帧先输出中立输入；解析/决策异常时 `main` 捕获异常并输出 20 帧中立输入，优先避免技术负。`dir` 只用九个合法方向，`aim` 用 `null` 或 0–359 的浮点角度，`kick` 为布尔。
- **跨窗口记忆**：记录上一窗口位置用于估计对手速度；门将做粘性选择（优先沿用上一窗口的门将）；检测新对局（`frame==0` 或帧号回退）时清空记忆。

### 1.2 关键行为

- **门将**（`n≥2`）：粘性指定，站在“球—自家球门中心”连线上，按 `back = clamp(0.68·D, 1.35, cap)` 出击；球距本方球门中心小于 3.4 格时直接扑球；自由球高速朝本方球门飞来时按预测轨迹找可到达的拦截点。
- **追球者**：每个窗口选离（预测）球最近的本方非门将单位；n=2 时目标取球靠自家球门一侧 0.40 格（抢断只需比持球者近 0.12 格）；n≥3 时站在持球者朝自家球门方向 0.92 格的位置，球暴露在球门一侧时直接扑球。
- **护球推进**：控球者每帧从 360 个角度里选一个，使球（持球者前方 0.62 格）到所有对手的最小距离最大，并把窗口开始时的对手位置也当作虚拟障碍；推进方向在八方向里选“朝对方球门 + 不撞人”的分最高者。
- **射门**：只在距离 <3.6 格，或距离 <7 格且线路余量 >2.2 时起脚，目标取对方球门线上的 5 个点；持球者已进入球门高度且贴近对方门线时直接朝门线起脚（利用“进球判定先于控球判定”）。
- **贴墙压制（stall）**：我方领先 ≥1 球且 `timeLeft ≤ 60` 秒、我方控球时，持球者移动到最近的墙点并朝墙站立，其余队友退到持球者后方；利用贴墙时球会贴到持球者中心、抢断条件 `d+0.12 < 持球者到球距离` 无法满足的引擎语义耗尽时间。
- **安全后卫**：若门将自己带球，指定一名非持球队员回撤守门，避免空门。

### 1.3 本轮相对第 2 轮赛后版本（`b4b5ccae`）的两处改动

改动只涉及防守站位参数，没有改射门、护球、压制等其它逻辑。

#### 改动 A：门将出击上限按人数分档（`agent.py:684`）

```python
# 旧（b4b5cc）
cap = 14.0 if n == 1 else (11.0 if n == 2 else (12.0 if n == 3 else 14.0))
# 新（本轮提交）
cap = 6.0 if n in (2, 3, 5) else 14.0
```

理由来自对局追踪（`tools/trace_match.js`，逐窗口记录）：

- 在本方只有 2–3 人时，旧的上限（11/12）会把唯一的门将顶到离球门 11–12 格的位置。追踪中 n=2 的一局，球在 (37.21, 12.76) 时门将站在 (31.96, 11.93)（离球门 11.04 格），对手带球推进到 5–6 格内起脚，门将回追不及。
- 统计多局失球事件，失球前的对手起脚点集中在**距球门 2.5–6.5 格**（例如 v0 的 n=3 一局：x=36.65 / 38.15 / 33.63，角度 0.09–0.32 rad；exp2 的 n=2 一局：距门 2.47–3.30 格）。少人时门将不该长期站在 11–12 格外。
- n=4/6 保持 14 是因为自测中改小反而变差（见 2.6 的门将上限扫描）；n=1 的单人局保留 14（把上限改小、门将站得更深反而更差）。
- n=5 的旧上限是 14，收紧到 6 的依据同样是逐窗口追踪与大池数据（600 局池 n=5 从 75-1-24 变为 82-1-17，见 2.3）。

#### 改动 B：n≥4 双门角封堵的分人数参数（`agent.py:629`）

旧版对所有 n≥4 统一用 `Dgoal<12、frac=0.50、settle×0.12`。本轮按人数分开：

| n | 触发距离 `Dgoal` | 封角点插值 `frac` | 纵向分散系数 |
|---|---:|---:|---:|
| 4 | < 14 | 0.50 | 0.12 |
| 5 | < 12 | 0.42 | 0.12 |
| 6 | < 12 | 0.50 | 0.00 |

- n=4 把触发距离放宽到 14：4 人局有 3 名非门将，提前封角在自测中稳定更好（600 局池 n=4 从 74-0-26 变为 82-0-18）。
- n=5 把封角点拉近球（0.42），减少“球在 12 格外时后卫过早退到门前”的空档（n=5 从 75-1-24 变为 82-1-17）。
- n=6 取消纵向分散：6 人局非门将足够多，按 `index` 奇偶已经能覆盖两个门角，额外的 ±分散会把封角点推离射门线（n=6 从 64-0-36 变为 85-0-15，失球 125→59）。

## 4. 局限与风险

1. **没有第 3 轮官方数据。** 本文写于开赛前，没有任何本轮比分、进球时间线或回放；赛后应另写 `postmatch.md`，不能用本文的本地数字替代。
2. **本地对手同源。** 50 个对手都是本工作区自己写的脚本，其中大量是同一份早期代码的后代，行为高度相似；虽然做了分组消融，仍不能覆盖官方对手可能采用的护球、传球、长传、全场紧逼或完全不同的射门选择。第 2 轮的官方对手是另一个模型，本地池不能替代它。
3. **确定性放大参数敏感度。** 固定人数时引擎无随机数，同一参数在不同对手上会因整场脚本翻转而出现大幅波动（2.6 的 n=1 细扫就是例子）。本文的结论是“在多个独立对手池上方向一致”，不是“参数最优”；对未知对手的真实期望仍有很大不确定性。
4. **改动 B 的参数是本地拟合。** n=4/5/6 的触发距离、封角插值和分散系数是在自测池上选出来的；虽然三组独立池排序一致，但绝对数值不应外推到官方对手。
5. **静态物理常量。** 程序把 `catalog.js` 的常量写死在代码里，没有从 `obs.rules` 动态读取；如果官方引擎参数与公开规则不同，20 帧前向模型会漂移。
6. **贴墙压制的引擎依赖。** stall 依赖“贴墙时球会到持球者中心、抢断要求 `d+0.12 < 持球者到球距离`”的本地语义。若官方引擎改动该细节，压制可能失效；规则没有说明是否按净胜球排序，领先 1 球后从第 60 秒开始放弃进攻也可能牺牲净胜球。
7. **n=1 与 n=3 仍是相对弱项。** 50 池上 n=1 为 64-0-36、n=3 为 72-1-27，明显低于 n=2 的 98-0-2 和 n=4 的 82-0-18。本轮没有找到能稳健提升这两个人数且不依赖过拟合的方案。
8. **金球与冻结的覆盖有限。** 冻结帧、开球、门线判定都有代码路径，600 局中只有 2 局进入金球（都以平局结束），样本很少。
9. **座位差异。** 前几轮 120 局电池中 b 座略弱于 a 座；本轮改动按人数而非座位，未专门处理座位差异。
10. **未读取对方代码。** 所有对手分析只来自本工作区的自写脚本和旧公开战报，没有读取对方代码、私有回放或网络数据。
