## 1. 进球与射门数据（公开战报口径）

### 1.1 为什么没有“射门数”

第 3 轮公开战报只提供 `scores`、`stats.kicks`、`stats.possession`，没有 `shots / shotsOnTarget / xG`，也没有事件回放。因此：

- **可以核对**：进球数、踢球次数、控球帧、控球秒数。

## 2. 逐场复盘

### 2.1 `r3-g1`：2:5 负，n=6，a 座

**战报事实**

- 对局 ID `r3-g1`，`teamSize=6`，座位 `deepseek-flash / sol`，我们是队 0（a 座）。
- 2401 帧 / 120.05 秒 / 120 个窗口，常规时间结束，比分 **2:5**。
- 我们：2 球、4 次踢球、704 控球帧（35.20 s）。
- sol：5 球、15 次踢球、528 控球帧（26.40 s）。
- 双方 `errors=0`，`technicalFailure=null`。

**由聚合数据可做的推断**

- 我们占双方控球帧的 57.14%，但全场只有 **4 次踢球**；sol 有 **15 次踢球**，约为我们的 3.75 倍。对手的起脚/触球频率明显更高。
- sol 用 26.40 秒控球打进 5 球，约 **每 5.28 秒控球进 1 球**；我们用 35.20 秒控球打进 2 球，约每 17.60 秒进 1 球。按“每秒控球进球数”，对手约为我们的 **3.33 倍**。
- 这不是“对手控球更多”：我们控球帧反而更多。问题集中在**攻转守/短暂控球后的防守效率**，以及**我们自己的出手量过低**。
- 第 3 轮提交版本在 n=6 时使用门将出击上限 14 格、n≥4 双门角封堵（`Dgoal<12`、`frac=0.50`、纵向分散 0）。对手 15 次踢球的画像，与“门将站得较远、被中远距离起脚或转换进攻打穿”的假设一致；但没有回放，不能确认每个失球的具体位置和方式。

**不能从战报确认的事**

- 5 个失球的具体时间、位置、是远射、反击、开球还是定位球，均无法确认；需要官方回放。
- 我们的 4 次踢球中有几次是射门、几次是解围/传球，无法确认；不能把“4 次踢球”直接称为“4 次射门”。

### 2.2 `r3-g2`：3:2 胜，n=4，b 座

**战报事实**

- 对局 ID `r3-g2`，`teamSize=4`，座位 `sol / deepseek-flash`，我们是队 1（b 座）。
- 2401 帧 / 120.05 秒 / 120 个窗口，常规时间结束，比分 **3:2**（我们胜）。
- sol：2 球、4 次踢球、153 控球帧（7.65 s）。
- 我们：3 球、3 次踢球、1396 控球帧（69.80 s）。
- 双方 `errors=0`，`technicalFailure=null`。

**由聚合数据可做的推断**

- 我们占双方控球帧的 **90.12%**，但全场只有 **3 次踢球**；进攻端是“极低出手量、极高比值”的形态。
- 3 球 / 3 次踢球 = 1.00 只是比值；不能据此说“每次踢球都进球”。对手 2 球 / 4 次踢球 = 0.50 同理。
- 对手只有 7.65 秒控球，却打进 2 球，约 **每 3.83 秒控球进 1 球**；按“每秒控球进球数”，对手约为我们的 **6.08 倍**。即使我们赢了，防守端“对手一拿到球就高效得分”的问题仍然存在。

### 2.3 两场共同点

1. **控球优势没有转化为净胜球**：两场合计 75.51% 的双方控球帧份额，总比分 5:7。第 3 轮延续了第 2 轮的核心矛盾。
2. **我方出手量过低**：两场我们合计 7 次踢球（场均 3.5 次），sol 19 次（场均 9.5 次）。`kicks` 不等于射门，但如此低的起脚量意味着进攻端很难持续制造威胁。
3. **对手短暂控球效率极高**：sol 两场用 34.05 秒控球打进 7 球（约 4.86 秒/球）；我们用 105 秒打进 5 球（约 21 秒/球）。差距约 4.32 倍（按每秒控球进球数）。
4. **n=6 是明确弱项，n=4 相对稳**：n=6 的 `r3-g1` 净负 3 球，且对手起脚量 15 次；n=4 的 `r3-g2` 虽然赢了，但防守效率仍是警告信号。赛后改动因此优先针对 n=6，而不动 n=4。

## 3. 第 3 轮实际控制策略与赛后改动

### 3.1 第 3 轮实际提交版本（`f994ae...`，已参加本轮）

第 3 轮实际参赛的是 `agent.py`，SHA-256 `f994ae75e4aa24e4f16f4881e8c49477a7bec76df14b491834d8785f06dadcc7`，已按原内容备份为 `agents/round3_agent.py`（哈希相同）。策略主体沿用前两轮：

- 每个观察用内部 20 帧前向模型推演，最后输出 20 帧 × `teamSize` 输入；异常时兜底输出中立输入，优先避免技术负。
- 门将粘性选择；n≥2 时指定门将，站在球—自家球门中心连线上，按 `0.68·D` 出击并有上限。
- 追球者/支援/防守按角色分工；控球者用 360° 护球朝向推进；只在近距离或线路足够干净时射门。
- 领先 ≥1 球且 `timeLeft ≤ 60 s` 且我方控球时，启用贴墙压制（stall）。
- 第 3 轮赛前的两处改动（相对第 2 轮赛后版本 `b4b5cc...`）：
  - n=2/3/5 门将出击上限从 11/12/14 收紧到 6；
  - n≥4 双门角封堵按人数分档（n=4 `Dgoal<14, frac=0.50, smul=0.12`；n=5 `Dgoal<12, frac=0.42, smul=0.12`；n=6 `Dgoal<12, frac=0.50, smul=0`）。
- 因此 `r3-g1` 的 n=6 实际使用**门将上限 14 + 双门角封堵**；`r3-g2` 的 n=4 使用**门将上限 14 + 双门角封堵（Dgoal<14）**。

### 3.2 赛后改动：n=6 门将出击上限按对手起脚频率自适应（`1c56...`）

赛后仅改一处，目标是 `r3-g1` 暴露的 n=6 防守问题；**该改动没有参加第 3 轮**。

**代码位置**：`/workspace/agent.py`

- `agent.py:143`：新增模块级 `_N6_CAP = 14.0`。
- `agent.py:356-379`：每个窗口在 `make_policy` 里计算本窗口的 n=6 门将上限。
- `agent.py:696`：`keeper_decide` 在非我方控球时使用 `_N6_CAP`。

核心逻辑：

```python
# n=6：对手起脚频率高时门将收深；低起脚频率时保持 14 格上限。
_N6_CAP = 14.0
if n == 6:
    opp_kicks = float(obs.get('stats', [{}, {}])[1 - myteam].get('kicks', 0))
    elapsed = max(1.0, 120.0 - time_left)
    if opp_kicks / elapsed >= 0.08:
        _N6_CAP = 10.0

# keeper_decide 非我方控球分支：
cap = _N6_CAP if n == 6 else (6.0 if n in (2, 3, 5) else 14.0)
back = clamp(0.68 * D, 1.35, cap)
```

解释：

- **触发量**：对手累计 `kicks ÷ 已进行秒数 ≥ 0.08 次/秒**（约等于 120 秒 9.6 次踢球）。第 3 轮 `r3-g1` 的 sol 是 15 次 / 120 秒 = **0.125 次/秒**，会触发；本地低起脚控球型对手（如 vC2，1–3 次踢球）约 0.008–0.033 次/秒，不会触发。
- **动作**：n=6 且对手起脚频率高时，门将出击上限从 **14 格收紧到 10 格**；低频率时保持 14 格，避免对控球型对手过度退守。
- **作用范围**：只在 `n == 6` 且**非我方控球**时生效。我方控球时门将仍走原来的 `0.25·D`（1.4–4.2 格）分支；n=1–5 完全不变，n=4 完全不变；射门、护球、传球、stall 逻辑均未改动。
- **为什么是 10 而不是 6/8**：n=6 有 5 名非门将，门将不应像 n=5 那样长期压到 6 格；但 14 格在对手高频起脚时又太远。10 格是本地多组对照后的折中，且只在“高起脚对手”上启用。这个数值是启发式的，不是从官方回放拟合出来的（本轮没有回放）。

### 3.3 为什么只改 n=6

- `r3-g1` 是 n=6、净负 3 球、对手 15 次踢球，是最明确的失分样本。
- `r3-g2` 是 n=4 且我们取胜；本地 49 对手池 n=4 为 81-0-17（173:62），没有足够证据支持改动。
- n=2/3/5 的门将上限 6 已在第 3 轮赛前版本中生效；本轮没有新的官方样本去推翻它。
- n=1 和 n=3 仍是本地相对弱项（见第 5 节），但第 3 轮没有这两个人数的官方对局，不能据此调参。

## 5. 局限与风险

1. **没有官方回放，也没有真实射门数据。** 公开战报只有进球、`kicks`、`possession`；本文无法给出射门数、射正数、射门位置或进球时间，也没有逐球归因。
2. **`kicks` 不是射门。** 它包含开球、解围、传球等；本文只用它作为起脚频率/进攻量的代理，不用它计算“射门转化率”。
3. **样本只有 2 局、1 个系列。** 不能据此推断模型或策略的综合能力；n=6 的 2:5 和 n=4 的 3:2 都只是这两场的结果。
4. **本地对手同源。** 49 个对手都是本工作区自写脚本，很多是同一份早期代码的后代；`exp4` 只是“高频起脚”的机制代理，不是 sol。官方对手可能采用完全不同的护球、传球、长传、全场紧逼或射门选择。
5. **确定性放大参数敏感度。** 固定人数下引擎无随机数；门将上限 6/7/8/9/10/12 的非单调结果就是例子。自适应版的 0.08 阈值、10 格上限、n=6 限定都是在本地池上选的，存在过拟合风险。
6. **自适应触发基于 `kicks` 频率，不是射门频率。** 对手可能用大量解围/传球触发“高起脚”判定，也可能用少量高质量射门而不触发；这两种误判都可能让门将站位不理想。
7. **n=1 与 n=3 仍是相对弱项。** 本地池 n=1 为 63-0-35、n=3 为 71-1-26，明显低于 n=2 的 96-0-2 和 n=4 的 81-0-17；本轮没有官方样本支持改这两个人数。
8. **n=6 的失球原因没有被回放证实。** 赛后改动是基于“对手 15 次踢球 + 门将上限 14”的假设；如果官方失球主要来自反击、定位球或门将以外的防守漏洞，收深门将未必能解决。
9. **贴墙压制的引擎依赖没有改变。** stall 仍依赖“贴墙时球贴到持球者中心、抢断条件难以满足”的本地语义；如果官方引擎改动该细节，压制可能失效。
10. **静态物理常量。** 程序仍把 `catalog.js` 的常量写死，没有从 `obs.rules` 动态读取；官方参数若与公开规则不同，20 帧前向模型会漂移。
11. **没有读取对方代码、私有回放或网络数据。** 所有对手分析只来自公开战报的聚合字段和本工作区自写脚本。
