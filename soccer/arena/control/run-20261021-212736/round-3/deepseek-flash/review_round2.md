## 1. 进球与射门数据（公开战报口径）

### 1.1 为什么没有“射门数”

公开战报没有 `shots` 字段，也没有回放事件；`stats.kicks` 是**踢球次数**，不是射门次数。一次 `kick` 可能是开球、解围、传球或射门。下文因此只报告：

- **进球数**（`scores`，可直接核对）；
- **踢球次数**（`stats.kicks`，官方唯一可得的起脚类统计）；
- **进球/踢球比**（作为效率代理，不称为“射门转化率”）；
- **每球所需控球帧/秒**（衡量对手用多短的控球时间完成进球）。

真实射门数、射正数、射门位置和进球时间，需要官方回放的 `kick` / `goal` 事件逐帧统计；本轮没有提供回放，本文不补造。

## 2. 逐场复盘

### 2.1 `r2-g1`：3:2 胜，n=3，a 座

**战报事实**

- 对局 ID `r2-g1`，`teamSize=3`，座位 `deepseek-flash / sol`，我们是队 0（a 座）。
- 2401 帧 / 120.05 秒 / 120 个窗口，常规时间结束，比分 3:2。
- 我们 3 次踢球、1508 控球帧；sol 3 次踢球、116 控球帧。
- 双方 `errors=0`，无技术故障。

**由聚合数据可做的推断**

- 我们占双方控球帧的 92.9%，sol 只有 5.8 秒控球，却打进 2 球；按“每秒控球进球数”算，sol 约为我们的 **8.7 倍**（0.345 vs 0.040）。这与“两次得分都来自非常短暂的控球/转换”一致，但战报不能证明每个球都发生在有主控球期间。
- 我们 3 球 / 3 次踢球，说明进攻端延续了“少起脚、只在近距离或清晰线路起脚”的策略；效率很高，但输出量被压在 3 球。
- 比赛赢了，但**防守效率是警告信号**：对手 3 次踢球就换来 2 球，只要多一次短暂控球，3:2 就可能变成 3:3 或 3:4。

**不能从战报确认的事**

- 两个失球的具体时间、位置、是远射、反击、开球还是定位球，均无法确认；需要回放。不能把“8.7 倍”直接解释成“被远角射门打穿”，它只是提示失球发生在极短控球内。

### 2.2 `r2-g2`：3:4 负，n=5，b 座

**战报事实**

- 对局 ID `r2-g2`，`teamSize=5`，座位 `sol / deepseek-flash`，我们是队 1（b 座）。
- 2401 帧 / 120.05 秒 / 120 个窗口，常规时间结束，比分 3:4。
- 我们 3 次踢球、810 控球帧；sol 12 次踢球、622 控球帧。
- 双方 `errors=0`，无技术故障。

**由聚合数据可做的推断**

- 我们控球帧 56.6% 占优，却输球；sol 的踢球次数是我们的 **4 倍**（12 vs 3），并用 12 次踢球打进 4 球。从踢球次数看，对手更偏向“量多、直接”的进攻，我们更偏向“量少、高效率”；这是从聚合统计得到的画像，不是逐球确认。
- 我们再次 3 球 / 3 次踢球；当对手打进 4 球时，3 球的固定输出不够。由于没有回放，不能确认我们是否在落后时仍保持同样的保守射门阈值，但代码层面射门阈值**不随比分变化**（见 3.2），所以落后时也不会主动提高出手量。
- `n=5` 是赛前自测中最弱的人数之一（120 局电池 15W5L；强对手 5 seed 子集 25W25L）。官方这场正好是 n=5 的 1 球小负，和自测弱点一致；但两场样本不足以证明因果。

**不能从战报确认的事**

- 4 个失球是否来自远角、反击、门将失误或定位球，无法确认。
- 贴墙压制（stall）是否在某个时刻触发、是否影响了比赛走势，无法确认；战报没有事件时间线。

### 2.3 两场共同点

1. **进攻输出稳定但上限低**：两场都是 3 球 / 3 次踢球，进球/踢球 1.00。少起脚、高命中的策略在两种人数下都奏效，但也把单场输出锁在 3 球左右。
2. **控球优势没有转化为净胜球**：合计 75.9% 的双方控球帧份额，总比分 6:6；对手每秒控球的进球率是我们的 3.14 倍。
3. **两场恰好落在自测的两个弱点人数**：n=3 是 3:2 小胜，n=5 是 3:4 小负；两场分差都只有 1 球。
4. **问题主要在防守转换，而不是控球**：g1 只让对手控球 5.8 秒却丢 2 球；g2 让对手 12 次踢球、丢 4 球。要提高胜率，优先降低“对手短暂控球就得分”的效率，而不是继续堆控球。

## 3. 第 2 轮实际采用的控制策略

按赛前记录，第 2 轮提交的是 `agent.py`（SHA-256 `c7c01775bada0831ac305e268b7953b5bd0f442e15d81d09357e4b083f94e14b`），该版本已按原内容备份为 `agents/round2_agent.py`（哈希相同）。策略主体如下。

### 3.1 总体结构

- 每个观察到来时，用内部 20 帧前向模型推演本窗口：自己的单位按指令移动，球按速度、摩擦、墙反弹、控球/抢断和进球判定推进；在推演的每一帧运行同一套策略，最后组装 20 帧 × `teamSize` 输出。
- 物理常量从 `catalog.js` 抄入代码（移动 3.15 格/秒、球速 14、摩擦 0.97、墙反弹 0.72、控球半径 0.82、抢断余量 0.12、盘带距离 0.62、踢球冷却 7 帧、控球锁 6 帧、抢断锁 4 帧）。
- 冻结帧先输出中立输入；异常时兜底输出 20 帧中立输入，优先避免技术负。

### 3.2 角色与关键行为

- **门将**（`n≥2`）：粘性选择，优先沿用上一窗口门将；站在球—球门中心连线上，按比例出击；球距本方球门中心不足 3.4 格时直接扑球；自由球高速朝本方球门飞来时按预测轨迹找拦截点。
- **追球者**：每个窗口选离球（或预测拦截点）最近的本方非门将单位；开球时门将也参与。
- **支援/防守者**：控球时按固定纵向分工前插；无球时退到球—球门连线。
- **精确护球**：控球者每帧从 360 个角度中选一个，使球（持球者前方 0.62 格）到所有对手的最小距离最大，并把窗口开始时的对手位置作为虚拟障碍。
- **保守射门**：只有距离 <3.6 格，或距离 <7 格且线路余量 >2.2 时才射门；射门目标只取对方球门线上的 5 个点（y=10.8/11.6/13.0/14.4/15.2）。
- **门线终结**：持球者进入球门高度（y∈[10.6,15.4]）且贴近对方门线（队 0 的 x≥41.9，队 1 的 x≤1.1）时，直接朝球门起脚，利用“进球判定先于控球判定”的引擎顺序。
- **贴墙压制（stall）**：我方领先 ≥1 球且 `timeLeft ≤ 60` 且我方控球时，持球者移动到最近的安全墙点并朝墙站立，其余队友退到持球者后方约 6 格；`STALL_TIME` 固定为 60 秒，不读环境变量。
- **安全后卫**：若被指定为门将的人正是持球者，则从其余单位中选离自家球门最近的人本窗口按门将逻辑站位，避免门将带球压上后空门。

### 4.3 机制实验与协议检查

- **贴墙压制**（`tools/pin_test.js`）：n=1/2/3/6，三种朝墙方向，400 帧；`lostFrames=0`，`minOwnerDist=0.000`，即使所有对手同时扑抢也无法改变 owner。结论：在本地引擎上，领先时贴墙可以把时间耗尽。
- **门线终结**（`tools/goalmouth_test.js`）：持球者在 x=42、守门员在 (43.2,13) 时起脚即得分；x=42.4、42.6 同样得分；x=41 起脚不得分（球停在 42.29）。因此代码用 x≥41.9 作为“足够贴近门线”的阈值。
- **协议检查**：用 `example.json`（`teamSize=5`）单行观察测试，输出 1 行 JSON、20 帧 × 5 个单位，所有 `dir` 合法、`aim` 为 `null` 或 0–359 度、`kick` 为布尔；耗时 **0.0218 秒**，stderr 为空。

## 5. 复盘后的改动（面向第 3 轮，`b4b5cc...`）

### 5.1 改动内容：n≥4 时的双门角封堵

第 2 轮 g2 是 n=5、丢 4 球。赛前已知的弱点之一是“20 帧决策粒度下，对方在 7–9 格外打远角，门将窗口内无法二次反应”。但直接把所有后卫改成封两个门角（含 n=3）在本地会让 n=3 退化：n=3 只有一名非门将后卫，封角会放空中路。实测“所有人数都封角、Dgoal<10”的版本在强对手 60 局电池里 n=3 为 4W6L、22:32，而提交版是 6W4L、26:24。

因此本轮只对 **n≥4** 启用，并且只在球已经逼近本方球门（球到本方球门中心距离 `Dgoal < 12`）时启用：

```python
# agents/role_decide，非门将防守者
Dgoal = math.hypot(bp[0] - my_gx, bp[1] - 13.0)
if n >= 4 and Dgoal < 12.0:
    post_y = 10.8 if (u.index % 2 == 0) else 15.2
    frac = 0.50
    tx = bp[0] + (my_gx - bp[0]) * frac
    ty = bp[1] + (post_y - bp[1]) * frac
    # 轻微分散，避免与另一名后卫重叠
    settle = spread_y.get(u.id, 0.0) * 0.12
    ty = clamp(ty + settle, 3.0, 23.0)
    tx = clamp(tx, 2.0, W - 2.0)
    return (dir_toward((u.x, u.y), (tx, ty)), None, False)
```

- `n≤3` 保持原来的“球—球门中心连线”站位；代码路径在相同输入下不变，因此 **r2-g1 的 n=3 行为不受该改动影响**。
- `n≥4` 时，非门将后卫按 `index` 奇偶分别封 y=10.8 和 y=15.2 两个门角，减少“所有后卫和门将挤在中心线、被一脚远角绕过”的情况。
- 该改动**没有参加第 2 轮**；它是在看到 g2 的 n=5 失 4 球后，用本地官方 `simulation.js` 自测出来的候选修复。

### 5.3 这个改动能说明什么、不能说明什么

- **能说明**：在本地官方 `simulation.js` 上，n≥4 的双门角封堵明显改善了 n=5 的防守数据，且不改变 n≤3 的行为；120 局和 300 局两套电池方向一致。
- **不能说明**：它**没有在官方第 2 轮使用**，不能声称“如果早用就能赢下 r2-g2”。官方对手 sol 的打法、射门位置和进球时间都未知；本地对手都是自写脚本，不能替代官方对手。这个改动是“基于战报弱点 + 本地验证”的下一步候选，不是已证实的官方胜利方案。

## 6. 局限与风险

1. **没有官方回放。** 公开战报只有聚合字段，没有进球时间、射门位置、事件流；本文无法逐球复盘，也无法确认 stall 是否触发、失球是否来自远角。
2. **没有射门数据。** `kicks` 不是 `shots`；本文只报告进球、踢球和控球，没有编造射门数、射正数或预期进球。
3. **样本极小。** 第 2 轮只有 2 局、1 个系列；不能据此推断模型或策略的综合能力。官方 n=3 小胜、n=5 小负，只能说明这两场的结果，不能说明“n=3 一定强/弱”。
4. **本地对手同源。** 10 个自写对手里，v0/noshield/exactshield/exp1/exp2 都源自同一份早期代码，无法覆盖官方对手可能采用的护球、传球、长传、全场紧逼或完全不同的射门选择。对 exp2 只有 7W5L，说明“镜像级”对手并不被压制。
5. **确定性带来的样本相关性。** 固定人数 + 固定座位 + 固定 seed 只有一局；120 局电池不是 120 个独立样本，300 局 5 seed 也仍有相关性，不能给置信区间。12 局头对头的排序与全电池排序曾经不一致，说明结果对对手集合和初始条件敏感。
6. **n=3 仍然弱。** 300 局强对手电池中 n=3 是 30W20L；第 2 轮 g1 也只是 3:2 小胜。复盘后的改动有意不碰 n≤3，所以这个弱点仍然存在。
7. **远角射门/20 帧反应问题没有根治。** n≥4 的双门角封堵只是让后卫提前占位，不能保证门将在窗口内二次反应；n=3 仍只有一名非门将后卫，无法同时封两个角。
8. **贴墙压制的引擎依赖。** 它依赖“贴墙时球重置到持球者中心、抢断要求 `d+0.12 < 0`”的本地引擎语义；如果官方引擎修改了贴墙控球/抢断细节，机制可能失效。另外，领先 1 球后从第 60 秒开始放弃进攻，可能牺牲净胜球；规则没有说明是否用净胜球排序。
9. **静态物理常量。** 程序没有从 `obs.rules` 动态读取参数，而是使用 `catalog.js` 的固定值；如果官方引擎参数变化，20 帧前向模型会漂移。
10. **座位差异。** 120 局全电池 a 座 56W1D3L、b 座 54W6L；第 2 轮 g2 正好是 b 座。新改动没有消除座位差异。
11. **`duration` 单位未知。** 战报的 1.32 / 2.07 未注明单位，本文不把它当作模拟时长；模拟时长以 `frames=2401 / 20 Hz = 120.05 s` 为准。
12. **没有读取对方代码。** 所有对手分析仅来自公开战报的聚合统计；没有使用对方代码、回放或私有数据。
