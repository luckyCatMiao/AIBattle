# 3V3 足球 · 第一轮准备复盘

> 本文只记录**准备期的离线自测**。截至提交时，官方对局尚未进行，因此没有任何官方比分或对手信息；下文所有比分均来自本地用官方 `simulation.js` 运行的自测，不代表比赛结果。

## 1. 提交内容

- `entry.json`：`{"mode":"program","command":["python3","agent.py"]}`
- `agent.py`：纯 Python 3 标准库实现，逐行读取 stdin 的 JSON 观察，向 stdout 输出一行 `{"inputs":[...]}` 并立即 flush；不使用网络、不读取任何外部文件、不区分种子硬编码。
- 每帧严格输出 `teamSize` 个单位输入，共 20 帧；按 `u.index` 对齐。任何异常（解析失败、字段缺失、超时前兜底）都退化为 20 帧中性输入，保证协议合法（宁可丢球，不 technical loss）。

## 2. 实际采用的策略

### 2.1 总体框架

每个响应只拿到当前观察，因此程序内部实现了一个与官方规则一致的**前向模型**（移动/贴墙滑动、单位分离、球的摩擦与撞墙反弹、控球/抢断/踢球冷却），在 1 秒窗口内推演 20 帧。策略在每个窗口开始时算一次角色与目标，之后按模型滚动执行；下一窗口再根据真实观察纠偏。对手位置用上一窗口的速度外推（带 4.5 u/s 的瞬移尖峰保护，开球/换场复位时清零）。

### 2.2 角色分工

- **门将**（`n>=2`）：粘性选择——沿用上一窗口的门将，只有它离自家球门超过 15 个单位或比赛重置时才重选（选离自家球门最近者）。门将站在球门中心与球连线的方向上，后退距离 `0.68·D`（D 为球到门中心距离），并受人数相关上限约束（n=2 为 11，n=3 为 12，n>=4 为 14）。这个几何保证 6 宽球门的射门锥大部分被 0.82 的控球半径覆盖；同时按球的高度微调站位。
  - 门将的参考球位置采用**半冻结**：对手控球时，把窗口开始时的真实球位与模型预测位置做 0.5 混合。完全冻结对远射最稳，但会被贴身盘带打穿；完全动态又会被“带球假动作+外推速度”骗出门线。0.5 混合是自测中两种极端之间的最佳折中。
  - 自由球高速飞向自家球门时，按弹道找可到达的拦截点；球已逼近则直接扑球。
  - `n=1` 时没有独立门将：对手控球时该单位退守球门（清道夫门将），自由球/我方控球时正常追球进攻。1v1 中“谁先控球谁基本赢”，因此不能让人一直守在门里。
- **追球者**：离预测球点最近的单位（门将通常不参与，除非判定为中圈开球——球在 (22,13)、无 owner、速度≈0，此时门将也去抢，避免中路人当门将导致没人抢开球）。自由球用弹道预测求拦截点；对手控球时从侧方逼近并尝试抢断。
- **支援/防守者**：按固定纵向分工散开。我方控球时前插到传球线附近并拉开宽度；对方控球时站在“球—自家球门”连线上，靠球门一侧卡位，并兼顾盯防附近对手。

### 2.3 控球决策

- 持球者用**屏蔽式朝向**：`aim` 独立于移动方向，把身体放在最近逼抢对手与球之间，球因此位于远离对手的一侧；同等速度的单一防守者无法从另一侧够到球。这是 1v1 和局部少打少能稳定推进的关键。
- 朝对方球门推进；进入射程且射门线路未被封堵时直接射向球门 6 宽范围内的空当（`shot_target` 会避开站在线路上的对手）。
- 被逼抢或距离较远时，窗口开始时评估一次传球：若存在空位队友且线路安全则传出，否则继续带球。传球在自测中主要提升了对多人大巴阵的破密防效率，但也带来被拦截风险，因此只在“明显值”时启用。
- 开球/进球后的冻结期：观察里的 `freeze` 会换算成帧数，前缀输出中性帧（引擎本就不动），剩余帧才执行计划，避免在冻结期空转浪费窗口。

### 2.4 健壮性处理

- 新比赛/换场：`frame` 回退或归零时清空记忆（上一窗口速度、门将、比赛 key）。
- 位置跳变：速度模长 > 4.5 视为复位，不做外推。
- 所有输出在本地先用官方 `submitWindow`/`normalizeFrame` 校验过；20 帧 × `teamSize` 宽，方向名与 aim 角度均合法。
- 单次响应耗时实测约 0.02–0.07 秒（示例观察 0.065 秒），远低于 5 秒上限；连续两次响应（n=6）合计约 0.1 秒。

## 3. 自测方法与结果

### 3.1 方法

本地用官方 `simulation.js` + `catalog.js` 搭了子进程对战台（`tools/match.js`、`tools/bench.js`），完全按官方协议：每窗口喂 `sim.view(g, team)`，校验返回、`submitWindow`、`advanceWindow`。每个对手在 `n=1..6` 各打两局（交换先后手/座位），共 12 局；对手均为自写脚本，未读取任何对方文件。

自写对手：

- `baseline`：最近者追球，持球者每帧直接朝球门中心踢。
- `kickbot`：最近者追球，持球者长传吊向对方球门，门将离线 2 格。
- `dribbler`：持球者带球到门前 16 格内射门。
- `park`：全员深度回收摆大巴，得球后长传反击。
- `swarm`：全员追球，持球者推进到 18 格内射门。
- `noshield`：本程序的“不屏蔽”克隆——同样带球推进，但朝向直接对准球门（贴身直射型）。
- `v0`：本程序的克隆，关闭传球、对手控球时改为直接扑球点（屏蔽盘带型）。
- `mirror`：自己打自己，用来检查座位对称性。

### 3.3 结果解读

- 对五种“直肠子”脚本（直接踢门、长传、带球、摆大巴、全员追球）保持全胜，失球极少，说明基础防守站位、门将覆盖和屏蔽推进在面对可预测策略时有效。
- 真正的强度门槛是两个“自己的变体”：`v0`（屏蔽盘带 + 传球）和 `noshield`（贴身直射）。84 局中的 6 场失利全部来自这两个对手，说明同水平对抗下胜负对细节非常敏感，也暴露出对贴身直射型仍有约 1/3 的局会丢分。
- 镜像战 31:31，且每局比分严格互为镜像（如 n=3 的 5:1 与 1:5），说明引擎与座位完全对称时，先手的一方在相同策略下拿到同样的结果分布；这验证了“座位交换”是公平的，但**不能**把镜像胜率当作强度指标。
- 门将参考球的三种方案做过对照：完全冻结对远射/长传最好（对 baseline、kickbot 曾 8:0/5:0），但被贴身盘带打穿（对 noshield 仅 7W5L）；完全动态能压住 noshield，却在对 baseline 的 n=6 崩盘（0W2L，含 1:5）。0.5 混合把两边都拉回可接受区间（noshield 8W4L，baseline/kickbot 全胜），是最终选择。
- 门将后退上限做过 10–15 的扫描：10–14 区间内都属于噪声级差异（各种组合约 25W5L），15 明显变差（对 v0、noshield 各 4W6L）。最终取 n=1 14、n=2 11、n=3 12、n>=4 14。

## 4. 局限与风险

1. **没有官方对局数据**。以上全部是本地脚本对手的结果；真实对手的策略、人数分布与座位安排未知，不能据此推断比赛胜负。本文没有编造任何官方比分。
2. **确定性带来的样本量问题**。引擎无随机数，seed 只在未指定 `teamSize` 时改变人数；固定人数后，同一对手 + 同一座位只有一局，比分对初始条件和细微参数高度混沌敏感。自测的 12 局是“不同人数 × 两个座位”，不是统计独立的重复试验，不能给出置信区间。
3. **1v1 的结构性开球劣势/优势**。`nearestEligible` 按数组顺序（team0 在前）严格小于比较，完全对称的开球距离下 team0 必然先碰球。先手方在 1v1 中拿到球后可以用屏蔽朝向稳定得分；作为 team1 时只能靠抢断和反击。自测中 1v1 对 `v0` 是先手 12:0、后手 10:0（仍胜），但对 `noshield` 是 5:6 / 6:5，说明这个结构性差异在强对手面前无法完全消除。
4. **门将折中仍有代价**。半冻结参考球对“带球突然变向 + 近距离爆射”依然会慢半拍；对 `noshield` 的 4 场失利即来源于此。继续调参在自测里已进入混沌区（同一改动在不同人数上此消彼长），没有可靠的泛化信号，因此停止过拟合。
5. **模型误差**。前向模型按官方常量实现，但浮点舍入、单位分离顺序、子步撞墙等细节仍可能与引擎有微小偏差；策略对此做了保守处理（每窗口用真实观察重置），但极端贴墙/门线情形仍可能出现计划与执行不一致。
6. **协议兜底优先于质量**。任何解析异常都会输出中性帧；如果官方观察出现未预期的字段缺失或类型变化，程序会保证合法但不一定踢得好。
7. **时间与资源**。单次响应实测远低于上限；但若运行环境 Python 启动极慢或观察异常巨大，仍以 5 秒硬限制为准，程序没有做主动的超时预算控制。
