## 1. 结论摘要（先给数字）

- 本轮实际提交版本的自测胜率**远未达到 90% 的目标**：`practice.py`（黑盒、冻结对手、交替座位、人数 1–6 轮换）实测 4 批种子共 80 局 **14 胜 16 平 50 负（胜率 17.5%）**；作为对照，上一系列最终策略在同样 4 批种子（另加一批）上也是 **14 胜 21 平 45 负（17.5%）**。**胜局数完全相同，不能宣称本轮有可测的提升。**
- 本地复现环境（自写 `work/simtest.py`：我方用 `policy2`，对方用我移植的 Sol 策略按“每决策窗口一次计划”的方式行动）在同一组种子上给出 **6 局 3 胜 2 平 1 负**（约 50%），而同一份代码在 `practice.py` 上只有 17.5%——**本地自测明显偏乐观**，只能用于筛选改动方向，不能当作正式赛胜率；下文所有“胜率”都以 `practice.py` 的黑盒实测为准。
- 本轮确实找到了两条可复现的机制性优势（第 2 节），但**没能把它们稳定转化为比分**：新版本进球数上去了（从上一系列的“团队局几乎 0 进球”变为每局约 0.5–1 球），但失球也上去了，净胜球仍为负。

## 2. 本轮读到的对手机制（`opponent/sol_agent.js`）

逐行阅读后确认的几条关键事实（下面都用“进攻坐标系”：把球门放在 x=43 一侧）：

1. **每决策窗口只重规划一次**。`decide()` 从当前观察出发，枚举 9 个候选窗口（`plan(o, model, variant)`，variant ∈ main/attack/wide/link，model ∈ previous/mirror/attack/chase），各自用 50 帧、3 种敌方模型做 rollout，再用 `evaluate()` 选一个。也就是说：**窗口内的 20 帧一旦发出就固定**，第 0 帧之后的走位来自它自己的 rollout（对“我们”的假设是它自己的策略，不是我们），所以在窗口内做“传球后立刻射门”这类两脚配合，它在 1 秒内看不到。
2. **防守线被 clamp 到 x≤36**。对手 policy 里防线目标 `x = clamp(b.x-3.2, 8, 29)`（局部坐标，等效真实 x = clamp(球x+3.2, 15, 36)）。因此**只要球越过 x=36，防线就追不上**，剩下只有守门员。这是本轮最有价值的发现。
3. **守门员默认站在离门线 3.3 格处**（真实 x=40.7），球进入 x>34 时改为出击到 `clamp(b.x-1.2,2,5)`、y 限制在 9.8–16.2；球在窗口开始时的位置决定它这 1 秒的目标。
4. **他们不会进入我方禁区**（`guardWindow` 把局部 x≥32.75、y∈[4.75,21.25] 全部过滤），所以不会吃红牌，也永远不来我方禁区逼抢。
5. `shot()` 模型**不检查球门口**（只检查 x<1.2 / y<1.23 / y>24.77），因此从贴边角度的“假射门”在它的评估里是进球——它的候选搜索会被这个偏差误导。

## 3. 本轮验证过的两条可利用机制

用自写的“射门实验室”（`work/shotlab2.py`、`work/passtest.py`：精确引擎 + 对手策略的窗口式行动）逐条验证：

- **角区走廊射门**：进攻方站在对方禁区**外**的走廊里（y<5.5 或 y>20.5，x≈36–40，注意规则只禁止“单位进入禁区”，球在禁区里不犯规），射向**近门柱**，即使对方守门员已经站到出击点，也 100% 进球；而同样位置射远门柱会被没收。
  - 从 x=36/38/40、y=4、瞄 y=10.7：全部进球；从 x=28–34 则全部被对方的防线挡下（这解释了为什么上一系列“20 格长射”几乎无效）。
- **同窗口内的“传球→一脚射门”**：A 在走廊 x≈33、B 在 x≈38，A 传球、B 控制后立刻射近角，在对手窗口计划固定（1 秒盲区）的前提下进球（`work/passtest.py` 的 6 个场景里 4 个进球；A 越靠后越容易被守门员预判）。

## 4. 本轮实际实现（`policy2.py`）

- **保留**：`agent.py` 内的 `pysim`（引擎移植）、协议、单文件构建。
- **新增/改写**：
  - 对手策略的 Python 移植（`_opolicy/_ocarry/_oshot/_omove` 等），用于预测对方 20 帧计划；移植后用 60 局历史回放验证：**对手第 0 帧动作的方向准确率 95.5%、踢球 99.4%、瞄准 99.3%**（`work/valid_opp.py`）。
  - **射门评估器** `shot_quality()`：精确球飞行 + 对手“反应延迟”可达模型（守门员 0.95 s、其他 0.55 s），返回进球概率；并用它做射门/传球/长传的选择。
  - **两脚球评估** `mate_potential()`：给某队友传球的价值 = 该队友“立刻射门”或“再传一脚后射门”的最大值，使“中场 → 走廊 → 射门”的链条能被搜索到。
  - **长传空当** `punt_eval()`：把球踢向进攻走廊的空当，并用“我方跑位球员 vs 对方球员谁先到”的赛跑模型估值（含踢球者自己 kick-and-chase）。
  - **防守**：守门员贴门线盯近门柱（球朝本方球门飞行时改为盯落点 y），两名后卫站在门线附近覆盖远门柱与中路，最近的前锋在“球—本方球门”连线上保持 2.6 格距离（0.82 半径在该距离上足以封住整个射门锥），散球若抢不到则退到落点的球门侧封线。
  - **红线**：任何我方单位都禁止进入对方禁区（移动 5 帧前瞻 + 目标点外推 + 被挤出后强制回撤），因为真实引擎（`simulation.js`）对进入对方禁区是**红牌罚下**（不是旧版 `pysim` 里的自由球——本轮的移植已同步修正）。

## 6. 局限与未解决问题（如实说明）

1. **胜率不达标**：本轮提交版本实测 17.5%（4 批种子 80 局），与上一系列版本在同一批种子上胜局完全相同（14:14），**没有可测的提升**。新决策层把进球数从“团队局几乎为 0”提升到每局约 0.5–1 球，但**失球增加得更多**，净胜球仍为负。
2. **1v1 是高方差对攻**：双方都没有守门员，谁先拿到球并射正谁得分，实测 11:3 胜、5:7 负、2:6 负、3:6 负——没有找到稳定压制手段。
3. **推进链条仍不稳定**：对方防线 + 守门员出击 + 追球者的组合，使得“把球送到 x≥36 走廊”这一步经常失败；长传会被对方守门员（站位 3.3 格）直接没收，短传会被防线挡下，带球会被追球者正面顶住。
4. **对手真实 `decide()` 与我的模型有差距**：我的本地模型按“对方策略窗口式行动”建模，实测对手真实表现更强（例如真实对局里对手会连续执行“长传走廊→近角射门”的固定套路并连续得分），所以本地 3 胜不能代表正式赛。
5. **没有解决“对手守门员总比我方快半步”的问题**：对手多个进球是 10–11 格处射远角，我方守门员与球路只差 0.1–0.3 格。
6. 本轮未能在正式赛条件下把角区走廊套路稳定执行到终局——机制本身在实验室里 100% 成立，但在真实对抗中缺少稳定的“把球送到走廊”的手段。
