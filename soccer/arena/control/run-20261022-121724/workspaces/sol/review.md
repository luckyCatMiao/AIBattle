# 第 2 轮提交说明与离线自测

## 状态与入口

本轮提交为 `entry.json`：

```json
{"mode":"program","command":["python3","agent.py"]}
```

`agent.py` 通过 `exec` 启动同目录的 `agent.js`。Node.js 持续接收 stdin JSON 行，每次输出一行 20 帧动作。运行时只读取本方脚本与公开规则模块，无网络、无文件写入。新增的 `agent_r1.js` 是准备开始时从本方上一轮 `agent.js` 复制的基线，也是本轮运行时使用的候选策略模块，**不是对方代码**。未修改 RULES.md、GAME.md、simulation.js、catalog.js、example.json。

**以下结果全部为本轮准备期实际运行的离线自测，不是第 2 轮正式比赛结果。** 当前 public_results.json 为空。上一轮说明及其历史战报转录保存在 `review_r1.md`，本轮没有新增正式战绩或逐帧正式回放。

## 实际采用策略

### 基础足球控制

- 按 `yourTeam` 左右镜像为统一向右进攻；实际人数取 `teamSize`，支持 1–6 人。
- 重建公开模拟状态，逐帧计算一秒内的移动、朝向和踢球，使用公开模拟器推进；窗口内没有真实反馈。
- 无人持球时预测摩擦与反弹，按可达时间选择抢球点；多人局其余单位保持接应与后方保护。
- 多人局 index 0 优先守门，追踪射门预测轨迹，近距离出击收球并向前解围；单人局唯一球员参与进攻，不永久驻门。
- 控球时枚举球门内部目标点，以精确角度射门；用对方到球路线的可达距离近似判断拦截风险。没有好射门时推进、走侧翼、护球，受压时寻找传球或空当。相对上一轮增加了较大横向角度的出球选择。

### 本轮新增：多模型候选窗口搜索

- 每次生成 7 个候选一秒动作窗口：包括上一轮本方策略、当前策略对不同对手模型的预测，以及更积极射门和更保守射门的变体。
- 对手模型有上一轮本方策略、积极射门模型、多单位追球压迫模型；全部自行编写，未读取对手程序。
- 每个候选分别在 3 个模型下推演最多 50 帧。前 20 帧执行候选固定动作，后续为启发式策略续演，不是实际可执行的窗口内反馈。
- 评分包含进球差、球场推进、持球、接球可达时间、射门空间、门将位置以及犯规惩罚。取最坏模型分数与平均分数的加权组合，略优先保留基准候选以减少无意义切换。
- 不是穷举最优解或真正的 minimax；对手模型和续演策略可能同时失真。

### 禁区安全

基础控制保留上一轮的保守禁区余量。候选窗口再通过安全过滤：根据持球、无球两种速度累计位置区间，限制整秒动作接近对方禁区，正面约 x=32.75，侧面约 y=4.75/21.25，必要时停止或后撤。左右座位统一镜像处理。

此过滤用于降低预测错误和碰撞推挤导致的犯规风险，**不是形式化保证**：区间未完整包含球员分离碰撞、墙边滑动和窗口内进球重置。最终测试中未发生本方犯规，但不能推断所有对手下绝不犯规。

## 实际运行的对抗自测

运行：

```text
node tournament_r2.js r1,swarm,corners,oracle 2 > r2_verified.jsonl
```

共 **96 场完整比赛**。每类覆盖 1–6 人、双座位、两个 seed（5000 + 10×人数，以及再加 1）。这些种子在固定人数测试中主要改变开球偏好，不是大量独立随机场景。除 oracle 外，双方均每秒提交 20 帧，均从自己的预测状态制定窗口，未读取实际未来动作。

| 对手类型 | 场数 | 本方胜/平/负 | 本方进球/失球 | 本方犯规 |
|---|---:|---:|---:|---:|
| swarm：多人追球压迫基线 | 24 | 24 / 0 / 0 | 146 / 0 | 0 |
| corners：守门及远角进攻基线 | 24 | 24 / 0 / 0 | 100 / 0 | 0 |
| r1：本方上一轮完整程序 | 24 | 8 / 16 / 0 | 31 / 14 | 0 |
| oracle：上一轮策略，每物理帧获得真实反馈 | 24 | 0 / 20 / 4 | 4 / 10 | 0 |

- 合计 **56 胜、36 平、4 负**；四场失利均为 oracle 的单人局。
- oracle 故意拥有每帧重新决策的额外信息优势，不符合正式比赛双方一秒窗口限制，只作压力测试。
- 最终版本 96 场记录到的最大单次决策时间为 **130.03 毫秒**，远低于 5 秒硬上限；这不是跨平台最坏耗时保证。
- 这些基线简单且与候选模型相关，不能把自测成绩当作对未知正式对手的胜率。

### 开发过程与未采用版本

保留的日志包括 `r2_initial.jsonl`、`r2_shoot.jsonl`、`r2_search.jsonl`、`r2_search2.jsonl`、`r2_final_tests.jsonl`。它们不是最终提交成绩。

- 缩小禁区余量未带来稳定改善。
- 给接球者自动更积极踢球，会在近身争抢时立即送出球权，已撤回。
- 多模型搜索早期版本对旧策略仍出现负场，后续加入旧策略候选与模型。
- 早期安全过滤的 96 场测试仍有 5 次本方犯规。逐帧定位发现，球员即使停留不动，也可能被追球队员持续分离推挤进禁区；因此扩大余量并重新完成全部 96 场，最终为零犯规。没有隐去失败试验，也没有将其与最终版本混算。

## 协议、边界状态与耗时检查

1. `node validate_r2.js`：覆盖所有人数、双座位，共 **144 个确定性伪随机状态**，含静止球、运动球和持球场景。所有输出通过公开 `submitWindow` 校验，并额外验证角度在 [0,360)、kick 为布尔值。最大响应 **91.23 毫秒**，结果在 `r2_validation.jsonl`。
2. 通过真实 `python3 agent.py` 入口，连续发送 example.json 观察 **6 行**（该样例为 5 人局），逐行读取并检查 20 帧、人数、方向、角度、踢球类型。全部通过；首行含启动约 **0.214 秒**，其余约 **0.026–0.032 秒**；退出码 0，stderr 为空。
3. `node --check agent.js` 与 `node --check agent_r1.js` 均通过。
4. 完整对抗包含上下半场和相应的金球阶段，不仅是静态格式测试。

## 局限

- 对未知对手没有在线动作辨识；模型覆盖有限，搜索仍可能选出仅对模型有效的动作。
- 对手真实动作在整秒内不可见；射门、收球和抢断的微小时间差会放大。逐帧反馈压力对手在单人局稳定赢下测试，不能声称单人防守问题已解决。
- 密集防守对抗旧策略出现大量平局，缺少复杂换位与强力破门机制。
- 接球时间、射门拦截、墙反弹预测中存在近似，续演评价不等同于真实进球概率。
- 观察未公开完整抢断锁、犯规锁和开球方状态；重建时部分状态只能近似。freeze 的公开精度也有限。
- 保守禁区安全限制会牺牲边路空间；没有证明不会被碰撞推进禁区。
- 未专门实现领先拖延或落后搏命；没有经过未知正式对手检验。第 2 轮正式复盘应等取得真实战报后另写，不能用这些自测冒充。
