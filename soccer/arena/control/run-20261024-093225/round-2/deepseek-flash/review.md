## 1. 从机制里挖出来的三条硬结论

全部由 `dev2/scenario.js`、`dev2/corridor.js` 用官方引擎实测得到。

### 1.1 决策窗口锁死了对手的反应时间

双方每 20 帧（1 秒）同时提交一次逐帧输入，收齐后统一推进。
**我这一窗口里发生的事，对手要到下一个窗口才可能回应。**

### 1.2 从禁区外沿起脚 ≈ 必进

球速 11 格/秒，球员 3.15 格/秒。球门有效宽度 5 格（y∈[10.5,15.5]），
门将控球半径只有 0.82 格 —— **门将最多覆盖 1.64 格，永远盖不满 5 格**。

实测（射手 (33,13)，门将在门线正中 (42.68,13)，起脚时刻分别取窗口第 0/5/10/19 帧）：

| 落点 ty | 结果 |
| --- | --- |
| 10.7 / 11.5 / 14.5 / 15.3 | **GOAL**（f0=0/5/10/19 全部进球） |
| 13.0（正对门将） | 每一次都被没收 |

而一名防守者站在球与球门连线上就能封死全部落点：

| 防守者位置 | 10.7 | 13.0 | 15.3 |
| --- | --- | --- | --- |
| (35.5, 13.0)（正中，距球 1.5 格） | 挡 | 挡 | 挡 |
| (35.5, 12.2)（偏 0.8 格） | 挡 | 挡 | **GOAL** |

**结论：整场比赛就是「谁能造出/消灭这条无遮挡通道」。**

### 1.3 对手「已锁定的移动」照样会挡球（最容易踩的坑）

我最初假设「对手这一窗口动不了」。`dev2/dumpgame.js` 回放直接打脸：
f560 我从 (39.1,4.7) 射门，按「对手静止」算出的余量是 **+1.05 格**，看上去必进；
但对面门将这一窗口的输入早已锁定为「向门线中点 (42.68,11.0) 移动」，
它照走不误，最后停在离球路 **0.55 格**的地方把球没收。

修正：用对手**最近一窗口的平均速度线性外推**来预测位置，
剩下的一部分按满速接近球路估计，两者加权（`SOCCER_TRUST`）。
在 3/5 人数 × 种子 1–3 × 两座位（每格 12 局）上扫这个权重：

| 对手 \ TRUST | 0.0 | 0.35 | 0.6 |
| --- | --- | --- | --- |
| v1 | 33.3% | 66.7% | **100%** |
| solid | 66.7% | **91.7%** | 83.3% |
| botSmart | **83.3%** | 75.0% | 50.0% |
| opp_search | 0% | 0% | 0% |
| opp_tr0（把 TRUST 固定成 0 的同一份代码） | 50.0% | 25.0% | 33.3% |
| 平均 | 46.7% | 51.7% | **53.3%** |

**「对手完全反应不了」和「对手完美反应」都是错的，中间那个才对**；
0.6 的平均最好，所以最终取 0.6。

## 2. 前向模型：`pysim.py` 与官方引擎逐位一致

把 `simulation.js` 的移动 / 贴墙滑动 / 单位分离 / 控球抢断 / 踢球 / 球体 4 子步 /
反弹 / 犯规 / 开球全部按原样移植，再用 `dev2/dumpraw.js` 导出官方引擎的
**未取整内部状态**逐帧比对（`dev2/validate3.py`，容差 1e-9）：

```
seed=7    n=1/2/3/5/6  各 40 窗口  mismatched=0
seed=11   n=1/2/3/5/6  各 40 窗口  mismatched=0
seed=23   n=1/2/3/5/6  各 40 窗口  mismatched=0
seed=41   n=1/2/3/5/6  各 40 窗口  mismatched=0
seed=101  n=1/2/3/5/6  各 40 窗口  mismatched=0
                合计 1000 个窗口，全部为 0
```

比对项：每个单位的 x/y/facing/kickCd/controlLock/stealLock/foulLock、
球的 x/y/vx/vy/owner、比分 / 帧号 / freeze / status。

有了它，「我这个计划会不会丢球 / 会不会进球」就能在本地算准——
`dev2/opp_search.py`、`dev2/replay.py` 都建立在这上面。

## 3. 最终策略

### 3.1 进攻

1. **有必进机会就第 0 帧起脚**：在 10.6–15.4 的落点网格上逐个算球路，取
   `margin = min over 飞行时刻 t、对手 o 的 (|o_pred(t) − ball(t)| − 3.15·max(0,t−反应时间) − 0.82)`
   最大、且离门将最远的落点。
2. **没有直接射门机会 → 找「一脚传球 + 接球人本窗口内起脚」的组合拳**：
   扫传球方向（±48°）、算接球帧，再在接球点重算必进余量。
3. **被逼抢且传不出去**：扫 36 个方向，选「**球被对手控制得最晚**、队友能先到则加分」的方向出球。
4. **都不是**：带球向禁区外沿推进。
5. **无球队友**：所有候选点先算一次「站到这里能不能形成无遮挡射门」，全队共享这张价值图，
   再按「价值高、跑得近、和队友不挤」贪心分配。

### 3.2 防守

1. 最近的人去抢球（松球用精确球路算出最早能拿到的点）。
2. 第二个人站到「球 → 本方球门中心」连线前 2.2 格，堵死射门通道。
3. 其余人盯对方最靠近我方球门的接应点。
4. 门将：球在飞行时取球路与本方门线的交点；否则站「球对两根门柱张角的角平分线」。
5. **1v1 特例**：唯一一人从**本方球门一侧**贴上去（球→本方门线方向 0.45 格）。
   这样抢下球的瞬间球正好被放在朝对方球门的方向上，可以直接起脚。
   实测把 1v1 对 solid 从 **0:6 翻成 6:0**（进 24 失 6）。
6. **绝不踏入对方禁区**（会判犯规）：帧构建时对每个单位做禁区规避，只沿边界滑动。

### 3.3 与第 1 轮 v1 的差别

v1 也是几何派，但它的射门判据假设「对手 1.15 秒后才反应」，
而且**传球组合拳是坏的**：`build_frames` 只给持球者发 `kick`，
接球人那一帧的 `kick` 从来没被真正发出。所以 v1 的「传+射」实际退化成「传，然后等下个窗口」。
本轮把组合拳打通，并把「对手静止」换成了「按对手速度外推 + 余量」。

## 6. 被否决的做法（附实测，避免下一轮重走）

| 做法 | 实测 | 判定 |
| --- | --- | --- |
| 假设对手本窗口完全静止（`TRUST=0`） | 对 v1 33.3%，1v1 从 12–0 掉到 8–8 | 否决 |
| 完全按对手速度外推、不给追赶余量（`TRUST=1`） | 对 v1 66.7%，1v1 8–8、5v5 12–4 | 否决 |
| 把对方门将建模成「朝本方门线对准球的那点满速移动」 | 对 v1 从 100% 掉到 50%，对 solid 83.3%→50% | 否决（说明真实门将并不会可靠地扑到球路上） |
| 无球队友固定站三个「前场高度」（v1 做法，`SUPX=0`） | 3v3 只有 4–4 | 否决 |
| 「对手够不到、队友更近」出球线路（`FB=1`，要求必须有队友先接到） | 对 v1 75.0% | 否决 |
| 1v1 也用「最大化被拦截时间」的出球（`FB=2` 全人数） | 对 v1 的 1v1 从 6–0 掉到 3–3；对 solid 1v1 3:18 | 否决，只在 3 人以上启用 |
| 全员都从本方球门一侧贴上（`PRES=1` 全人数） | 3v3 对 solid 从 4–2 掉到 0–6 | 否决，只在 1v1 启用 |
| 沿 y<6 / y>20 走廊贴到门线再射 | 近距离射门角度太陡，反而更容易被门将没收 | 否决 |
| 26 帧 rollout 搜索（`SEARCH=1`，用「无策略幽灵对手」当模型） | 对 v1 仍是 8–0，但对搜索型对手从 1–5–2 掉到 0–7–1 | **未启用** |
| 抢到球当帧就起脚（`ONEPASS`） | 与关闭时**逐字节相同**（预测条件几乎从不成立） | 未启用 |

## 7. 局限（请连同上面的胜率一起看）

1. **没有和 Sol 交过手。** 本轮规则禁止读取对方工作区与代码，我也没有对方文件。
   上面每一个胜率都是对我**自己的 v1 / 参数变体 / 手写机器人**测的。
   第 1 轮的教训就是「弱机器人自测 93.9% 换来正式赛 0:2 / 1:6」——
   这份 review 里的百分比同样**没有对 Sol 的预测力**。
2. **对局几乎完全确定，样本量远小于局数。** 双方都是确定性程序，每次开球后状态完全重置，
   所以同一人数下不同种子往往只产生 **2 种结果**（取决于 `|seed|%2` 决定谁先开球）。
   「40 胜 0 负」实际只有 4 个独立结果；如果把种子换成另一批，成绩可能就有出入
   （我用新种子 11–15 复测过，还是 100%，但这仍然只有 2 个独立结果）。
3. **最大的隐患：一个能建模我方的搜索型对手把我打成 0:12。**
   `dev2/opp_search.py` 在 agent 自己的候选集上做 1 窗口 rollout，
   **并且直接用 agent 的真实 20 帧计划当对手模型**——这是超现实的强假设
   （真实对手不知道我的代码），但它正是「用官方引擎做 50 帧 rollout」那类 agent 的形态。
   我试过用「无策略幽灵对手」模型做同样的搜索（`SEARCH=1`），结果反而更差，所以没有启用。
   **如果 Sol 的对手模型足够好，我的胜率会明显低于上面写的数字。**
4. **不同对手之间方差极大。** 同一份程序：对 v1 的 3v3 是 12–0，对 botSmart 的 3v3 是 0–2–4
   （几乎全是 0:0 / 1:1）。这不是随机波动，而是我的进攻套路在「两名防守者始终堵在球门前」时
   几乎没有解法。**这是本轮最该继续解决的问题。**
5. **6v6 是明确短板**（对 v1 只有 6–6，场均 0–1 球，多场 0:0）。第 3 轮会用到 6v6。
6. **对手模型仍是近似的。** 「最近一窗口平均速度线性外推」对匀速跑位准，对窗口内急停转向不准。
7. **门将站位没有最优解。** 角平分线只是折中；真正保险的是场上球员堵住通道，而补位并不总能及时。
8. **没有做终局/金球特化。** 程序完全不看比分与剩余时间，平分进入金球时行为与常规时间一致，
   不会加 aggressiveness——本轮有 6 场 0:0 / 1:1 拖进金球后仍是平局，这里本来还有提升空间。
