## 2. 机制分析（读 `simulation.js` + `catalog.js` 得出）

这些是策略的全部依据，都经过离线对局验证：

1. **决策窗口是 20 帧（1 秒），双方同时提交整段 20 帧后才统一推进。**
   因此对手在这 20 帧里的动作在窗口开始时就已锁定，**本窗口内无法对本窗口新出现的情况做反应**。
2. 球被踢出后速度 11 格/秒、每帧 ×0.978；从距门线 9 格（禁区外沿）射门飞行约 0.94 秒（≈19 帧）。
   **在窗口第 0 帧起脚，球正好在本窗口内到门线，对方门将完全没有反应时间**——只要落点离门将超过
   0.82 格就是必进球。飞行距离越远（>12 格）对方门将越有时间横移补位，所以「把球送到禁区外沿再射」
   是唯一稳定的得分手段。
3. 球员不能进对方禁区（犯规）；禁区深 9 格，所以射手最靠前只能站到距门线 9 格。
   但**禁区只覆盖 y∈[6,20]**：在 y<6 或 y>20 的边路，球员可以一直走到 x≈42（贴底线），
   那里的射门角度极其刁钻。
4. 球离脚后走直线，唯一能挡射门的是「站在球与球门连线之间的人」。设球距门 D、防守人距球 r，
   防守人能封住的角度半宽 ≈ atan(2.5/D)，控制半径 0.82 ⇒ **r ≤ 0.33·D 就能封死全部射门角度**。
   所以被贴身盯防时不要硬射，要传。
5. **控球者离球固定 0.62 格；对手只要离球 < 0.50 格且更近就能抢断。**
   反过来，防守方贴到离球 0.45 格几乎必定断球 —— 这是本作最强的防守动作。
6. 球速 11 格/秒 >> 球员 3.15 格/秒 ⇒ 传球能瞬间把球送过防守人；但传得太远（>10 格）
   落点在 1 秒后才到，一次性射门就失去「窗口内起脚」的优势，所以短传才有价值。
7. 裁判的镜像对称轴是 **x=22**（球门线 x=1 / x=43，出生点 11.5 / 32.5）。
   第一版程序把 x=21.5 当对称轴，导致球队 1 视角下门将站位差 1 格，自测出现 8:0 的座位偏差，
   修正后自测双方座位胜负平衡。

## 3. 实际采用的策略

**进攻（我方控球）**
1. 先算「窗口第 0 帧起脚」的射门：沿球到对方门线的直线采样，按
   `对手反应延迟 1.15 秒后才开始全速跑向球` 的模型算富余量；在门框内 9 个落点里挑
   「富余量 + 离门将距离」最大的一个。可行就第 0 帧起脚打离门将远的死角。
2. 射不了（被贴身封死）就找传球：对每个队友模拟球飞到其身前 0/2.5/5 格的线路，
   要求线路不被对手拦截、队友能在球到达时赶到，并评估「接到后能不能立刻射门」；
   挑分最高的一条，**队友接球当帧就起脚**（一次性配合，防守方本窗口内无法调整）。
3. 传不了：距门线 >16 格时直接**长传打到禁区外沿空当**（球速 11 格/秒，一步推进 20+ 格），
   全队压上抢第二点；否则带球推进到禁区外沿。
4. 门将得球**立刻出球**（找队友或大脚开向对方半场），绝不带球。
5. 无球队员站位在对方禁区外沿一线，按球的纵向位置铺开。

**防守（对方控球）**
- 离球最近的球员贴到**离球 0.45 格**（在球与自家球门连线上）—— 既封死射门扇面又能直接抢断；
- 第二近的球员在 4 格后补位，其余盯对方最靠前的球员；
- 门将守门线，位置取「球飞向本方门线的预测交点 y」，否则按球的位置做角度收缩。

**通用约束**
- 所有目标点都做「对方禁区外推」处理（安全边距 0.62 格）；
- 每帧生成时再做一次硬保护：如果这一步会踩进对方禁区，就改成沿禁区边界滑动并发出对应方向；
- 落后且时间不多 / 金球阶段会把门将压到中线当出球点搏一把。

## 4. 自测结果（全部为离线实跑，用官方 `simulation.js` 当裁判）

对手：`botChase`（全员追球）、`botKeeper`（追球+门将）、`botSmart`（门将+贴身封堵+选角度射门）、
`botBlock`（铁桶防守+一次性进攻）、`botRush`（全场紧逼+见球就射）。

| botBlock | 36–0–0 | 100% | 134 | 0 |
| botRush | 36–0–0 | 100% | 136 | 0 |
| botKeeper | 33–0–3 | 91.7% | 64 | 0 |
| botChase | 31–0–5 | 86.1% | 68 | 0 |
| botSmart | 33–0–3 | 91.7% | 66 | 0 |

**其他验证**
- 协议：每一帧都过 `submitWindow` 校验（非法方向/字段会直接抛错），540+ 局无一次失败；`example.json` 冒烟测试输出 20 帧 × teamSize 单位，stderr 为空。
- 响应时间：单窗口最大 34 ms、平均 0.9 ms（硬上限 5000 ms）。
- 镜像等价性：把观察镜像后喂给程序，输出严格镜像，100/100 项零偏差（说明没有座位偏置）。
- 裁判对称性：给两队喂互为镜像的随机输入，540 帧内状态始终保持镜像。
- 自内战：py(team0) vs py(team1) = 5–3–0，接近平衡。
- 早期版本的教训（已修）：门将带球不传被断、座位坐标用了 21.5 对称轴、`build()` 里改内部位置却仍发出原方向（保护无效）。

## 5. 局限与已知风险（不粉饰）

1. **对手不可见，以上全部是对自写机器人的胜率。** sol 的真实风格未知；如果 sol 的防守组织
   比 `botSmart`/`botChase` 更强，胜率会低于 93.3%。这是最大的不确定性。
2. **平局是主要失分项（36/540 = 6.7%），全部是 0–0。** 典型场景是：对方把球控在自己禁区里
   （例如门将停在门线上抱球），而规则禁止我方球员进入对方禁区，于是形成无法打破的僵局。
   规则没有进攻时限，这个僵局在现行裁判下无解；我没有让程序「故意犯规去把球逼出来」。
3. **我方犯规偏多（约 8–11 次/局）。** 程序的目标点全部做过禁区外推，但 8 方向移动 + 队友
   碰撞会把球员挤进禁区边角。我做过一个「绝不踏入对方禁区」的严格版本并实测：
   同套自测从 93.3% 掉到 70%~86%（因为丢掉了「追球到禁区边、由裁判把球放到任意球点」带来的
   进攻机会，同时也救不出对方禁区里的球）。最终选择保留自然追球行为，不做刻意的犯规战术。
   需要说明的是：本引擎判罚任意球时球会被放在禁区外最近的任意球点且随后是可争抢的松球，
   这与规则文本「由被犯规方开球」并不一致；我的程序没有针对这一点做任何定向设计。
4. **进球高度依赖「窗口第 0 帧起脚」**。一旦某个窗口的时序被打乱（例如球在窗口中途才到我方
   脚下），射门成功率会明显下降；这是 0–0 平局的另一个来源。
5. 1 人局（solo）和 2 人局没有中场组织，全靠门将长传 + 单点抢点，偶然性更大。

```bash
node dev/matrix.js                 # 5 对手 × 6 人数 × 双方座位
SEEDOFF=200 node dev/matrix.js     # 换一组互不重叠的种子
node dev/mirrortest.js             # 镜像等价性
node dev/timing.js                 # 单窗口响应时间
node dev/run.js --a py --py agent.py --b botSmart --seeds 1,2,3 -v
```
