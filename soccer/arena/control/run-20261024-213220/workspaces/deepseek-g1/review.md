## 1. 这一版做了什么（相对上一版）

上一版（第 3 轮提交）是「启发式 + 每窗口候选 rollout 搜索」，对 Sol 是 **0 胜**：
6 局只进 3 球、失 16 球，几乎每局都在本方半场被压着打。复盘后我判断它的
搜索建立在错误的动作模型上，于是**保留 `pysim.py`（引擎逐帧移植）与单文件构建流程，
重写决策层**为 `core2.py`：

| 模块 | 做法 |
| --- | --- |
| 门将 | 「清道夫门将」：站在**球—本方球门中心连线**上，距门 `k = 0.70·D`（上限随人数 8.6~11） |
| 防守 | 门将 + 1~2 名「门墙」球员：同样在连线上、横向 ±1.7 格错开，**站进本方禁区**（对手进禁区即犯规，绕不到身后） |
| 进攻 | 射手按 index 固定（不随球漂移），优先去对方球门两侧的**角区/弧顶**等「高射门价值点」 |
| 出球 | 统一「踢球评估」：任意角度踢出后逐帧模拟球路，先看会不会被身体截下、再看会不会进，最后看落点争夺 |
| 时间管理 | 平/落后且剩余 <50 s（或金球）切「全员压上」；领先不切换 |

## 2. 机制层面的关键发现（都有可复现实验）

### 2.1 门将深度决定一切：`k ≈ 0.7·D` 能封死 21 格内的射门

`dev4/exp_keeper.js`：射手固定在若干位置、门将站在「球—球门中心」连线上距门 k 格，
统计球门 5 格有效宽度里有多少落点能进（25 个落点）：

| 射手 | k=3 | k=5 | k=7 | k=9 | k=11 | k=13 | k=15 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| (12,9) | 14/25 | 10/25 | 3/25 | **0** | **0** | 25/25 | 25/25 |
| (15,13) | 14/25 | 12/25 | 8/25 | 2/25 | **0** | **0** | 25/25 |
| (18,7) | 14/25 | 13/25 | 11/25 | 8/25 | 3/25 | **0** | **0** |
| (22,13) | 16/25 | 14/25 | 12/25 | 10/25 | 8/25 | 4/25 | **0** |

结论：**门将必须前压到约 0.67~0.75·D**（k 超过 D 就跑到射手身后，反而全进）。
注意门将**离开本方禁区完全合法**——禁区限制只针对「对方禁区」。
这一条同时解释了两件事：为什么 Sol 能从 10~14 格稳定破门（我的旧门将站得太浅），
以及为什么我这一版把 `k` 从 8.6 提到 11 之后，大人数局的失球从 20 掉到 4。

### 2.2 只靠门将不够：对手一次横传就能把他晃开

实测（`dev4/concede.py` 复盘）失球模式：Sol 在禁区弧顶横传 1~2 格后立刻起脚，
我的门将这一窗口是被锁死的，追不上这 1.5 格的横向位移，于是「站在正确连线上」变成
「站偏 1.5 格」——而 k 越深，1.5 格的横向误差投射到球门线就越大。
所以必须再加一层**静态覆盖**：门墙球员横向 ±1.7 格错开，三个人合起来盖住整个射门扇面。
实测把门墙从 3 人减到 2 人（腾出攻击手）反而更好：0:5 → 2:1。

### 2.3 引擎的「踢球起点」是 0.59 格，不是 0.62

`kickBall` 里 `off = unitRadius + ballRadius + 0.03 = 0.59`。我一开始按 0.69 算，
在角区那种掠射角度上会差 0.1 格——正好是「擦着门柱出去」和「进」的区别。
改成 0.59 后，同一批对手的胜率从 50% 直接跳到 **66.7%**。这是本轮单点收益最大的修复。

### 2.4 禁区是免费的进攻出发地

对手不能进我的禁区，所以我把门墙放进本方禁区：他们不会被从身后绕过来，
射门又必须从禁区外（≥9 格）起脚。这条规则是本轮防守体系的支点。

## 3. 自测方法与结果

### 3.1 怎么测

- 唯一对手是 `practice.py` 拉起的**冻结 Sol**（`--games 12/24`，交替座位、人数 1–6 轮换）。
- 另外用三个 `--seed-base`（9500 / 20000 / 31000）各跑 12 局，检查是否只是过拟合某一批种子。
- 机制实验用 `simulation.js`（`dev4/exp_keeper.js`）与 `pysim.py`。
- 调试工具：`dev4/dbg.py`（把真实观察喂给决策函数并打印角色/目标）、
  `dev4/concede.py`（逐球复盘失球前的站位）、`dev4/trace1.js`（整局逐球员轨迹）。

### 3.2 结果

| 口径 | 战绩 | 胜率 | 进:失 |
| --- | --- | --- | --- |
| 24 局（默认种子） | 16-0-8 | 66.7% | 40:4 |
| 12 局 × seed-base 9500 | 8-0-4 | 66.7% | — |
| 12 局 × seed-base 20000 | 8-0-4 | 66.7% | — |
| 12 局 × seed-base 31000 | 8-0-4 | 66.7% | — |
| **累计** | **40-0-20** | **66.7%** | — |

三个 seed-base 结果完全一致，说明这不是挑种子挑出来的：胜负结构是稳定的
「大人数全胜、小人数全平」。

### 3.3 走错的路（都实测过，记录以免重复）

| 尝试 | 结果 | 判断 |
| --- | --- | --- |
| 拿到球就大脚往前开（hoof-ball） | 1 胜 5 负，失 17 球 | 送球权，Sol 反击效率极高 |
| 全队压上、只留门将 | 0 胜，单局失到 8 球 | 门墙才是防守支点 |
| 门将并入进攻（小人数局） | 2v2 从 0:0 变成 0:2 | 空门代价立刻兑现 |
| 长传找角区支点（不停球直接吊） | 与短传版本完全一致 | 传球评价本身没成为瓶颈 |
| 搏命阶段放宽射门门槛（远射也认） | 6 胜 4 负 | 远射基本等于交出球权 |
| 门墙间距 1.3 / 2.2 格 | 4 胜 6 负 / 6 胜 4 负 | **1.7 格最优**，很敏感 |
| 冻结期间照常规划（不交中立帧） | 2 胜 10 负 | 反向优化，已回退 |
| 持球者远离球门时禁止走边线走廊 | 24 局 12 胜 12 平（1v1 全平） | 1v1 靠边路起脚，禁掉就没进球，已回退 |
| 小人数局把门将也当传球点 | 24 局 12 胜 12 平 | 同上，已回退 |

> 方法论教训：**12 局的练习赛分辨不出 50% 和 66.7%**（人数只轮换两轮，1v1 只占 2 局）。
> 我中途有两次「12 局看不出变化」的改动，换 24 局口径后才暴露成 12 胜 12 平。
> 最终版的所有结论都以 24 局为准。

### 3.4 顺带修掉的三个真 bug

1. **持球者角色没被赋值**：重写 `plan_roles` 时漏了 `roles[ci] = ('carrier', …)`，
   导致 3 人以上时持球者被当成「平衡位」球员，**全场一次都不射门**（0 进球持续了十几轮迭代）。
2. **`eval_kick` 先判进球再判拦截**：于是「球路穿过三个身体」也被算成必进球，
   持球者一直往人堆里射；改成先查拦截后查进球。
3. **踢球起点 0.59 写成 0.69**（见 §2.3）。

## 4. 最终策略一览

```
门将(index 0)   : 球—本方球门中心连线上，k=0.70·D（人数≥4 时上限 11，否则 8.6）
门墙(1~2 人)    : 同一条线上横向 ±1.7 格，站在本方禁区内
持球者         : ① 有通道就射（精确角度，瞄远端门柱）
                 ② 否则按 15° 网格 + 精确队友方向逐个评估「这脚踢出去会发生什么」
                 ③ 都不划算就带球（8 方向 8 帧前瞻，最大化射门潜力）
射手(1~2 人)    : 优先对方角区（y<6 / y>20 的走廊）与弧顶，挑「通道干净 + 射门价值高」的点
其余           : 追球 / 逼抢 / 门墙
平或落后 ≤50 s  : 全员压上（人数≥4 时）
```

每窗口只做一次决策：把 20 帧在我自己的 `pysim` 里推演一遍，逐帧重新决策，
对手用「追球」模型近似。单窗口最坏 0.08 s（上限 5 s）。

## 5. 局限与风险（请连同结论一起看）

1. **没达到 90%。** 66.7% 是实测，不是估计。差距全部集中在 **2v2 和 3v3**：
   这两档打成 0:0 的僵局（我控球 65~80%，球却始终推不过半场；对手也进不了）。
   我试过在人数 ≤3 时全员压上、门将压上、放宽射门门槛、双人逼抢，**全部更差**
   （最差 0:4）。也就是说在这两档里，我的进攻手段无法在对方摆好防线时创造
   10~12 格的干净射门，而任何加强进攻的改动都会先打穿自己的门墙。
2. **样本是确定性的。** 引擎没有随机数，seed 只决定人数和开球方。所以
   「24 局」实际是 6 种人数 × 2 座位 × 2 轮，不是 24 个独立样本；
   好在我用三个 seed-base 复核过，结论完全一致（见 §3.2）。
3. **66.7% 只对「冻结的 Sol」成立，不能外推。** 前几轮的历史反复证明：
   第 1 轮自测 93.9% → 正式 0:2 / 1:6；第 2 轮自测 88.9% → 正式 0:3 / 0:3。
   本轮的自测终于是**直接对 Sol** 打的（不是代理对手），可信度比前几轮高，
   但仍可能因为正式赛的种子（人数分布）不同而落到 33%（只抽到 2v2/3v3）或 100%（只抽到大人数）。
4. **2v2/3v3 的僵局本质上是「谁都推不动」。** 我的 agent 在这两档选择保平而不是冒险，
   因为实测冒险必输。如果正式赛的 6 局里小人数占比高，胜率会显著低于 66.7%。
5. **门墙间距、门将上限这类参数非常敏感**（±0.5 格就能让胜率摆动 16 个百分点），
   存在对这几局过拟合的风险。我尽量只保留「多个 seed-base 都一致」的改动。
6. **没做领先护球。** 早期版本有「领先就把球护进本方禁区」的做法，本轮没启用；
   本轮是靠防守把失球压到 24 局 4 个，而不是靠拖时间。
7. **金球/终局没有专门设计**：平局进金球时沿用「全员压上」。

## 6. 复现方式

```bash
# 对冻结 Sol 的练习赛（本报告的全部数字）
python practice.py --games 24
python practice.py --games 12 --seed-base 9500

# 协议与性能自检（72 个构造观察）
python dev4/proto_test.py

# 门将深度机制实验（需要 node + 官方 simulation.js）
node dev4/exp_keeper.js

# 复盘工具
python dev4/summary.py <practice 回放目录>
python dev4/concede.py <practice 回放目录>     # 每个失球前对手的起脚点与我方站位
python dev4/dbg.py                             # 把一个真实观察喂给决策函数并打印角色

# 重建提交产物（pysim.py + core2.py -> agent.py）
python dev4/build2.py agent.py
```

- `core2.py` 是真正在维护的决策源码；`agent.py` 是 `pysim.py + core2.py` 合并出的提交产物。
- `agent_round3_backup.py` 是本轮开始时的旧版（0% 那一版），仅作对照，不参与提交。
- 受保护文件（`RULES.md` / `GAME.md` / `simulation.js` / `catalog.js` / `example.json`）未改动。
