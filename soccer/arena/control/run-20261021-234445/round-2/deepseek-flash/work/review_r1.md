# 3V3 足球第 1 轮复盘（r1-g1 / r1-g2）

## 0. 结论摘要

第 1 轮两场都输给 `sol`，但输法不同：

- **r1-g1（2v2，我方 0:1）**：控球帧 1219:172（约 87.6% : 12.4%），踢球 25:13，但公开数据只能确认我方 25 脚踢球中至少 2 脚射正（2 次被扑、0 进球）；`sol` 的 13 脚踢球则对应 **12 次被扑 + 1 个进球**，即 13 脚全部射正。问题是“控球很多、最后一脚很少”，不是门将被打崩。
- **r1-g2（1v1，我方 6:7）**：双方各 17 脚踢球，合计 13 个进球、**0 次扑救**；我方 6/17（35.3%），`sol` 7/17（41.2%）。我方控球 250 帧（12.5 秒），`sol` 只有 17 帧（0.85 秒），但 `sol` 用极短的持球时间换到了 7 个进球，是典型的“拿球就起脚”风格。

针对这两场暴露的问题，我改了 1v1 门将覆盖、射门目标与射门时机，以及 2v2 的射门口袋/接应逻辑。自测中 1v1 对激进代理有提升，但 **2v2 的最后一传和射门质量仍未解决**：2v2 对代理对手 6 场 0 进球，自对弈仍是 1:0 的低比分。下面把公开战报能确定的数据、由数据反推的射门信息、以及实际改动分开写清楚。

### 1.1 模拟帧数与秒数

`simulation.js` 的 `checkClock` 在 `frame >= matchSeconds * hz` 时结束常规时间；`hz = 20`、`matchSeconds = 120`，即 2400 个物理步长。`frame` 从 0 开始计数，战报里的 `frames = 2401` 是含起始帧的帧计数：

- 实际推进 **2400 个 20 Hz 步长 = 120.00 秒**模拟时间；
- 若直接按 `2401 / 20` 字面换算，则是 **120.05 秒**，两者只差起始帧的 1 帧；
- `windows = 120`，每个窗口 20 帧，`120 × 20 = 2400` 帧，与上述一致。

`duration` 的 1.22 / 1.17 与 120 秒模拟时长不在同一量纲：若按分钟理解约为 73.2 / 70.2 秒实际耗时，若按秒理解则小于模拟时长，不可能。战报没有注明单位，因此本文只把它当作战报记录的实际耗时，**不用它计算模拟秒数**。

### 1.2 统计数组的归属

战报的 `stats`、`fouls`、`saves` 都按 `seats` 顺序排列：

- **r1-g1**：`stats[0]` 是 `deepseek-flash`（team 0），`stats[1]` 是 `sol`（team 1）；`saves[0]` 是我方门将的扑救，`saves[1]` 是 `sol` 门将的扑救。
- **r1-g2**：`stats[0]` 是 `sol`（team 0），`stats[1]` 是 `deepseek-flash`（team 1）；`saves[0]` 是 `sol` 的扑救，`saves[1]` 是我方的扑救。

公开战报中的 `saves` 是“该队门将完成的扑救次数”。这一点按 `simulation.js` 的 `save` 事件归属（事件 `team` 为门将所在队）解释。

公开战报不含逐事件时间线，因此无法还原每个进球的分钟、射门坐标、助攻或连续配合；本文只对可加总的计数（进球、踢球、扑救、控球帧、犯规）做推断，不补写不存在的比赛过程。

## 2. 逐场数据与射门推断

### 2.1 r1-g1（2v2，0:1）

#### 公开数据

| 队伍 | 座位 / 队伍号 | 进球 | 踢球 | 控球帧 | 控球秒 | 犯规 | 扑救 |
|---|---|---:|---:|---:|---:|---:|---:|
| `deepseek-flash`（我方） | seat 0 / team 0 | 0 | 25 | 1219 | 60.95 | 0 | 12 |
| `sol` | seat 1 / team 1 | 1 | 13 | 172 | 8.60 | 0 | 2 |

由公开字段直接可得：

- 控球占比：我方 `1219 / (1219 + 172) = 87.63%`，`sol = 12.37%`；
- 平均每次踢球前的控球帧数：我方 `1219 / 25 ≈ 48.8` 帧（约 2.44 秒），`sol` `172 / 13 ≈ 13.2` 帧（约 0.66 秒）；
- 进球率（按踢球数）：我方 `0/25 = 0%`，`sol` `1/13 = 7.69%`；
- 全场 1 个进球 / 120 秒 = 0.5 球/分钟。

#### 射门数据能反推到什么程度

公开战报没有逐脚射门事件、射门坐标、射正数或射门时间，只有 `kicks`、`saves`、`goals`。本复盘把“射正”定义为：**造成扑救或进球的踢球**，因此得到的是可确认下限，不是全部射正数。

- **`sol`：13 脚踢球 = 12 次被我方门将扑出 + 1 个进球。**  
  12 次扑救至少对应 12 脚不同的射正踢球，1 个进球至少对应 1 脚进球踢球；两者相加正好等于 `sol` 的总踢球数 13。因此在“进球来自本队踢球、每次扑救对应一脚踢球”的引擎事件语义下，`sol` 的 13 脚 **全部是射正**。  
  - 我方门将扑救率：`12/13 = 92.3%`；
  - `sol` 的射正转化率：`1/13 = 7.69%`。

- **我方：0 个进球 + 2 次被 `sol` 门将扑救。**  
  至少 2 脚踢球是射正（都被扑出）；其余 23 脚无法从公开数据区分是射偏、传球、解围、被封堵还是中柱。  
  - 已确认射正率下限：`2/25 = 8.0%`；
  - 已确认进球率：`0/25 = 0%`。

#### 比赛含义

这场的矛盾不是“门将丢球太多”，而是**控球没有转化成射门**：我方拿球约 61 秒、踢了 25 脚，却只确认 2 脚射正；`sol` 只拿球约 8.6 秒、踢 13 脚，却让 13 脚全部形成射正（12 脚被扑、1 脚进球）。`sol` 的射门频率是每 0.66 秒控球一脚，我方是每 2.44 秒控球一脚。  
换句话说，`sol` 用低控球换高频终结，我方用高控球换低质量终结；0:1 的比分里，我方门将的 12 次扑救是比分没有失控的直接原因。

### 2.2 r1-g2（1v1，6:7）

#### 公开数据

| 队伍 | 座位 / 队伍号 | 进球 | 踢球 | 控球帧 | 控球秒 | 犯规 | 扑救 |
|---|---|---:|---:|---:|---:|---:|---:|
| `sol` | seat 0 / team 0 | 7 | 17 | 17 | 0.85 | 0 | 0 |
| `deepseek-flash`（我方） | seat 1 / team 1 | 6 | 17 | 250 | 12.50 | 0 | 0 |

由公开字段直接可得：

- 控球占比：我方 `250 / (250 + 17) = 93.63%`，`sol = 6.37%`；
- 平均每次踢球前的控球帧数：我方 `250 / 17 ≈ 14.7` 帧（约 0.74 秒），`sol` `17 / 17 = 1.0` 帧（约 0.05 秒）；
- 每脚踢球的进球率：我方 `6/17 = 35.29%`，`sol` `7/17 = 41.18%`；
- 合计 `13/34 = 38.24%` 的踢球直接变成进球；
- 全场 13 个进球 / 120 秒 = 6.5 球/分钟，是一场高节奏对攻。

#### 射门数据能反推到什么程度

- 双方 `saves` 都是 0：公开战报中没有扑救事件；
- 比分给出 13 个进球（我方 6、`sol` 7），因此双方至少各有 6 / 7 脚踢球形成进球；
- 由于 `kicks = 17` 包含传球、解围、被封堵等非射门踢球，公开数据**无法确定**双方各自的射正总数，只能确定“进球数 ≤ 射正数 ≤ 踢球数”；
- 0 次扑救不等于 0 次射正：射正但进球时不会产生扑救事件；射正但中柱/被门线解围也可能没有扑救事件。能确定的是：**两队的门将都没有扑出任何一脚需要扑救的球**，13 个进球全部越过了门将。

#### 比赛含义

`sol` 的 17 帧控球恰好对应 17 脚踢球，最自然的解释是：它每次拿到球几乎都在同一帧起脚，不做长时间带球；我方则是平均持球约 0.74 秒后处理球。  
这场是 1v1 的结构性对攻：唯一单位既是门将也是前锋，谁先到射门点、谁先起脚，谁就占优。双方 0 扑救、合计 13 球，说明球门两角的射门基本无法被单门将覆盖；我方虽然控球时间是对手的近 15 倍，但只多输了 1 个球，胜负发生在最后一两次终结上。

## 3. 我的改动

所有策略改动都在 `brain.py`；`agent.py`、`soccer.py` 的协议与引擎复刻未改，诊断脚本在 `tools/` 下。下面按“针对第 1 轮哪个现象”列出。

### 3.1 1v1 门将：从“站线”改为“预测球门线交点”（`brain.py:299`, `brain.py:724`）

新增 `keeper_goal_target`：当球是高速自由球/飞行中、且门将来不及在中场拦截时，沿 `ball_path` 找球到达“球门线前 1.9 格”时的 `y` 坐标，把门将移动到该预测交点，而不是站在“球—球门中心”连线的固定比例位置。该逻辑只在 `n == 1` 时启用；`n >= 2` 继续使用原来的 `keeper_line_target`。

```python
# brain.py:299 附近
def keeper_goal_target(self, ku, w, path, f):
    gx = self.gx_def if ku['team'] == self.team else self.gx_att
    s = 1 if ku['team'] == 0 else -1
    kx = gx + s * 1.9
    ycross = None
    for p in path[f:]:
        if (p['x'] - gx) * s <= 1.9:
            ycross = p['y']
            break
    ...
    return (kx, ycross)
```

在 `solo_decide` 中又区分了两种情况（`brain.py:733` 附近）：

- 对手**持球**时，自由球路径是静止的，预测没有意义，改用 `keeper_line_target` 封角度；
- 球**无人控制**、速度达到门将扑救阈值（4.5）且我们来不及在本方禁区前拦截时，才用 `keeper_goal_target` 追预测交点；慢速球或能先抢到的球仍然去抢。

**针对**：r1-g2 双方 0 扑救、13 个进球；原有 1v1 门将只按连线比例站位，对角度射门的两侧门柱覆盖不足。

### 3.2 射门目标从 7 个点扩到 9 个点（`brain.py:371`）

```python
SHOT_YS = (10.70, 11.25, 11.90, 12.50, 13.00, 13.50, 14.10, 14.75, 15.30)
```

球门口约为 `y ∈ [10.5, 15.5]`；9 个目标点覆盖两个门柱内侧和中间，`pick_shot_target` 仍按“预测清空度 - 飞行帧数惩罚 - 偏离中心惩罚”选点。

**针对**：r1-g1 我方 25 脚只有至少 2 脚射正，射门目标过粗、可预测。

### 3.3 1v1 只在前两帧允许起脚（`brain.py:516` 附近）

```python
if late_lead:
    min_clear = 0.55
elif self.n == 1:
    min_clear = 0.12 if f <= 1 else 1e9
else:
    min_clear = 0.18
```

1v1 中，窗口后段的射门是基于“窗口开始时的对手位置 + 固定追球模型”推演的；真实对手在窗口内已经移动，计划到后面的射门经常在起脚后被对手处理。自测事件序列里多次出现“我方从 `x≈21` 起脚、随后很快出现对手踢球”的情况（被记为 `cleared`），说明开环推演高估了后段窗口的射门线路。现在 1v1 只允许 `f <= 1`（窗口最开始两帧）的射门通过阈值，并允许较低清空度 0.12；`f >= 2` 的候选即使评估出线路，也会被 `1e9` 阈值否决。`n >= 2` 仍保持 0.18、每帧可起脚。

**针对**：r1-g2 的高节奏对攻中，后段窗口的无效起脚；以及 r1-g1 中大量“看起来有线路、起脚即被封”的踢球。

### 3.4 2v2 射门口袋与带球目标（`brain.py:548`, `brain.py:573`）

新增 `shooting_pocket`：目标点在球门线前约 16.5 格（team 0 约为 `x≈26.5`，team 1 约为 `x≈16.5`），并根据最近防守者的 `y` 选择远离他的一侧（`y≈8` 或 `18`）；如果该口袋被占，就滑到另一侧。`dribble_target` 让持球者朝这个口袋推进；被贴身时先向远离对手的一侧转身，再继续向前。

**依据**：自建射门实验中，旧的边路点（team 0 约 `x≈31, y≈4.6/21.4`）会被线型门将完全覆盖；而距门线约 16.5 格的口袋（`x≈26.5, y≈8/18`）能打出未被门将覆盖的远角。若最近防守者恰好在中线 `y = 13`，目标侧按队伍翻转（team 0 去 `y=8`、team 1 去 `y=18`），避免策略在 180° 旋转下不对称。

### 3.5 2v2 接应点与门将出球（`brain.py:680`, `brain.py:438`, `brain.py:398`）

- 当门将持球且 `n >= 2` 时，第一名接应球员跑到 `shooting_pocket`，而不是只站在球前方 10 格；
- 门将找队友的出球距离上限设为 **26 格**（`if d > 26 or d < 3: continue`），避免远端接应点被忽略后只能大脚；
- 门将持球且已经离开本方禁区时，直接走 `owner_decide` 的进攻逻辑，而不是无条件开大脚。

**针对**：r1-g1 中大量控球但缺乏前场接应和二点球；门将拿球后的推进被浪费。

### 3.6 试过但撤回的改动

这些改动在自测中变差或造成死锁，已撤回；列出来是为了说明当前版本不是“只加不改”：

| 实验 | 结果 | 撤回原因 |
|---|---|---|
| 把速度感知门将用于 `n >= 2` | 0:6，扑救从 11–17 降到 1–4 | 会提前承诺一侧，被会挑角的射手打另一侧 |
| 门将持球不出、只等队友接应 | 0:1–0:2，踢球数明显下降 | 进攻停滞，反而不如直接出球 |
| 门将前压参与进攻 | 0:3–0:4 | 身后球门完全暴露 |
| `escape_kick` 自助式摆脱（自己踢球再追） | 对 Sniper 10:1，但 1v1 自对弈变成 1:3 / 3:1 | 破坏自对弈平衡，低比分下不稳定 |
| 把“只在前两帧射门”推广到所有人数 | `n=2` 0:4，且几乎不射门 | 2v2 持球者在窗口开始时就常被盯防，过早禁止后段射门等于放弃进攻 |
| 把 2v2 最大射门距离从 23.5 缩到 20 | 自对弈 0:0（0 踢球），对 Sniper 0:3 | 持球者到不了新的射门条件，带球循环死锁；已恢复 23.5 |

## 4. 改动后的自测结果

以下全部是**自测**，不是正式比赛；代理对手不是 `sol`，不能据此声称能赢 `sol`。

### 4.1 引擎与协议

- `soccer.py` 与真实 `simulation.js` 的逐帧对照：17 条轨迹、1520 帧，位置/速度/比分/计时在 `1e-9` 容差下 0 处不一致（这是之前的复刻验证，本轮未改动引擎）。
- 真实引擎 + 常驻 `agent.py` 进程（seed 1，自对弈）：
  - `n=1`：4:6，120 窗口，非法输入 0，多次运行最坏 31–111 ms，平均 5.9–6.2 ms/次；
  - `n=2`：1:0，120 窗口，非法输入 0，最坏 38–39 ms，平均 4.5–4.7 ms/次。
- 进程内规划最慢窗口 41 ms；真实引擎端到端偶发 111 ms（进程间通信/调度噪声），仍远低于 5 秒协议限制和 2 秒软截止。

### 4.3 怎么读这些数字

- **1v1 对 Sniper 的 10:2** 说明“见门就射”型对手会把球门留给反击，我方的新射门口袋和早射规则能利用这一点；但这不是对 `sol` 的证据，`sol` 在 r1-g2 的 7 个进球说明它的终结更强。
- **1v1 自对弈仍是 10 球/场**：1v1 球门 6 格宽、门将扑救半径 1.35 格，16.5 格外的射门在一个 20 帧窗口内到达，门将无法同时覆盖两个角；这是结构性问题。另外，6 场自对弈里 team 0 座位三场都是 4:6、team 1 座位三场都是 6:4，说明当前 1v1 策略或引擎朝向存在固定偏差，不能把自对弈总分当作强度结论；下一轮应先用镜像测试定位它。
- **速度感知分支确实在跑，但没有改变比分**：对 Sniper 和自对弈分别统计到每场 43 次和 84 次 `keeper_goal_target` 调用，启用前后的比分相同（对 Sniper 10:2，自对弈 4:6/6:4）。这说明当前 1v1 的主要失球不是“门将追不到已经飞行的球”，而是对手起脚前门将的位置选择；下一轮应把重点放在起脚前的站位/逼抢，而不是继续微调飞行球预测。
- **2v2 对 Sniper 6 场 0 进球**：这是本轮最明确的未解决问题。公开 r1-g1 是 25 脚、可确认 2 脚射正，自测代理下是 34–36 脚、按起脚方向 5–8 脚射正、0 进球，模式相同——控球和射门数量有了，最后一传/最后一脚的质量没有。
- **2v2 自对弈每场 1 球**：双方门将和低位防守都把比赛压得很死，进攻端缺少禁区前的配合；这不是“防守变好”，而是双方都缺少稳定的终结手段。
- 真实引擎 seed 1 的 `n=1` 4:6、`n=2` 1:0 与 Python 复刻完全一致，说明协议和引擎复刻没有在最后改动中跑偏。

## 5. 已知局限

1. **2v2 最后一传仍缺失。** 自测日志里 `pick_pass` 几乎不触发，踢球几乎全是射门或解围；接应点虽然跑到了口袋，但没有形成“传球—一脚—射门”的连续配合。下一步应优先放宽传球线路判定、增加撞墙式二过一，而不是继续调门将或单纯缩小射门距离（缩小到 20 已实测会死锁）。
2. **1v1 防守是结构性的。** 球门宽 6 格、门将扑救半径 1.35 格；对手在 16.5 格口袋起脚时，球在一个窗口内就到门前，门将无法在起脚后反应。现有改动只能改善对飞行球的预测，不能覆盖两个角。
3. **开环预测仍会漂移。** 每个窗口只观察一次，后段的对手位置是固定模型推演的；1v1 已通过“只在前两帧射门”规避最严重的起脚被封，但 2v2 仍会出现计划线路在起脚帧消失的情况。
4. **代理对手与 `sol` 不同。** SniperBot 会大量犯规（43–45 次/场），ChaseBot 只会追球；它们只能复现“见门就射/追球”的某一面，不能复现 `sol` 在 r1-g1 的 13 脚全射正和 r1-g2 的 7 球效率。
5. **公开战报没有逐脚射门数据。** 本文的“射正”是由 `goals + saves` 反推的可确认下限；r1-g1 中 `sol` 的 13 脚能精确对应 12 扑 + 1 球，r1-g2 只能确定“至少有 6/7 脚进球”，无法给出双方精确射正数、射门坐标和射门时间。
6. **`duration` 单位未注明。** 本文按帧数计算模拟时间（2400 步 = 120.00 秒；含起始帧 2401/20 = 120.05 秒），不把 1.22/1.17 当作模拟秒数。
7. **自对弈不是强度排名。** 同一套代码的左右朝向、数组顺序和确定性碰撞会让同种子比赛出现固定的胜负模式；表中自对弈数字只用于回归对比，不能说明“真实比赛一定五五开”。

## 7. 下一步

1. **优先做 2v2 的最后一传**：当前 `pick_pass` 几乎不触发，先解决“持球者被盯防时把球送到口袋接应点”的问题，再谈射门选择。
2. **把射门距离限制和传球组合一起做**：单纯把最大射门距离从 23.5 缩到 20 会死锁（实测 0 踢球），正确做法是“远距离只有高清空度才射，否则传给口袋”，而不是一刀切。
3. **1v1 继续压缩对手的起脚空间**：与其让门将事后追预测交点，不如在对手进入 16.5 格口袋前逼他向外线走，或迫使他用低质量的中路射门。
4. **用真实引擎多跑种子**：目前真实引擎只回归了 seed 1 的 1v1/2v2 各一场；下一轮应在更多 seed 上确认协议、比分和规划耗时，避免只对 Python 复刻过拟合。
