# 3V3 足球参赛复盘（赛前版）

> 说明：截至本文件撰写时，正式比赛尚未开始，**没有任何正式对局结果**，因此本文不含、也不编造赛后复盘。下面记录的是我实际采用的策略、可复现的自测数据与已知局限。

## 1. 交付物

- `entry.json`：`{"mode":"program","command":["python3","agent.py"]}`
- `agent.py`：逐行读取 JSON 观察、逐行输出一个 20 帧窗口的决策；对每帧做结构与取值校验，异常时降级为合法动作，保证不输出非法输入。
- `soccer.py`：按公开的 `simulation.js` / `catalog.js` 逐条复刻的 Python 前向模型（含移动、分离、控球、传球/射门、门将扑救、犯规、进球、开球、半场与金球时钟）。
- `brain.py`：策略本体。
- `tools/`：自测脚本（真实引擎协议对局、镜像对称、精确性对比、自对弈矩阵等）。
- 未修改 `RULES.md`、`GAME.md`、`simulation.js`、`catalog.js`、`example.json`；未读取任何对手文件；`canary.txt` 未改动。

## 2. 实际采用的策略

### 2.1 决策框架：1 Hz 开环推演
服务端每 20 帧才收一次输入，窗口内双方都无法反应。因此 agent 在每个窗口开始时：
1. 用 `world_from_obs` 由公开观察重建世界；
2. 用 `apply_history` 从事件流恢复观察中被隐藏的 `stealLock`/`foulLock` 与开球方（观察只给出 `kickCd`、`controlLock`）；
3. 用 `soccer.py` 克隆世界，对 20 帧逐帧推演自己的行动，同时用一个固定脚本模拟对手的 20 帧；
4. 一次性输出全部 20 帧。

射门/传球都安排在窗口靠前的帧，利用“对手在窗口内不能改主意”这一点。

### 2.2 角色分工（n ≥ 2）
- **门将（index 0）**：站在本方球门线前 2.6 格，按预测的球 y 坐标横向移动；只有在本方禁区内、球速 ≥ 4.5 时才享受 1.35 的扑救半径。领先进入尾盘时留在本方禁区深处持球。
- **场上球员**：按到球的距离排名。最近的去逼抢/争抢落点；其余球员按名次站到“球—本方球门”连线的保护位置，或前插到前场边路做接应点。
- **进攻**：持球者优先在 23.5 格内寻找射门线路（在 7 个球门目标点中选对预测对手清空度最大的一个，普通情况要求净空 ≥ 0.18，领先尾盘要求 ≥ 0.55）；无射门机会则找向前、无人盯防、传球线路干净的队友；只有在己方后场深处且身边 2.2 格内有两名以上对手时才大脚解围；否则带球，沿边路（y≈4.6 或 21.4）推进，被贴身时向远离对手的一侧转身护球。
- **护球机制**：球在持球者身前 0.62 格，抢断要求抢球者到球 < 0.82 且比持球者近 0.12 以上，所以背身拉开距离时对手从身后无法抢断。

### 2.3 犯规管理（本次最后一项改动）
规则规定“任何单位进入对方禁区即犯规”。因此：
- 所有目标点经 `safe_target` 处理，与对方禁区保持 `BOX_MARGIN = 0.55` 的清空距离；
- `choose_dir` 在候选移动中禁止“离对方禁区更近”的落点（已经贴近时允许平行移动和向外撤离，避免卡死）；
- 本方禁区是安全的，门将和回传球可以主动利用；
- 这一改动把自对弈 18 场中的犯规从约 18 次降到 6 次（剩余均为碰撞把人推入禁区，且多为对方犯规）。

### 2.4 比分管理
领先且剩余时间 < 32 秒（或金球阶段）时：
- 有球队员优先把球回传给位于本方禁区的门将；
- 门将持球待在本方禁区深处。对手若进禁区抢球就是犯规，因此这段持球实际不可被抢断，用来消耗时间。

### 2.5 1v1（n = 1）
单人模式没有独立的门将，采用专门逻辑：对手持球且接近本方球门时回到门将线；否则按球的未来轨迹做拦截；自己持球时能射则射，否则带球推进。

### 2.6 健壮性
- 规划使用单调时钟，软截止 2.0 秒；超时后剩余帧用“全体向球移动、持球者朝球门”的兜底脚本填满；
- 输出前校验 `20 × teamSize` 的形状与方向/角度取值，非法值被清洗；
- 坏 JSON 输出 20 帧中立动作；
- 正常规划耗时：单窗口最坏 26–39 ms（进程内测量），远低于 5 秒限制。

## 3. 自测结果（均可复现）

### 3.1 引擎复刻的精确性
用真实 `simulation.js` 录制的 17 条轨迹（9 个场景轨迹 + 8 条对局片段，共 1520 帧；涵盖犯规进场、门线进球、进球后开球、半场、扑救、1v1 争抢、抢断、撞墙反弹、边路射门）逐帧对比，位置/速度/比分/计时/隐藏计数全部一致，**容差 1e-9 下 0 处不一致**。另外早期对 `circle_hits_wall` 做过 30 万组随机点/半径的对照，0 处不一致。

复现：`for f in tools/scen/*.trace.json tools/trace1.json tools/t_*.json tools/c1.json; do python3 tools/py_check.py $f; done`

### 3.2 左右镜像对称

两种驱动方式：(a) 每个窗口新起一个 `python3 agent.py`；(b) 每个队伍一个常驻进程，逐行问答。

## 4. 已知局限与风险

1. **窗口内无反应**：20 帧是开环的，对手在窗口内的真实动作与我方固定脚本模型不同，预测会漂移。0.55 的禁区清空距离是对漂移的补偿，但不能完全避免被碰撞推入禁区（实测真实引擎每场 0–1 次犯规）。
2. **观察有量化误差**：坐标/速度保留 3 位小数，`freeze` 与金球剩余时间保留 0.1 秒；`stealLock`/`foulLock` 只能由事件流按帧龄恢复，边界上可能差 1 帧。
3. **对手模型很粗**：对手被假设为“追球、持球者推进、门将守线”，遇到专门设计的强队（例如大量横传调度、专打我方边路身后）时，我方前场逼抢可能被绕过。没有做任何对手侦察（规则也不允许）。
4. **主机停顿**：WSL2 上偶发约 3.2 秒的停顿，实测发生在“每窗口新起 Python 进程”的驱动方式下的启动阶段，而非规划本身（同一观察的回放规划仅 2 ms）。若服务端复用常驻进程，这一风险基本消失；规划阶段的 2.0 秒软截止只是额外保险。代价是：一旦停顿触发兜底，该窗口之后的对局轨迹会与无停顿运行分叉（同一 seed 的自对弈曾因此出现不同比分）；这是用时间截止换取 5 秒保证的取舍。若停顿超过约 4.5 秒仍可能超出 5 秒限制，这是运行环境问题，代码无法完全消除。
5. **自对弈与真实协议结果可能不同**：自对弈直接使用真值状态，真实协议使用量化观察 + 隐藏状态恢复，混沌系统会放大这点差异（例如 n=5/seed 5：Python 自对弈 2:1，真实引擎 1:1）。以真实引擎端到端结果为准。
6. **1v1 偏弱**：对 ChaseBot 12 战全胜但每场失约 1 球；对同等水平的对手基本是五五开（6:7 金球）。1v1 没有独立门将，进攻投入与防守覆盖很难同时兼顾。
7. **尾盘持球依赖犯规规则**：领先时把球带回本方禁区消耗时间，合法性来自“对手进禁区即犯规”。若赛事组织方对消极比赛有额外判罚，这一战术需要放弃；代码中的触发条件很窄（领先且 <32 秒/金球），不影响正常时段。
8. **金球阶段没有专门加强进攻**：仍按常规策略踢，20 秒内可能以平局收场（真实引擎 seed 5 即为 1:1 平局）。

## 5. 结论

当前版本已完成：精确前向模型、1 Hz 开环规划、角色分工、射门/传球选择、禁犯规边界、尾盘控球、异常兜底与协议校验。自测中对基准对手 72 战全胜（321:12），自对弈完全均衡，真实引擎协议下零非法输入、响应时间满足要求。正式比赛尚未进行，赛后如有对局再补充复盘。
