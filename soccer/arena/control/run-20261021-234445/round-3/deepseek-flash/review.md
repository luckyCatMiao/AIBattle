# 3V3 足球第 3 轮：策略、自测与局限（赛前版）

> 本文是第 3 轮开赛前写的策略与自测报告，不是赛后复盘。写作时 `public_results.json` 为空，第 3 轮没有已公布的对局；因此本文不含任何第 3 轮的比分、进球、扑救、控球或比赛过程。赛后另写 `postmatch.md`。文中所有自测数字都来自本仓库脚本，对手不是 `sol`，不能当作对 `sol` 的强度预测。

## 0. 摘要

- **入口不变**：`entry.json` 仍是 `{"mode":"program","command":["python3","agent.py"]}`；比赛实际运行 `agent.py → planner.Brain2`。
- **第 2 轮的公开结果**（仅作背景）：1 胜 1 平，进 2 失 0；3v3 2:0 胜，5v5 0:0 金球未分胜负；控球占比 77.97%，但 5v5 的 69 脚踢球只迫使对方门将扑救 2 次，0 进球。结论是“防守合格、进攻转化不足”，第 3 轮只针对最后一脚做增量改动。
- **本轮新增两个进攻机制**：
  1. **松球一触**（`add_onetouch`）：窗口开始时球是自由球时，用真实球路模拟本窗口内谁会拿到球；若我方单位在进攻半场拿到，就把它的动作改成“拿球后下一帧直接起脚”。
  2. **传球一触 / 窗口内组合**（`add_combo`）：我方持球者的脚本是传球时，模拟这次传球在本窗口内的球路；若短传能在窗口内到达、接球点射门余量足够，就把接球者改成“接球后下一帧直接起脚”。
- **机制依据**（读 `simulation.js`）：`controlLock` 只在起脚时设置为 6 帧（`simulation.js:249-250`），**获得控球不会设置**（`simulation.js:344-358`）。所以接球后的下一帧起脚是合法的。双方每 1 秒同时锁定 20 帧输入，门将和防守在窗口内无法对这次传球/拿球重新决策，这就是组合的收益来源。
- **真实引擎匹配对照**（对手 = 自建旧版 `Brain`，同一 seed/n/座位，只切换 `PLAN_ONETOUCH`）：n=3/5 的 8 场从 **8:1** 提升到 **13:0**；n=1/2/4/6 的 16 场两种设置都是 **27:6**。合计 24 场：**35:7 → 40:6**，进球 +5、失球 −1。胜负从 20 胜 3 平 1 负变为 22 胜 2 平 0 负。
- **协议与性能**：用真实入口 `agent.py` 跑 6 个人数的整场，`illegal=0`；独立运行时单窗口最坏 53 ms、平均 3.7–11.4 ms；两个整场并发时出现过一次 2.89 s 的 CPU 争用尖峰，仍低于 5 s 上限。`agent.py` 另有 2.5 s `SIGALRM` 看门狗和中性帧兜底。

## 1. 入口、协议与运行约束

- 服务端 20 Hz；每 1 秒提交一次 20 帧 × `teamSize` 的输入，双方同时提交。
- 程序从 stdin 每行读一个观察 JSON，向 stdout 每行写一个 `{"inputs": [...]}`，每行后 flush；调试信息只写 stderr。
- 单次响应硬上限 5 秒；目录/字段非法按技术负处理；不足 20 帧的部分由引擎按中性输入补齐。
- `agent.py` 的处理链：
  - 解析 JSON；`teamSize` 缺省时沿用上一次的值；`yourTeam` 决定 `Brain2` 的队伍；
  - `world_from_obs` 构造世界，`timed_plan` 在 2.5 s 的 `SIGALRM` 下调用 `Brain2.plan`；
  - 校验 20 帧 × `teamSize` 的形状，`aim` 统一 `% 360`，`dir` 缺省为 `N`；
  - 任何异常先尝试 `_fallback_frame`（追球/护球），再退化为全 `N` 中性帧。
- 自测确认：非法 JSON、`{}`、`teamSize=0` 都会输出 20×3 的合法中性帧（见 §4.4）。

## 2. 与本轮改动直接相关的机制

以下都来自公开的 `simulation.js` / `catalog.js`，没有读取对手代码。

### 2.1 帧内顺序

每个物理帧的顺序是：冻结检查 → 所有单位 `updateUnit`（先递减 `kickCd`/`controlLock`/`stealLock`/`foulLock`，再用输入设置朝向、移动、踢球）→ `separateUnits` → `checkFouls` → `updateBall`（4 个子步 + 摩擦 + `tryPossession`）→ 控球统计 → 时钟。

由此得到两件事：

- 第 k 帧能否踢球，取决于该帧 `updateUnit` 递减后的 `kickCd` 和 `controlLock`：`inp.kick && owner==u && kickCd<=0 && controlLock<=0`（`simulation.js:232`）。
- 控球是在 `updateBall` 末尾判定的；如果单位在第 t 帧末尾拿到球，第 t+1 帧的 `updateUnit` 里 `controlLock` 本来就是 0，可以直接踢。

### 2.2 控球权

- 自由球：`tryPossession` 取 0.82 格内最近的合法单位；开球方在等距 0.06 格内有偏好（`simulation.js:344-358`）。
- 持球被断：抢断者必须在球 0.82 格内，且到球距离 +0.12 小于持球者到球距离（持球者通常 0.62），也就是抢断者要离球 <0.50。
- 获得控球**不设置** `controlLock`；抢断成功时被断者获得 `stealLock`，抢断者不获得锁。只有起脚才设置 `kickCd=7`、`controlLock=6`。

这是本轮“一触”合法的直接依据。

### 2.3 门将、禁区与射门

- 门将扑救：球速 ≥ 4.5、球和门将都在门将本方禁区内、距离 < 1.35 格时没收（`simulation.js:327-341`）。
- 禁区犯规：任意单位进入对方禁区即犯规，冻结 0.6 s、1 s 僵直，球放到最近的禁区外点（外扩 0.9 格）。
- 球门：球心 x≤1（team1 得分）或 x≥43（team0 得分）且 y∈[10.5,15.5]；几乎平行于门线的射门会先撞墙。
- 因此所有射门点必须留在对方禁区外；本轮 `BOX_MARGIN=0.62` 不变。

### 2.4 确定性与种子

引擎没有随机数。给定 `teamSize` 后，种子只决定 `kickoffTeam = abs(seed) % 2`，所以同一对阵只有 6 种人数 × 2 种开球方 = 12 种不同对局；`seed=1` 与 `seed=101` 完全等价，`seed=1` 与 `seed=3` 在开球方上也等价。本文的自测因此把重复种子的结果并列展示，但不会把它们当成独立样本。

## 3. 采用的策略

### 3.1 基础决策器（沿用第 2 轮的 `Brain2`）

- **观测锚定**：每个窗口以观察到的状态为锚点；我方单位的移动用 8 方向逐帧精确投影（`project`），但不把对手引发的持球/犯规事件写回自己的目标。
- **对手预测**：用相邻 1 Hz 观测的差分估计对手速度，剔除瞬移（>1.15×最大速度），按 0.75 阻尼外推到窗口内各帧（`update_vel` / `opp_pos_at`）。
- **射门模型**：对 12 个门线目标点（10.85…15.15）用真实球路（含墙反弹）评估；对手按外推位置、门将按 1.35 格扑救半径，并给门将 0.42 秒反应余量（`eval_shot` / `pick_shot`）。只有余量 > 0.06 的目标才进入候选。
- **踢球时机**：优先第 0 帧起脚；合法性用 `k ≥ max(kickCd, controlLock) − 1` 判断（因为该帧先递减再检查）。
- **禁区纪律**：所有移动/射门目标都离对方禁区至少 0.62 格；投影射门点时进入禁区 0.45 格内就停止该分支。
- **无球分工**（n≥2）：index 0 是门将；其余单位按到球距离排序，最近者贴防（在持球者与我方球门连线上、持球者球门侧约 0.75 格），其他人覆盖“球→本方球门”的线路；n=5 时贴防只在对手距我方球门 <16 格时启用，避免失去宽度。
- **持球**：朝远离最近对手的方向护球；有合适射门就射，没有就找有推进、有开放度、球道干净的传球；被压死时解围；门将持球优先安全出球。

### 3.2 新增一：松球一触（`planner.py:802`）

触发条件与流程：

1. 只在窗口开始时 `ball.owner is None` 时启用。
2. 用 `free_ball_path` 模拟球的真实自由飞行（4 子步、墙反弹、每帧 0.978 摩擦）。
3. 用 `_move_frames` 模拟我方每个单位按当前动作目标的逐帧位置；对手用 `opp_pos_at` 外推。
4. 逐帧判定：
   - 若球速 ≥4.5 且会进入对方门将的 1.35 格扑救范围，停止；
   - 否则按 0.82 格最近合法单位判定谁拿球，并应用开球方 0.06 格偏好；
   - 若拿球者不是当前评估的单位，停止；
   - 若拿球点不在进攻半场，或已进入对方禁区（距离 <0.05），停止。
5. 若拿球者是我方单位，就在拿球帧的**下一帧**从它的位置评估射门（`pick_shot(..., t_offset=k)`，把对手外推时间对齐到起脚帧），余量 >0.10 才执行。
6. 把该单位的动作改成 `kick`（`still=True`, `hold_from=k`）：第 k 帧站定、朝向射门目标、起脚；k 之前的移动目标保持不变。

**为什么安全**：如果预测错了（球实际没到该单位脚下），引擎会忽略这次踢球输入（它并不持球），代价只是该帧少走一步；不会产生非法输入，也不会把球权白送。若对手先拿到球，预测在“拿球者不是该单位”处停止，不会触发。

**为什么有效**：拿球发生在窗口中间，对手的 20 帧输入已经锁定；门将/后卫无法在这一秒内重新决策。自测中它把旧版 Brain 的多次解围/松球变成了禁区外沿的近距离射门。

### 3.3 新增二：传球一触 / 窗口内组合（`planner.py:902`）

1. `decide_owner` 选择传球时，记录 `(传球者, 起脚帧 k, 角度, 接球者)`；`decide_keeper` 的出球也登记同样的信息。
2. `add_combo` 用 `project` 算出传球者在第 k+1 步的释放位置，再用 `ball_flight` 模拟这次传球（含墙反弹）。
3. 逐帧判定接球者：
   - 球到对方门将扑救范围就停止；
   - 按 0.82 格最近合法单位 + 开球方偏好判定；
   - 只有接球者是我方、且不是传球者、不是 n≥2 的门将才继续。
4. 若接球帧 f 的下一帧 f+1 仍在窗口内，就从接球者位置评估射门（`t_offset=f+1`），余量 >0.10 才执行。
5. 把接球者改成下一帧起脚（同样 `still=True`, `hold_from=f+1`），它在此之前的移动目标不变，所以传球的相遇点仍然成立。

**收益**：这是一次“传球—接球—起脚”都在同一个 20 帧窗口内完成的组合。门将看到的是传球前的状态，等球到接球者脚下时，它已经按旧脚本移动了 0.3–1 秒，射门角度因此更容易成立。

**风险控制**：传球被对手截断时，接球者不会获得控球，起脚输入被引擎忽略；组合只会在模型余量 >0.10 时启用。

### 3.5 防守与犯规纪律

本轮没有改防守结构。第 2 轮正式比赛的 0 犯规来自 `BOX_MARGIN`、`keep_out` 和“对手在对方禁区内持球时不去抢”的纪律；本轮所有新代码都在“我方将获得控球”或“我方正在传球”时触发，不会让无球防守者进入对方禁区。自测中我方犯规仍为 0 或 1 次/场，绝大多数为 0。

## 4. 自测：设置与结果

所有比分都来自公开 `simulation.js` + `catalog.js` 的真实引擎；Python 复刻 `soccer.py` 只用来构造观察，不用来判定 A/B。每场都是两个持久化 Python 进程通过 stdin/stdout 协议对接，和正式比赛的协议一致。

### 4.1 匹配对照：旧版 `Brain`，n=3 与 n=5

同一 seed、同一人数、同一座位，只切换 `PLAN_ONETOUCH`（0/1）。真实引擎是确定性的，所以同一行的差异只来自这个开关。

| 对局（seed / 人数 / 座位） | 关闭一触 | 开启一触 |
|---|---:|---:|
| seed1 n=3 座位0 | 1:0 | 1:0 |
| seed1 n=3 座位1 | 2:0 | 3:0 |
| seed2 n=3 座位0 | 2:0 | 3:0 |
| seed2 n=3 座位1 | 1:0 | 1:0 |
| seed1 n=5 座位0 | 0:1 | 1:0 |
| seed1 n=5 座位1 | 1:0 | 1:0 |
| seed2 n=5 座位0 | 1:0 | 1:0 |
| seed2 n=5 座位1 | 0:0 | 2:0 |
| **合计 8 场** | **8:1（6 胜 1 平 1 负）** | **13:0（8 胜）** |

最直接的变化：n=5 seed1 座位0 从 0:1 变成 1:0，n=5 seed2 座位1 从 0:0 变成 2:0；n=3 的两场从 2:0 变成 3:0。

### 4.2 匹配对照：n=1、2、4、6

同样的方法，16 场：

| 人数 | 关闭一触 | 开启一触 |
|---|---:|---:|
| n=1（4 场） | 10:6 | 10:6 |
| n=2（4 场） | 2:0（2 胜 2 平） | 2:0（2 胜 2 平） |
| n=4（4 场） | 9:0 | 7:0 |
| n=6（4 场） | 6:0 | 8:0 |
| **合计 16 场** | **27:6** | **27:6** |

- n=4 的进球从 9 降到 7（4 场里 3:0/3:0 变成 2:0/2:0），n=6 从 6 升到 8；合计不变。
- n=1 全部 6 个失球都出现在 1v1（4 场 2:1、3:2、3:2、2:1）。1v1 没有真正的门将体系，本身就是高比分对攻，一触对结果没有可见影响。

### 4.5 镜像与已知僵局

- 双方都用本轮最终策略时，n=5、n=6 的整场仍是 0:0（金球未分胜负），n=3 由开球方 1:0 决定。这是两套相同贴防/门将体系互相封死的结构性结果，第 2 轮的 5v5 0:0 也是同一模式。
- 因此本轮没有把“镜像能赢”当作目标；改进的目标是“对低控球、快速把球打到门前的对手多进一个”。自测代理里最接近这种风格的是旧版 Brain（每场 38–97 脚踢球），它也是一触收益最明显的对手。

## 5. 局限与风险

1. **自测对手不是 `sol`**。旧版 `Brain`、`Sniper`、`Chase` 都是本仓库自建脚本。旧版 Brain 每场踢 38–97 脚，远多于 `sol` 在第 2 轮 5v5 的 24 脚；所以“松球一触”在自测里的触发率可能高于正式比赛，不能把 35:7 → 40:6 直接外推为对 `sol` 的比分。
2. **组合的触发率不高**。一场窗口上限 400 的 n=5 自测里只有 3 次松球一触、2 次传球组合；它是“多出几次禁区外沿的近距离机会”，不是体系性压制。
3. **模型误差**。对手位置来自 1 Hz 差分 + 0.75 阻尼外推；门将的反应余量是常数 0.42 s。自测里出现过模型余量 1.06 的射门仍被扑出的情况，所以“余量 >0.10”不等于必进。一触的收益是概率性的。
4. **样本小且种子退化**。引擎无随机数，种子只决定开球方；n=3/5 的 8 场实际上只有 4 种不同对局。上表的胜平负不能做显著性推断。
5. **n=1 收益有限**。1v1 没有真正的门将/禁区体系，自测 4 场 10:6，结果高度依赖开球权。
6. **自测框架曾暴露一个实现错误**：传球元组扩展后，门将分支仍按 6 元组解包，导致部分窗口回退为中性帧。该错误已修复；最终 24 场匹配对照、6 个人数的真实入口点整场、Sniper/Chase 代理测试都没有再出现 worker 错误。这里保留记录，是为了说明自测确实在“跑起来”的层面做过校验，而不是只看比分。
7. **性能边界**。独立运行时单窗口最坏 53 ms；两个整场并发时出现过 2.89 s 的尖峰。正式比赛若与对手程序同机并发，仍建议依赖 `agent.py` 的 2.5 s 看门狗；超时会退化为安全的中性/追球帧，不会超时。
8. **没有第 3 轮正式数据**。本文不含任何第 3 轮赛后结论；金球、红黄牌（本引擎无）、加时等都没有可引用的正式事件。
