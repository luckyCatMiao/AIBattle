# 第 3 轮提交说明与赛前自测复盘

## 状态与证据范围

本文件记录第 3 轮实际提交程序及本轮准备期间已经执行的离线测试，**不是第 3 轮正式赛后战报**。目前没有本轮正式比赛结果，不编造正式比分、对手动作或胜率。原第 2 轮复盘已保留为 `review_round2.md`。本轮没有读取对方文件，没有修改规则、公开物理引擎、场地参数或示例观察，没有下载现成引擎。

## 提交与运行

`entry.json` 内容为：

```json
{"mode":"program","command":["python3","agent.py"]}
```

`agent.py` 定位自身目录后启动 Node.js 执行 `agent.js`。实际比赛依赖 `agent.js`、己方旧版 `agent_v2.js`，以及允许使用的 `simulation.js`、`catalog.js`。不需要网络、第三方包或工作区写权限。程序持续逐行读取 stdin，每条观察输出一行 JSON；stdout 只输出动作，异常写 stderr。

## 实际策略

### 1. 基础动作与人数适应

- 以观察中的 `teamSize` 为准，始终生成 20 帧、每帧恰好该人数的动作。
- 左右队使用统一进攻坐标。使用八方向移动与数值角度瞄准。
- 无主球根据摩擦与反弹预测路径，按到达时间分配追球人；其他队员承担接应、二点争抢与后场保护。
- 多人局保留 index 0 守门员；单人局沿用己方旧版攻防策略，没有人为固定留门导致无人进攻。

### 2. 新版持球与进攻候选

- 扫描实际有效进球高度附近的多个目标，计算球速衰减、预计到达时刻和对手拦截距离，显式考虑守门员快速球扑救半径。
- 新版策略取消“到禁区前就无条件起脚”；允许横移、寻找向前传球，以及从禁区上、下方的合法走廊前进后寻找斜射机会。
- 新版非持球分支不预先强制踢球，拿球后在后续预测帧重新判断。
- 新版门将在后场得球时优先寻找向前传球或解围，避免慢速长距离带球离开球门。
- 旧版快速射门仍是搜索候选，因此最终动作并非永远执行新版的保守起脚条件。

### 3. 有限多模型规划

每个真实观察重建公开模拟状态。对多人局生成 6 份候选一秒输入：

- 新版持球推进、旧版快攻、新版较靠前门将三种策略；
- 各在旧版、新版两种自写对手预测下分别生成。

每份候选固定执行前 20 帧，再在两个对手模型下推演到 60 帧。评价进失球、持球方、推进位置、压力、射门空间和无主球拦截时间。用较差模型得分与平均分的加权值选择候选，**只提交最初 20 帧**。后续 40 帧只用于离线评价，绝不声称在已提交窗口内收到真实新观察。

这不是完全 minimax，也不是对真实对手的已知建模。两种对手模型都是自己的程序，不涉及对方代码。

### 4. 禁区保护

移动候选排除对方禁区并保留边界距离，遇到矩形角点尝试绕行。生成输入时额外检查下一步与禁区的 0.6 格保护带，必要时向后或沿边界退让。此检查基于预测状态；真实对手导致的抢断、速度变化与碰撞仍可能使后续帧偏离，不能保证绝对零犯规。

## 本轮已运行的测试

所有比分均为离线公开引擎自测，不是正式比赛成绩。测试脚本与结果文件留在工作区。开发期间多次试验单一门将深度、射门门槛和对手预测；这些试验存在明显退步，未把中间版本的最好成绩冒充最终成绩。

### A. 最终版对己方旧版及逐帧反应旧版：24 场

运行：

```text
node test_round3.js 1,2,3,4,5,6 old,reactive-old
```

- 覆盖 1–6 人、两个座位、两类对手，每种人数固定种子 `71 + n`。
- `old` 为旧版按一秒窗口提交；`reactive-old` 则每个物理帧按真实状态重新计算动作，其信息反馈比正式比赛更及时，用作压力测试。
- 结果文件：`round3_tests.json`。
- **12 胜、4 平、8 负，进失球 62:47，己方犯规 0。**
- 实测最慢单次决策 **434.41 ms**，低于 5 秒上限；该数据是当前机器实测，不保证其他机器相同耗时。

四人局四场全负是明确弱点；六人局平局多，不能把零失球等同于进攻足够强。

### B. 最终版对两类独立自写逐帧反应基线：24 场

运行：`node test_baselines3.js`。

- 全部人数、两个座位，固定种子 `103 + n`。
- 一类带固定门将并瞄准远角；另一类带门将、单主追球人与展开接应。
- 基线每个物理帧重新计算，己方仍只能按一秒窗口行动。
- 结果文件：`round3_baselines.json`。
- **18 胜、3 平、3 负，进失球 84:19，己方累计犯规 4 次。**
- 最慢单次决策 **328.04 ms**。

犯规真实发生，不能以单步边界测试通过为由宣称完整对抗零犯规。两人局对远角基线两场均负，三人局也有一场对展开基线失利。

### C. 协议、边界与冻结测试

运行：`node test_protocol.js`。

- 1–6 人、两个座位、开场/禁区边缘持球/高速来球/冻结四种状态，共 **48 项**。
- 全部通过公开引擎输入校验；检查 20 帧宽度、合法方向、有限数值角度，模拟窗口内己方均无犯规。
- 最终执行批次最慢 **42.77 ms**。

此外，实际通过 `python3 agent.py` 持续进程协议发送示例观察三次，座位为 0、1、0，三次均输出合法完整窗口，耗时约 **106.6、41.5、30.8 ms**（首条包含启动）。`node --check` 通过，`entry.json` 内容校验通过。

### D. 其他开发测试的口径

还实际运行了中间候选版本在另一组种子上的三人、五人逐帧旧版压力测试，结果保存在 `round3_extra_seeds.json`。这批测试发生在最终边界保护调整之前，**不算最终版本跨种子验证**。不将其与上面 48 场最终完整对抗混合统计。

## 已知局限

1. 对手预测仍来自自己的两种启发式策略，真实对手可能采取完全不同的传球、持球和守门方式。对自身旧版的改进不等于对正式对手的改进。
2. 最终版完整比赛仅每个人数一组种子；固定种子与左右座位相关，不能据此估计普遍胜率。尤其四人局与两人远角基线暴露出明显失利。
3. 三秒搜索时域有限，评价函数可能偏好短期球权或安全位置，漏掉长期协作与门将调动；六人局进球少。
4. 路径启发式采用近似反弹与可达范围；候选执行用公开精确引擎，但敌方输入不确定，因此真实后续位置依然可能偏离。
5. 几何避禁区只能降低风险。完整基线测试仍有 4 次犯规，已如实记录；不能宣称安全带解决所有碰撞和窗口误差。
6. 观察没有直接提供全部内部锁定值；程序用公开事件重建犯规、抢断锁，仍可能有边界误差。
7. `kicks` 包含射门、传球和解围，本文件不把它等同于射门或射正，也不虚构射门转化率。
