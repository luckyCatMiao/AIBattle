# 第 2 轮提交：策略与离线验证

## 范围与提交

正式入口：`entry.json`，内容为 `{"mode":"program","command":["python3","agent.py"]}`。程序持续接收 stdin JSON 行，按购买/比赛阶段输出一行 JSON 并立即 flush；不访问网络、不写运行时文件，适用于只读工作区。

本文记录本次准备阶段实际完成的修改与测试，**不是第 2 轮正式比赛复盘**，尚无本次提交的正式对局结果。工作区原有 `review.md` 已保留为 `review_prior_round.md`；它与当前公开战报的描述存在不一致，因此本次不把旧复盘的比分或推测当作已核实事实，也不据此宣称正式胜率。旧控制器备份为 `round1_agent.py`。

## 实际采用的策略

### 购买

- 低护甲时优先花 $650 补甲，随后依据余额将手枪/低价枪升级为微型冲锋枪、冲锋枪或步枪。
- 保留已有较好武器；防守方有剩余资金则购买拆弹器。
- 每人独立计算预算。源码按武器、护甲、拆弹器顺序执行购买，所输出条目的合计支出不超过对应人的余额。
- 不采用狙击枪主力配置：观察视距短且实体子弹需要飞行，偏好持续火力与护甲。

### 寻路与任务

- 按静态地图建立禁止穿越墙角的八邻接图，用缓存的 Dijkstra 距离场推进；逐帧模拟半径 0.3 的角色碰撞，以及先 X 后 Y 的墙边滑动。
- 路径平滑使用圆形角色净空检查。本次增加了近路径点的下一格衔接，减少离格转角处反复靠近同一中心点的风险。不是完整的停滞监控器，不能声称已覆盖所有地图卡位。
- 进攻根据种子与回合选择 A/B，携包者和队伍集中推进；掉包后前往拾取。携包者进入合法包点后立即在剩余预测帧保持静止，连续静止完成下包。
- 防守初始三人偏 A、两人偏 B；得到短时接触情报后靠拢。下包后按路径距离和拆弹器选择拆弹者，进入 0.85 格内即停止，其他单位靠近掩护。

### 守包改动

旧控制器使用炸弹附近固定偏移，坐标可能被墙体阻隔。本次从可达空格中选择距炸弹约 1.8–5 格且有直接视线的位置；对岗位之间过近加入代价，优先保持可干预拆包的分散部署。战斗移动评分也惩罚离开炸弹视线。

这只是静态视线约束，不保证任何时刻都能击杀拆弹者；墙角、弹道时间、朝向与敌方火力仍会影响防拆。

### 战斗与信息

- 输入始终是 20 帧 × 5 人的合法方向对象，瞄准和移动独立。
- 仅利用观察中的敌人、己方可见子弹和短时记忆。队伍间的接触信息用于寻路及朝向，不读取隐藏敌人状态。
- 根据连续观察估算敌人位移和弹道；缺乏弹道历史时采用来源推测。逐帧在九种移动方向中，综合任务推进、横向移动、已见子弹及预测火力风险评分。
- 敌人在视线内时瞄准最近威胁，否则面向推进方向、接触位置或炸弹周边。
- 公开源码 `canFire` 未应用 8 格观察视距，自动开火可能早于 `visibleEnemies` 报告敌人。本程序不因此假设全图真视，也不能手动禁止自动射击；测试直接使用未修改的公开引擎。

## 实际自测

所有对局使用原始 `simulation.js` 与 `catalog.js`；没有更改受保护资料，没有读取对手文件。结果文件均为本次真实运行产物。

### 1. 改动前与首批验证

- `round2_before.json`：9 场旧版衍生模式对抗，6 胜、3 平、0 负。此组主要确认原有控制器可正常执行，不作为独立强对手评估。
- `round2_initial.jsonl`：15 场，15 胜、0 平、0 负。种子 17、42、109，分别对左路进攻、右路进攻、中路突进、中央火力与冻结旧版。
- 首批验证后，又增加窗口中途进入下包/拆包范围即停止，以及守包移动的视线惩罚；以下主矩阵为这些修改之后运行。

### 2. 主矩阵：45 场完整比赛

运行命令：

```sh
node arena_r2.js 1,2,3,7,12,25,101,202,303 old,left,right,turret,sniper
```

结果见 `round2_matrix.jsonl`：

- **38 胜、7 平、0 负**，合计 196 回合；没有时间到回合，没有协议错误或响应超时。
- 各种子按奇偶切换我方席位；每场正常进行半场换边、经济重置和 4 胜结束判定。
- 平局：旧版在种子 2、7、101；left 在种子 3；right 在种子 7；turret 和 sniper 在种子 3。
- 本机记录的最慢单次响应约 **81.1 毫秒**，统计包括双方控制器，不等同于裁判机性能保证。
- `opponent_r2.py` 使用单独指定的推进、长周期横移和武器优先购买逻辑，但复用了冻结旧版的导航层。它不是完全独立实现，更不代表正式对手强度。`sniper` 只在资金允许时购买狙击枪，不保证每局都持有。

### 3. 专项场景：24/24 通过

运行 `node scenarios_r2.js`，结果为 `round2_scenarios_final.jsonl`。种子为 1、2、7、17、42、101、202、303：

| 场景 | 通过 | 观察到的结果 |
|---|---:|---|
| 无近距离敌人干扰的出生点推进下包 | 8/8 | 13–14 个决策窗口内下包 |
| 从防守出生区回防已下炸弹，携带拆弹器 | 8/8 | 9 个窗口内完成拆除 |
| 两名步枪护甲守包者对一名护甲拆弹器进攻者 | 8/8 | 均在首个窗口全灭防守方，阻止拆除 |

场景控制使用准备期测试代码设置初始状态，没有修改引擎文件。守包场景敌人是直线接近、没有侧移的脚本，难度很低，验证的是基本防拆功能，而不是复杂残局实力。

第一版专项测试见 `round2_scenarios.jsonl`，其中 4 个推进样例在下包前已全灭驻留出生区的无弹药敌人，未能验证下包。这些样例最初记为未通过；随后将无弹药敌人移到远处以隔离目标，重新跑完 24 个场景。未把提前获胜冒充下包通过。

### 4. 导航、协议与压力测试

- `python3 nav_r2.py`：示例地图 160 条随机起点到 A/B 的路径全部到达，最长 386 个物理帧；只覆盖示例地图，不能推及所有随机图。
- `python3 check_r2.py`：20×5 形状和方向检查、下包静止、拆包静止全部通过；20,000 步随机移动的碰撞检查全部通过。
- 合成 5 名敌人、200 发可见敌弹的观察，单次响应 **0.0674 秒**，低于 5 秒硬上限。这是性能用合成输入，不声称它是引擎实际产生的自然局面。

## 局限与保留风险

1. 地图和对抗样本有限，不能由这些相关样本估计正式胜率。7 场平局说明仍可能出现双方都赢下进攻半场或其他对称弱点。
2. 两秒敌人记忆及弹道估计可能失真；1 秒开环窗口无法实时响应新威胁，敌人突然转向时会选错走位。
3. 初始三二分防、接触后集中增援比较简单，可能被佯攻与快速转点利用；没有跨回合学习敌方部署。
4. 守包岗位只有静态几何保证，没有完整敌方到达时间预测或拆弹者优先火力分配；专项守包对手也不够强。
5. 缺少完整进度看门狗和动态换点机制；本次导航修正与测试不能证明所有地图都不会卡住。
6. 护甲优先可能使连续失利后长期只能购买冲锋枪，尚未证明优于协同存钱起步枪。
7. 程序只依赖 Python 标准库，缓存留在进程内。性能测试有较大余量，但极端规模观察和不同机器负载仍需实际裁判验证。
