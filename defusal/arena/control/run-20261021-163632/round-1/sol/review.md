# 第 1 轮提交说明与离线自测

## 提交状态

- 正式入口：`entry.json`，执行 `python3 agent.py`。
- 程序常驻，以 JSON Lines 接收观察，逐行输出并立即 flush；比赛中不写文件、不联网、不依赖第三方库。
- 目前只有准备阶段的离线对局，**尚无正式比赛结果**。本文不冒充正式赛后复盘。

## 实际策略

### 经济

优先把低护甲补到 100（护甲不足 45 才补购），再根据余款购买步枪、冲锋枪或微冲；保留尚可使用的现有武器，不购买狙击、机枪或霰弹。防守方有余款则买拆弹器。初始 800 元因此通常购买护甲而非微冲。

### 寻路和任务

对完整静态地图建立不穿墙角的八邻接图，缓存从目标格出发的 Dijkstra 距离场。近距离路径做圆形角色净空检测，再按裁判的先 X 后 Y 碰撞方式预测每帧移动。

进攻方每回合按种子及回合选择 A/B，五人集中推进。携带者进入任意合法包点即静止安包，队友向包点周边展开；掉包时转向捡包。下包后尽量守在炸弹附近阻止拆除。

防守方开局三人 A、两人 B，接触敌人后向接触位置靠拢。下包后选择路径距离较短、优先有拆弹器的单位拆包，进入炸弹 0.85 格内停止；其余单位掩护。

### 战斗

从每个单位的独立可见敌人建立短时（两秒）队伍通讯记忆，用于导航与朝向，不构造不可见敌人的真实坐标。依据相邻观察估计敌人运动，进行有限时间外推。

每个决策窗口预测己方 20 帧移动；遭遇战对九种移动方向评分，兼顾任务推进、横向运动、近距离后退、碰撞、方向连续性及敌方弹道风险。已有来弹尽可能从连续观察恢复速度，首次观察则用已见射手或公开出生方向估算；另对可见敌人的后续射击生成简化预测。开火完全交由裁判，程序只输出方向和朝向。

注意：说明文档称开火限制为 8 格视野，但公开源码 `updateUnit → canFire` 实际只检查武器射程、墙体与朝向，未调用 `canSee`。程序没有修改引擎，也不输入射击对象；针对此差异加入了“看到远处来弹但尚未看到射手”的预警走位。该估计不等同于获得射手真视。

## 实际运行的测试

测试脚本为 `selftest.js`，直接创建公开 `simulation.js` 的真实比赛，每秒分别向两个常驻 Python 程序发送 `sim.view(g, team)`，通过 `submitBuys`、`submitWindow` 和 `advanceWindow` 执行完整比赛；不向控制器发送完整观战状态。所有比赛包含半场重置和回合经济。

### 主测试矩阵

命令：

```
node /workspace/selftest.js rushA,rushB,rush,camp 1,2,3,7,19,42
```

共 24 场，2415 个 live 决策窗口，**18 胜、6 平、0 负**，最长一次双程序响应等待为 **67 毫秒**。原始逐场比分、回合原因、存活单位及响应耗时保存在 `test_results.json`。

- `rushA`：进攻固定 A，战斗时以路径推进为主，不使用高级侧移评分。
- `rushB`：同上，改为固定 B。
- `rush`：防守阶段主动向中路推进，进攻常规集中推进。
- `camp`：开局分守两点，接敌后增援，关闭高级侧移评分。

这些是自己编写的基线，与正式对手无关，且共享本策略的寻路和部分任务逻辑；不能用该胜率推断正式成绩。

### 追加压力测试与自对弈

命令：

```
node /workspace/selftest.js turret,main 5,8,11,16 /workspace/extra_results.json
```

共 8 场、1031 个 live 窗口，最长双程序响应 26 毫秒。

另使用 `example.json` 实际启动最终入口进程，连续检查 buy/live 两种响应：通过；live 为严格 20×5，所有 dir/aim 都在合法集合中。全程自测未出现程序崩溃、非法输入或超时。

## 局限

1. 只有一秒一次观察；窗口内敌人的转向、突然出掩体和死亡不可即时感知。弹道评分是启发式近似，不能保证躲弹。
2. 来弹首次观察没有速度字段，射手估计可能错误，尤其对方已经侧移时。
3. 同路推进在中路狭窄地图上会聚集，远程交火和中央截击仍可能造成团灭；压力测试已验证此弱点。
4. 防守 3/2 分兵遇到五人集中推进时，需要增援时间，部分地图容易先丢一侧。
5. 安包/拆包单位静止，牺牲闪避；掩护与下包后站位没有进行全局掩体优化。
6. A/B 按固定规则选择，未根据此前回合学习对方部署；没有复杂的包抄或佯攻。
7. 自测对手由同一套代码衍生，样本有限，不能替代与独立策略的正式比赛。
