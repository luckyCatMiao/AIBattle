# 爆破模式 5v5 参赛方案说明（第 1 轮）

> §1–§6 为赛前方案与离线自测结果；第 1 轮两场正式对局的赛后复盘见 **§7**（2026-10-21 追加）。

## 1. 提交物与接口

- `entry.json`：`{"mode":"program","command":["python3","agent.py"]}`
- `agent.py`：从 stdin 每次读一行 JSON 观察，向 stdout 写且仅写一行 JSON，写完立即 `flush`。
  - `phase:"buy"` → `{"buys":[...]}`，最多 5 个单位，只对存活单位下单。
  - `phase:"live"` → `{"inputs":[[{dir,aim} × 5] × 20]}`，固定 20 帧、每帧 5 个单位，`dir`/`aim` 只使用 N/U/D/L/R/UL/UR/DL/DR。
  - 非法 JSON、空对象或处理异常时返回一份中立窗口（全 N），保证「一行进、一行出」不破坏请求/响应流；空行直接跳过。
- 全部计算为纯 Python 标准库，无网络、无文件写入，可在只读工作区运行。

## 2. 对机制的关键理解

阅读 `simulation.js` / `catalog.js` / `RULES.md` / `GAME.md` 后，影响策略的主要结论：

1. **开火判定与视野无关**。`canFire` 只检查武器射程、`lineOfSight` 和 ±50° 朝向锥，不检查 8 格视野；`aim` 独立于 `dir`，朝向会持续保留。因此本图 20+ 格的直线长廊（中路 x=18–21、两侧主道 x=8–11 / x=28–31）上，双方可以在看不见对方的情况下互相开枪，**预瞄长走廊的价值极高**。
2. 视野是 100° 锥、8 格，2 格内为近距感知，墙体遮挡。因此远处开枪靠的是「猜到/预瞄」，近处才靠视野。
3. 开火、换弹、下包（静止 3 s，`dir==='N'`）、拆包（5 s / 带包 2.5 s）全部自动，程序只需要给移动和瞄准。
4. 护甲吸收 `min(armor, damage*0.5)`：手枪 24 → 带甲每发掉 12 血，步枪 30 → 掉 15 血。护甲对起手手枪局价值很大。
5. 地图 40×24：y=11–12 整行是墙，只有 x=8–11、18–21、28–31 三个缺口；x=14 与 x=25 的竖墙分别在 y=3–8 和 y=16–20；A 点 x5–10,y4–7（内有 x7–8,y5–6 的柱子），B 点 x29–34,y4–7（柱子 x31–32,y5–6）；进攻出生 (17..21,21)，防守出生 (17..21,2)。
6. 经济：起手 800，护甲 650，步枪 2700，冲锋枪 1250，拆弹器 400；半场重置为 800 + 手枪。公开事件只包含本队的 `shot`，敌人的开火起点不可见，`hit` 不公开。

## 3. 采用的策略

### 3.1 购买

- 手枪类：钱 ≥2700 买步枪，否则 ≥1250 买冲锋枪；已有冲锋枪且钱 ≥3350 才升级步枪。
- 护甲 <100 且剩余钱 ≥650 就买护甲（优先于攒钱）。
- 防守方 0、1 号位在买完上述物品后若还剩 ≥400，买拆弹器（2.5 s 拆包）。
- 起手 800：全员护甲 + 手枪；带甲手枪需要约 9 发才能击杀（前 8 发每发只掉 12 血，护甲耗尽后才掉 24），明显提高第一回合的容错。

### 3.2 进攻（默认 `flank`）

- 3 人走主道：`(9.5,21.5)→(9.5,15.5)→(9.5,12.5)→(9.5,9.5)→(9.5,6.5)`（B 点镜像到 x=30.5）。
- 2 人（编号 3、4）走中路包抄：`(19.5,13.5)→(18.5,10.5)→(12.5,9.5)→(12.5,6.5)→(10.5,6.5)`（B 点镜像）。
- 下包点在 `(9.5,6.5)` / `(30.5,6.5)`；到达后 `dir='N'` 静止 3 s 自动下包。
- 下包后按 `POST` 站位（包点南侧，朝北看包）。
- 掉包：离包最近的存活队员去捡包并下包，其余人继续推进；扛包者死亡后由存活者接管（见 4.2 的修复）。
- 站点选择由服务器 `seed` 与回合号确定，A/B 轮换，避免每回合同一路线。
- 团灭风险高时（例如中路对枪失利）不会主动撤退——本程序没有撤退逻辑，这是已知局限。

### 3.3 防守（默认阵型 `C`）

- 开局 5 人压中路 8–9 行横排（x=17、18、19、20、21），朝南看住三个缺口与中路长走廊。
- 每帧根据视野与「接触记录」估算威胁站点（`_update_threat`），一旦判定 A 或 B 受威胁，全队按 `DEF_HOLD[site]` 旋转到对应包点；否则维持中路的 `C` 阵型。
- 下包后：离包最近的人去拆包，其余人按 `RETAKE` 站位卡住包点入口。
- **存活集合变化时重新分配站位**：某个队员阵亡后，幸存者按「最近可用站位」重新分配，补上空出来的角度。这一条在自测中把防守胜率从 63% 提到 92%（见 4.4）。

### 3.4 移动、瞄准与容错

- 栅格 A* 规划 + 直线拉直（string pulling），逐帧复现服务器物理：3.0 格/s = 0.15 格/帧，斜向每轴 0.106 格/帧，单位半径 0.30，分轴滑动。
- `aim` 与 `dir` 解耦：有可见敌人时瞄最近的可见敌人，否则瞄最近的「接触点」（3 个决策窗口内有效），再否则用角色预设朝向。移动时也保持朝威胁方向。
- 卡角处理：某帧主方向被墙挡住时，尝试 45° 侧滑，并**把修正后的方向真的发给服务器**（只改本地预测不改输出会导致单位顶在墙角不动，这是自测中发现并修复的 bug）。
- 卡住检测：连续 2 个决策窗口位移 <0.25 格则丢弃当前路点。
- 规划重建键包含 `(回合, 阵营, 炸弹状态, 站点, 威胁, 存活集合, 炸弹坐标/携带者)`；重建时用 `_route` 剪掉已经走过的路点，避免幸存者被送回出生点。

## 4. 离线自测结果

所有测试用 `simulation.js` 驱动两个真实进程（`python3 agent.py`），`run_match.js` 对每一个提交窗口做合法性校验（20 帧 × 5 单位、合法方向），全程无一次非法输入。因此第 4 节所有数字都是在「输出完全合法」的前提下取得的。

### 4.1 对脚本电脑（弱基线）

3 个种子 × 3 种脚本风格（mixed/aggressive/passive）× 两个阵营，共 18 场：

- 进攻回合 36/36 胜，防守回合 36/36 胜（100%）。
- 说明基本规则、下包/拆包、经济与移动没有硬伤；但脚本电脑很弱，这个数字不能代表对真人/强 AI 的水平。

### 4.2 自测中发现并修复的问题

1. **墙角卡死**：防守方在 (15.3,9.2) 附近顶住墙不动。原因是 `_next_point` 在无直线视野时返回了不可达的格子中心，`dir_to` 给出 'L'，而程序只把修正方向用于本地预测、仍向服务器发送 'L'。修复后 `_move` 返回 `(dir,x,y)` 并把修正方向写入输出。
2. **掉包后原地发呆**：扛包者阵亡、炸弹掉落，但规划键没变，幸存者一直站到回合超时（seed 2 第 1 回合实测 100 s 不动）。修复：规划键加入存活集合与炸弹状态/坐标；修复后最后一名进攻者捡包并在 15.3 s 完成下包。
3. **重建规划把幸存者送回出生点**：加入存活集合后，每次死亡都会重下整条路线。修复：`_route` 按最近路点裁剪已完成的部分。

### 4.3 进攻风格对比（对默认 `C` 防守，8 个种子 × 3 个进攻回合 = 24 回合）

| 进攻风格 | 进攻回合胜率 |
|---|---|
| `stack`（5 人全走主道） | 3/24 = 13% |
| `flank`（3 主道 + 2 中路，默认） | **9/24 = 38%** |
| 备选中路绕行路线（先随主道过墙再横切中路） | 0/24 = 0% |

结论：保留 `flank`。备选路线在 y=13 横切时正好进入中路防守的预瞄走廊，实测更差，已删除。

### 4.4 防守重分配的作用（对固定对手：旧版进攻，8 种子 × 3 = 24 回合）

| 防守版本 | 防守回合胜率 |
|---|---|
| 死亡后不重分配（旧版） | 15/24 = 63% |
| 死亡后重分配（当前） | **22/24 = 92%** |

同时做了单变量对照：只改「进攻方自己是否在死亡后重建规划」，进攻胜率都是 9/24 = 38%——说明 4.3/4.4 的差异来自防守端变强，而不是进攻端退化。

### 4.5 镜像自对弈（双方同一份代码，8 个种子）

- 当前版本：进攻方（team0 前 3 回合）2/24 = 8%，team0 防守 8/14 = 57%。
- 镜像里「进攻胜率」衡量的是「进攻 vs 本程序的防守」。由于本程序的防守在 4.4 中显著增强，镜像进攻数字随之下降属于**镜像指标的解释问题**，不代表进攻代码退化（4.4 的单变量对照已证明）。
- 镜像中防守回合样本少于 24（4:0 提前结束会导致第 4–6 回合不被采样），因此防守列存在幸存者偏差，只有进攻列（每场固定 3 回合）适合横向比较。

### 4.6 响应时间与鲁棒性

- 152 个决策窗口实测：p50 = 1 ms，p95 = 12 ms，最大 23 ms（硬上限 5 s）。
- 11 条人工构造的异常观察（缺 `map`/`units`、炸弹无坐标、全队死亡、坐标 null、非法 JSON、空对象、正常 buy/live）→ 11 条合法响应，无崩溃、无错行；缺地图时走异常保护返回中立窗口。
- 直接以 `entry.json` 的命令对 `example.json` 做冒烟测试：输出 5 条购买指令（全员护甲），进程正常退出。

## 5. 已知局限

1. **自对弈过拟合风险**：`C` 阵型与两条进攻路线都是对本程序自己的进攻/防守调出来的；对手风格不同（例如不守中路、或专门打一侧主道）时，`C` 的中路堆人可能被绕开。
2. **进攻偏弱**：对默认防守只有 38%，多数败局在「进攻方全灭」，主要死因是出生后 1–2 s 内在中路长走廊被预瞄对枪打掉。没有撤退、拉扯、假打等战术。
3. **`canFire` 不看视野这一机制是把双刃剑**：本程序利用了长走廊预瞄，但也暴露在对手的同类预瞄下；没有做「避开已知预瞄走廊」的绕行。
4. **决策粒度 1 s**（20 帧一次）：无法做帧级微调（例如根据弹道瞬时侧移），对枪细节完全交给服务器自动开火。
5. **地图坐标硬编码**：所有站位/路线都是针对本图手写的，换图即失效；只做了 A/B 镜像复用。
6. **团队协同有限**：共享的只有「接触点记录」，没有分工协议（例如明确的架点/拉枪配合），站位分配是贪心最近匹配。
7. **拆弹器只给防守 0/1 号位**，且买包顺序固定，极端经济状态（例如全员 <650）下没有专门的强起/纯 eco 决策。
8. **下包后的 `POST` 站位在包点南侧朝北**，如果对手从南侧（中路缺口）回防，可能被背身；备选的「包点内四面围包」站位尚未充分测试，本轮没有采用。
9. 镜像指标存在幸存者偏差与解释偏差（见 4.5），不能直接当作进攻/防守强度的绝对度量。

## 6. 复现方式

```bash
# 对脚本电脑（18 场）
node tools/exp_bot.js 1,2,3 mixed,aggressive,passive

# 进攻风格 A/B（8 种子 × 3 回合）
AGENT_VARIANT=C AGENT_ATK=flank AGENT_BASE_VARIANT=C AGENT_BASE_ATK=flank \
  node tools/exp2.js 1,2,3,4,5,6,7,8

# 镜像自对弈
node tools/mirror.js 1,2,3,4,5,6,7,8

# 延迟
node tools/latency.js

# 单回合事件/走位追踪
node tools/fight.js 6 C 1
node tools/postrace.js 1 C 1
```

`AGENT_VARIANT` / `AGENT_ATK` 只是离线 A/B 开关，默认值就是提交策略（`C` / `flank`）；比赛环境不设置这些变量时行为与自测的默认配置完全一致。

## 7. 第 1 轮赛后复盘（2026-10-21）

### 7.1 两场比赛的公开记录

| 对局 ID | 座位（按顺序） | winner | 比分 | 模拟帧数 | 决策窗口 | 时长（墙钟） | roundLog |
|---|---|---|---|---|---|---|---|
| `r1-g1` | `deepseek-flash`, `sol` | `null` | 0 : 0 | 1 帧 | 0 | 0.14 s | 空 |
| `r1-g2` | `sol`, `deepseek-flash` | `null` | 0 : 0 | 1 帧 | 0 | 0.13 s | 空 |

两场的 `reason` 完全相同：

> 技术中断：deepseek-flash: Invalid response envelope; sol: Invalid response envelope

两场的 `errors` 也都是 `{"deepseek-flash": 0, "sol": 0}`，`technicalFailure` 字段记录了同一句 `Invalid response envelope`。两场的 `sha256` 分别为 `50dd3f71…`（`r1-g1`）和 `588da3ae…`（`r1-g2`）。

**这些数字的含义**

- 服务端以 20 Hz 推进，因此 **1 个模拟帧 = 0.05 s 模拟时间**；`r1-g1` 的 0.14 s 与 `r1-g2` 的 0.13 s 是墙钟时长（包含进程启动与第一次报文往返），不是游戏内经过的秒数。
- `windows: 0` 表示**一个 20 帧决策窗口都没有完成**：比赛连第一个 `live` 窗口都没进入，更没有打过一枪。
- `roundLog: []` 表示**没有任何回合开始/结束记录**，无法从战报中提取站位、交火、下包、拆包或经济数据。
- `scores` 为 0 : 0 且 `winner` 为 `null`，战报未把胜场判给任何一方；但按 `RULES.md`「输出格式错误判该场技术负」，从我方视角这两场都是**技术负（0 分）**，不能记成平局，也不能解释成战术失利。
- 两场唯一的差别是座位顺序（`r1-g2` 交换了先后手），失败结果、帧数、窗口数与错误文本完全一致，说明失败与地图侧别、先后手和对手策略都无关。

### 7.2 根因分析

**可以直接确认的事实**

1. 本程序按 `GAME.md` / `RULES.md` 公布的**裸 JSON 协议**编写：stdin 一行观察，stdout 一行 `{"buys":…}` 或 `{"inputs":…}`。用 `example.json` 冒烟测试时，旧版输出的是合法的 `{"buys":[{"unit":0,"armor":true}, …]}`。
2. 用本地 `run_match.js` 驱动真实进程时，旧版程序在 seed 1/2/3 上都完整跑完 6 回合（4:0 获胜），`validateInputs` 对每个窗口都通过；这说明策略与逐帧输出本身没有形状错误。
3. 我构造了一个**带信封**的观察 `{"id":7,"type":"observation","observation":{…example.json…}}` 喂给旧版程序，旧版只认顶层 `phase`，因此把这条报文当成「未知阶段」，返回了一个裸的 `{"inputs": …}`。这正是会被信封校验器判为 `Invalid response envelope` 的形态。

**最可能的根因（与所有公开数字一致）**

> 比赛运行器把观察封装在 envelope 中（例如 `{"id","type","observation"/"data"/"payload"}`），并要求回复同样是 envelope；旧版程序返回裸动作，于是第一次报文（购买阶段）就被判为 `Invalid response envelope`。双方两个座位都按公开文档输出裸 JSON，所以两边在同一时刻以同一条错误同时失败——这与「0 决策窗口、1 帧、0.13–0.14 s、双方对称报错」完全吻合。

**排除或降级的其他解释**

- *程序崩溃/超时*：硬上限 5 s，实际 0.13–0.14 s 就结束；本地进程启动与响应约 1–30 ms，且旧版在本地多场完整对局中稳定运行。更重要的是 `errors` 计数为 0，说明失败发生在报文信封校验层，而不是某个单位的行动或规则异常。
- *购买内容非法*：非法购买条目按规则只会被忽略，不会产生 `Invalid response envelope`；而且比赛在购买阶段就中断，根本没有进入 `live`。
- *对手针对*：失败发生在任何决策窗口之前，两场双方报错文本相同，不存在可利用的战术对抗。
- *模型推理问题*：本提交是 `program` 模式，比赛时只运行 `agent.py`，模型不在对局回路里；错误文本针对的是座位/进程的响应，不是模型 API。

**尚不能确认的部分**：真实裁判的 envelope 具体字段名不在公开资料中，且规则禁止读取私有裁判实现。因此上面的根因是**由现象反推的最强假设**，不是对裁判源码的确认；修复也只能覆盖常见信封形态，无法保证与未公开 schema 逐字段一致。

### 7.3 我的改动（`agent.py`）

没有改动任何战术、路线、购买或经济逻辑：这两场没有产生一个 `live` 帧，据此调整战术没有依据。改动全部集中在**协议适配与容错**：

1. **新增 `_find_obs()`**：若报文顶层含 `phase`，仍按裸观察处理；否则递归在 `observation` / `obs` / `view` / `state` / `data` / `payload` / `request` / `query` / `message` 等常见信封键下寻找观察。裸协议行为完全不变。
2. **新增 `_wrap_action()`**：检测到信封时，深拷贝原信封，把动作放回对应位置，并保留 `id` / `seq` / token 等元数据；键名做对称映射（`observation/obs/view/state → action`，`request/query → response`），`type` / `kind` / `event` 标记做 `observation→action`、`request→response` 的翻转；其余字段原样保留。
3. **主循环兼容两种模式**：信封解析或重建失败时回退为裸动作而不是崩溃；非法 JSON、空对象、非字典报文仍保持「一行进、一行出」并立即 `flush`，不会让请求/响应流错位。
4. **购买帧容错**：若观察缺少 `phase`、但同时含 `units` 与 `buy`/`buyable`，按购买阶段处理。
5. **修正异常分支**：非字典报文进入异常处理时不再因 `obs.get` 二次抛错。

改动后的验证（均可复现）：

| 输入 | 输出 |
