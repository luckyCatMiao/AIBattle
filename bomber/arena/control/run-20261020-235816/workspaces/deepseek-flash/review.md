## 三、回合与系列汇总

### 1. 总账

- 两局共 **10 个回合：我方 4 胜、对手 2 胜、4 平**；系列赛 **2 : 0**，按战报单局比分相加为 **4000 : 2000**。
- 两局的回合走势完全相同：**2 胜 1 负 2 平**。`r3-g1` 是“先赢两局、再平两局、最后输掉已无关胜负的第 5 局”；`r3-g2` 是“先输一局、再平一局、随后两胜收尾”。
- 与第 2 轮相比：系列赛从 **1 : 1** 变为 **2 : 0**；回合从 **3 胜 3 负 4 平** 变为 **4 胜 2 负 4 平**；平局数仍为 4，均打满 150 秒。

- 这两个负局与第 2 轮 `r2-g2` R3 的 `3 / 1 / 0`（55.6 秒、owner 1）属于同一模式：**回合中段、三属性全面落后、被已经成型的对手击杀**。连续两轮都出现至少一次，说明它不是单次偶然。

### 4. 平局：均势与“小优势无法兑现”

4 个平局全部是 3000 帧：

- `r3-g1` R3、`r3-g2` R2：双方 **6 / 6 / 3**，完全均势。
- `r3-g1` R4：我方 6 / 6 / 3，对手 6 / 4 / 3，**我方火力领先 2 级**，但 150 秒内未能兑现。
- `r3-g2` R4：我方 6 / 5 / 3，对手 6 / 6 / 3，**我方火力落后 1 级**，但守住了平局。

结论：我方在唯一一次“满级对未满级”的平局（`r3-g1` R4）里没有完成击杀；对手在 `r3-g2` R4 的小优势局也没有兑现。**“小幅属性优势转化为击杀”仍是最大的得分泄漏点**，但本轮它没有影响系列赛结果。40% 的平局率与第 2 轮相同。

## 四、过程分析

### 1. 系列走势

- **`r3-g1`**：我方 R1、R2 连续击杀尚未成型的 Sol（对手终局仅 2/2/0、1/4/2），取得 2 : 0；R3 双方满级、R4 我方满级对 6/4/3，均打满 150 秒平局。此时我方已有 2 胜、对手最多只能拿 1 胜，系列赛实际上已经锁定；R5 我方以 1/1/0 被满级 Sol 击杀，只把最终回合比分改写为 2 胜 1 负 2 平，**没有改变系列赛归属**。
- **`r3-g2`**：我方 R1 以 2/1/0 被满级 Sol 击杀，0 : 1 落后；R2 满级对满级打平；R3 双方满级、75 秒时我方完成击杀；R4 我方 6/5/3 对 6/6/3 守住平局；R5 对手仅 1/2/1，我方满级并在 56 秒完成击杀。最终 2 胜 1 负 2 平，系列赛翻盘。
- 两局都没有出现“领先被追平后崩盘”的连续失分：`r3-g1` 的失利发生在系列赛已锁定之后，`r3-g2` 的失利在下一回合就被止住。

### 2. 为什么会发育崩盘（本地逐帧复现的推断）

公开战报只有终局属性，无法直接看到 51–56 秒之前发生了什么。为了定位，本地用逐帧引擎（`engine.py`）复现了一个同类局面，并记录每一帧的掉落、拾取与属性变化：

- 对局：`tools/agent_safe.py`（第 3 轮提交版本，我方，owner 1）对 `tools/agent_w_reb_t.py`（陪练，owner 0），种子 20，第 3 回合。
- 结果：陪练在 **第 759 帧（37.95 秒）** 达到 6/6/3；我方直到 **第 1540 帧（77.00 秒）死亡** 仍是 **1/1/0**，整回合 **一次道具都没有捡到**。
- 逐窗口追踪显示，死亡前最后几个窗口（第 1459、1499、1519、1539 帧）我方均为 `hunt=True`、`aggro=1.0`，属性仍是 1/1/0；第 1539 帧在 (7, 7) 选择等待，下一帧被对手（owner 0）的炸弹击杀。
- 同一复现中，我方在该回合放置了 **17 颗炸弹**，拾取次数为 **0**；陪练在同一回合属性提升 **13 次** 并完成满级。至少从结果看，我方并不是没有行动，而是所有行动都没有转化为属性。
- 另一个复现（种子 9，同一对手，第 3 回合）中，我方在 **第 1521 帧（76.05 秒）** 死亡时只有 4/1/0；三次拾取全部是炸弹，火力和速度仍为初始值；对手在同一回合属性提升 13 次，并在 **第 760 帧（38.00 秒）** 已满级。

据此提出一个**推断性根因**：当双方属性差距拉大后，Agent 仍可能因为“对手距离 ≤ 5”而进入 `hunt`；`hunt` 模式下“靠近对手”的价值可能压过“去捡自己炸出来的掉落”的价值，导致它继续向更强的对手移动，而不是停下来经营。对手则在同一时间把地图资源转化为等级，形成雪球。这个推断能解释“51–56 秒时 1/1/0 或 2/1/0、对手满级”的终局形态，但**不能替代官方回放验证**：本地陪练不是 Sol，官方也没有提供死亡坐标、致死炸弹归属或逐窗口输入。

### 3. 满级局的转化问题

- 我方满级的 7 个回合是 **4 胜 3 平**，没有失利；问题不在“满级后会不会输”，而在“满级后能不能把均势或小优势变成击杀”。
- `r3-g1` R4 是唯一一次我方满级、对手未满级（6/4/3）却打平的回合；`r3-g2` R4 则是我方 6/5/3 对对手 6/6/3 守平。两局合计 4 个平局，占 40%。
- 与第 2 轮相比，回合胜场从 3 增加到 4，说明转化率略有改善；但平局率没有下降，仍是主要得分泄漏。

## 五、本轮使用的改动与赛后新增改动

### 1. 第 3 轮正式对局实际使用的版本

提交形态为 `/workspace/entry.json`：

```json
{"mode":"program","command":["python3","agent.py"]}
```

程序从 stdin 每行读取一个 JSON 观测，向 stdout 写一行恰好 20 帧的输入并立即 flush；只使用 Python 标准库。

第 3 轮两局使用的是赛前冻结的版本；相对第 2 轮赛后版本，本轮只新增一处改动：**紧急移动分支（保底路径）的安全修复**（详见 `tools/review_round3_prematch.md` 第 2.2 节）。该版本的本地副本为 `tools/agent_safe.py`（MD5 `2302f78b1df7d8b37d0538a5d0d454a7`），与赛后合入守卫的当前 `agent.py` 不是同一文件。要点：

1. 旧代码在“正常目标评估找不到可行动作”的保底分支里，用 `safe_until(cell, max(t, 20))` 从第 20 帧才开始检查危险，漏掉了“到达之后、第 20 帧之前”出现的火焰；
2. 旧代码的比较键是**取最大值**的，却把 `risky`、`bad`（1 表示危险）和 `ef`（越大越难逃）放在前面，等于优先选择更危险的格子；
3. 修复后从实际到达帧 `t` 开始扫描安全余量 `su`，先按 `su > 24` 分层，再按 `su` 从大到小，并依次偏好非陷阱格、易逃生格、非死角，最后才看推进、出口数和到达时间；`window_safe` 仍然是最终闸门。

赛前用 seed 22 的逐帧回放验证过：旧版在第 2 回合第 1161 帧于 (6,7) 自爆，修复后同一场景不再自爆。该路径只占千分之几的决策窗口，不能解释本轮两次 1/1/0、2/1/0 的发育崩盘。

在本轮公开战报能验证的范围内：

- 两局 `errors` 均为 0、`technicalFailure` 均为 `null`，没有崩溃或非法响应；
- 两个负局的终局属性是 1/1/0 与 2/1/0，更像“发育崩盘后被击杀”，而不是“双方均已成型的对局”；但仅凭终局属性不能判断致死炸弹归属；
- 但公开战报不提供死亡坐标与致死炸弹 owner，因此**不能据此证明本轮没有自爆**，也不能证明安全修复直接带来了两场胜利。它只是本轮实际使用的版本的一部分。

### 2. 赛后合入的改动：极端发育落后时的求战抑制

**动机**：本轮两次负局都是“接近初始属性 vs 满级对手”。本地逐帧复现显示，Agent 在严重落后时仍可能被“对手距离 ≤ 5”触发 `hunt`，继续向对手靠近，而不是停下来捡掉落、补发育。因此新增一个**只在极端落后状态生效**的守卫，不改变任何安全校验或爆炸投影，也不放宽 `escape_plan` 的准入条件。

**代码改动**（`agent.py`）：

```python
farm_left = any(t == SOFT for t in tiles)
# Catastrophic under-development: when we are near base stats while the
# opponent is already far ahead, do not let proximity force a hunt.
# Farming/collecting is the only route back into the round.
starving = (enemy is not None and farm_left and my_strength <= 6.0
            and my_strength + 6.0 < es)
hunt = False

# ...
if dist_e <= 5 and not starving:
    hunt = True

# ...
if desperate:
    hunt = True
if starving:
    hunt = False
```

其中 `my_strength = blast * 2 + bombs + speed * 1.5`，对手同理；初始属性对应 3.0，满级对应 22.5。`my_strength <= 6.0` 大致覆盖“总升级权重不超过 3 点”的状态（例如 3 个炸弹掉落，或 1 个炸弹 + 1 个火力，或 2 个速度），`my_strength + 6.0 < es` 要求对手至少领先 6 点。触发时只做一件事：**取消 `hunt`**（包括由距离、时间、`desperate` 触发的求战），使该窗口的 `aggro` 变为 0，目标估值以经营掉落与软墙为主。它不会清除 `desperate` 等残局标记，也不会放宽 `escape_plan` / `window_safe` 或增加任何新的冒险放弹条件。合入后 `agent.py` 的 MD5 为 `feef3ec938745d28d88c8ebd00f6eb2c`，与 `tools/agent_r3_starve.py` 完全一致。

**为什么阈值这样取**：

- 本轮两个负局的终局属性分别是 1/1/0（强度 3.0）和 2/1/0（强度 4.0），对手均为 6/6/3（强度 22.5），远低于 `6.0` 阈值，且差距远大于 6；
- 本地复现中的 4/1/0（强度 6.0）也包含在内；
- 正常满级、或只是小幅落后的局面不会触发，避免影响既有的求战与收尾逻辑。

## 六、局限与风险

1. **没有官方回放。** 公开战报只有回合帧数、胜者、终局属性和比分；没有地图种子、死亡坐标、致死炸弹归属或双方逐窗口输入。本文对败因的分类（发育崩盘、均势/小优势未兑现）是基于终局属性与时间的可验证推断，不能替代逐帧复盘。
2. **样本很小。** 本轮只有 2 场系列赛、10 个回合；每个座位只有 5 个回合，决胜回合只有 6 个。2 : 0 的系列赛和 4-2-4 的回合比分都不能用来推断长期强弱。
3. **本地陪练不是 Sol。** 所有对照对手都是自写变体或脚本机器人。守卫在 `wreb` 上改善、在 `v3` / `aggro_v3` 上轻微退化，说明它的效果依赖对手风格；对 Sol 是否有效，公开数据无法回答。
4. **守卫只覆盖“极端落后”状态。** 它不会阻止更早阶段的“炸开对手半区软墙、掉落被对手捡走”的雪球；本地复现中，对手在约 38 秒就满级，而我方在 77 秒仍是 1/1/0。要真正提高发育下限，可能需要重做“炸墙后是否去捡掉落”的估值，而不只是一个 `hunt` 开关；但目前没有官方回放支持更大改动。
5. **“低属性死亡”分类依赖阈值。** 本文把终局属性总和较低、且发生在 2200 帧前的死亡归为低属性死亡；不同阈值会改变计数。核心结论（本轮两次负局都是 1/1/0、2/1/0）不依赖这个分类。
6. **平局转化仍未解决。** 4 个平局全部 150 秒；其中 `r3-g1` R4 我方满级对 6/4/3 未能击杀。此前测试过的“最后 20 秒冒险”等候选没有产生行为差异或导致退化，因此没有继续放宽安全约束；在没有回放前，不应盲目增加残局冒险。
7. **出生角/掉落 RNG 的观察不可靠。** 两次负局的出生角都在奇数回合对角线（(1,1)/(17,15)），第 2 轮的崩盘也在 (1,1)；但地图几何是上下、左右镜像的，掉落 RNG 使用绝对坐标 `(seed, round, x, y)`，没有官方种子就无法区分“地图掉落分布”与“对手策略”。本文不据此改动策略。
8. **战报 `duration` 与模拟时间不是同一口径。** 本文用 `roundLog` 帧数 ÷ 20 计算模拟秒数；`duration` 只用于说明执行耗时，不能用来推算游戏内时间。
9. **守卫的收益幅度很小。** 合计 +5 系列胜 / -2 系列负，但这是 400 场本地对局的结果，且对两个较强本地对手有轻微退化；不能保证在正式对局中复现。

## 七、结论与下一轮优先级

### 1. 结论

- **结果**：`r3-g1` 我方（owner 0）2 胜 1 负 2 平、2000 : 1000 胜；`r3-g2` 我方（owner 1）2 胜 1 负 2 平、2000 : 1000 胜；系列赛 **2 : 0**，回合合计 **4 胜 2 负 4 平**。两局 0 错误、0 技术故障。
- **模拟帧数/秒数**：`r3-g1` 9,061 帧 = 453.05 秒；`r3-g2` 9,741 帧 = 487.05 秒；合计 18,802 帧 = 940.10 秒。战报 `duration` 分别为 8.17 秒、9.42 秒，是执行耗时。
- **最主要的现象**：
  1. **发育决定胜负**：我方满级（6/6/3）7 回合 4 胜 3 平 0 负，未满级 3 回合 0 胜 2 负 1 平；对手未满级 4 回合 0 胜 3 负 1 平。6 个决胜回合中 5 个由属性更高的一方获胜。
  2. **两次负局都是“1/1/0、2/1/0 型”发育崩盘**（51.00 秒、56.05 秒），与第 2 轮 `r2-g2` R3 的 3/1/0 崩盘同型；这是当前最可复现的失败模式。
  3. **两个负局都没有改变系列赛归属**：`r3-g1` R5 发生在系列赛已锁定之后；`r3-g2` R1 之后我方以两胜两平翻盘。但在更接近的系列赛中，同类崩盘会直接致命。
  4. **平局转化仍是最大得分泄漏**：4/10 平局，全部 150 秒；`r3-g1` R4 我方满级对 6/4/3 未能击杀。相比第 2 轮，回合胜场从 3 提升到 4，但平局率没有下降。
- **改动**：
  - 第 3 轮正式对局使用的是赛前冻结版本，包含“紧急移动分支（保底路径）的安全修复”；两局 `errors`/`technicalFailure` 均为 0，但公开战报不足以证明该修复直接带来了胜利。
  - 赛后合入“极端发育落后时的求战抑制”守卫：仅当 `my_strength <= 6.0` 且对手领先 6 点以上、地图仍有软墙时取消 `hunt`；不改变任何安全校验。本地 400 场对照合计 +5 系列胜 / -2 系列负、-5 死亡、-2 低属性死亡，但对 `v3` / `aggro_v3` 有轻微退化，收益幅度有限。
  - 赛后测试并否决“落后时提高掉落价值”和“守卫+掉落价值”两个候选：前者在本地多 1 个负场、多 1 次死亡；后者没有优于单独守卫，且多一处行为改动。

### 2. 下一轮优先级

1. **拿到第 3 轮官方种子或回放后，优先验证“发育崩盘”假设**：确认两次负局中我方是否真的炸开了软墙却没有去捡掉落、对手是否在同一时间段完成雪球；如果假设成立，再考虑把“炸墙后去捡掉落”的估值单独修正，而不是只靠 `hunt` 开关。
2. **继续观察守卫在正式对局中的表现**：记录它触发的窗口数、触发后是否真的捡到掉落、是否出现“该打不打”导致的平局或负局；若正式对局显示退化，应回退该改动。
3. **均势/小优势的转化**：`r3-g1` R4 的 6/6/3 对 6/4/3 打平是最明确的案例。没有回放前，不继续盲目增加残局冒险；优先用逐帧回放判断是“找不到安全放弹点”还是“找到了但估值不足”。
4. **保持安全边界**：不因为本轮两胜就放宽 `escape_plan` / `window_safe`；本轮两次负局从终局属性看都不像“放弹后无退路”的自爆形态，不能用来证明可以冒险。
5. **不对出生角或左右侧做策略性改动**：现有样本不足以支持地图偏差结论；地图几何镜像，掉落 RNG 的绝对坐标差异需要官方种子才能验证。
