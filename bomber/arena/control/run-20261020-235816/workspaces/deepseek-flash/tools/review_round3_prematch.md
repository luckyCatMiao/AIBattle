# 泡泡堂（BLAST BUDDIES）第 3 轮提交说明

> 截至本文件写就时，第 3 轮正式对局尚未进行，`public_results.json` 仍是空数组（`[]`）。
> 因此本文**不包含任何第 3 轮官方比分或复盘**，只记录实际采用的策略、可复现的本地自测结果和已知局限。
> 第 2 轮正式对局的复盘已原样保留在 `tools/review_round2.md`，未删除、未改写。

## 一、提交内容与运行方式

- `entry.json`：

  ```json
  {"mode":"program","command":["python3","agent.py"]}
  ```

- `agent.py`：单文件、仅使用 Python 标准库，不联网、不读写进程外文件、不调用外部引擎。
- 协议：从 stdin 逐行读取一个 JSON 观测，向 stdout 写且只写一行 JSON，并立即 flush：
  - `inputs` 固定 20 帧；
  - `dir` 取 `N/U/D/L/R`，`btn` 取 `null` 或 `"BOMB"`；
  - 观测损坏、字段缺失或内部异常时，不跳过该行，而是返回一个合法的 20 帧中立窗口，保证一观测一响应。
- 工作区只读时也经过验证：把 `agent.py` 复制到只读目录、以只读权限运行，仍能正常返回合法窗口。

## 二、实际采用的策略

### 2.1 总体框架

每个决策窗口（20 帧）内，Agent 先根据观测重建当前回合的精确状态，再分别评估“放弹”和“走到某个目标格”两类动作，最后用窗口级安全校验筛选，输出 20 帧输入。核心实现包括：

- **逐帧移动模型**：按 `move_frames(level)=max(3,6-level)` 和浮点 `progress` 复现“一帧走一格”的规则，包含移动中不能转向、不能放弹等约束。
- **爆炸投影**：按炸弹剩余引信（40 帧）、爆炸持续 12 帧、十字范围、硬墙阻挡、软墙吸收，逐帧投影已知炸弹的火焰，并处理炸弹连锁。
- **放弹前必验退路**：`escape_plan` 先在“假设该炸弹爆炸”的危险场中搜索一条能在引信结束前到达安全格的路线；再用 `window_safe` 把候选的 20 帧输入完整重放一遍，确认每一帧所处格子都不在已知或可推演的火焰中。任一步不通过就不放弹，改用移动或等待。
- **移动目标评估**：在 `(格子, 可行动帧)` 上做 Dijkstra，价值图综合掉落物价值、与对手的距离、出口数量、推进时间、终局安全余量等；目标是“有价值且到达后一段时间内安全”的格子。
- **对手封口模型**：枚举对手 20 帧内可能到达的放弹点，构造“对手一弹即可封死”的 `trap_cells` 与 `esc_best`（逃出所需帧数），尽量不把目标定在死角、单出口口袋或对手门口。
- **掉落物经营**：利用确定性 LCG 预测每个格子在本回合会掉什么（见 3.2），优先去拿尚未满级的炸弹/火力/速度掉落，并避开即将被火焰烧掉的掉落。
- **求战模式**：默认从开局就具备求战倾向（`hunt_start=0`）。是否追击由双方战力估算、距离、剩余时间和当前大比分共同决定；落后时提前求战，领先时更愿意拖时间；第 5 回合平分或最后 30 秒落后时进入更激进的“必须赢”模式，降低保命权重。
- **比分意识**：读取 `players[].wins` 区分领先/落后；平局不得分，所以落后时不能一味求稳，但领先时也不主动送掉回合。

### 2.2 本轮唯一采用的代码改动：紧急移动分支的安全修复

准备第 3 轮时，用逐帧回放定位到旧版的一次自爆（seed 22，第 2 回合，引擎帧 1161，坐标 (6,7)，引爆者是自己的炸弹）。根因在“没有正常移动目标”时的紧急保底分支：

1. 旧代码用 `safe_until(cell, max(t, 20))` 从第 20 帧才开始检查危险，漏掉了“到达之后、第 20 帧之前”会出现的火焰；
2. 旧代码的比较键是**取最大值**的，却把 `risky`、`bad`（1 表示危险）、`ef`（越大越难逃）放在前面，等于优先选择更危险的格子；该次回放中它确实选了对手门口的死角 (6,7)。

修复后：

- 从实际到达帧 `t` 开始向后扫描危险，得到真实的安全余量 `su`；
- 先按“能否安全度过本窗口之后的一段”（`su > 24`）分层，再按 `su` 从大到小；
- 之后依次偏好非陷阱格（`-bad`）、更易逃生的格（`-ef`）、非死角（`-risky`），最后才看推进、出口数和到达时间；
- 仍然保留“到达后 20 帧整体重放”的 `window_safe` 作为最终闸门。

修复只影响“正常目标评估完全找不到可行动作”的罕见保底路径；在可计数的抽样窗口中，该路径约占千分之几的决策窗口，但它正是旧版自爆的来源。修复后同一 seed 22 场景不再自爆。

## 三、自测结果

以下均为**本地离线自测**，使用工作区内的 `engine.py`（与 `simulation.js` 逐帧一致的 Python 移植）驱动，不是正式比赛结果。所有对局均为双方各坐一次 0/1 席位（除特别说明外）。

### 3.1 规则引擎与掉落预测的确定性校验

| 项目 | 方法 | 结果 |
| --- | --- | --- |
| Python 引擎与官方 JS 引擎一致性 | `tools/crosscheck.py` 随机输入窗口逐帧对比 | 本次复跑 5 局共 84 个决策窗口全部一致；此前完整对照中 28,463/28,463 个快照一致 |
| 掉落类型预测 | 对 seed 1–20、回合 1–5、全部 19×17 格子，把 `predicted_drop` 与引擎 `roll_drop` 对比 | 32,300/32,300 完全一致 |

掉落预测的意义是：知道某格“会不会掉、掉什么”后，可以优先经营高价值掉落；预测错误只会让经营目标变差，不会绕过任何安全检查，因为危险场始终来自观测与规则推演。

### 3.2 修复前后对比

**修复版自我对弈（seed 1–40，双方各坐一次，共 80 场 / 400 回合）：**

- 系列：7 胜 7 负 66 平；
- 回合：7 胜 7 负，386/400 回合为 150 秒超时平局；
- 死亡事件：双方各 7 次；
- 自爆：0 次；
- 中盘（约 55 秒）三项属性总和：5127 : 5127。

**修复前旧版同一批种子（80 场 / 400 回合）：**

- 系列：14 胜 14 负 52 平；
- 回合：18 胜 18 负，364/400 回合为超时平局；
- 死亡事件：双方各 18 次；
- 自爆：2 次；
- 中盘属性总和同样对称。

解读：修复让双方都更难被“自己或对手的炸弹”收掉，因此自爆消失、死亡数下降、平局数上升。这是安全性提升的直接结果，但也说明**自测环境下的进攻效率偏低**，见“局限”。

**修复版 vs 修复前旧版（seed 1–40，双方各坐一次，共 80 场）：**

| 指标 | 修复版 | 旧版 |
| --- | --- | --- |
| 系列赛 | 15 胜 7 负 58 平 | 7 胜 15 负 58 平 |
| 回合 | 17 胜 8 负（375 平） | 8 胜 17 负（375 平） |
| 死亡事件 | 8 次 | 17 次 |
| 自爆 | 0 次 | 1 次（seed 22，第 2 回合 1161 帧） |
| 中盘属性总和 | 5104 | 5117 |

在这组同种子、同席位的直接对照里，修复版在系列、回合和存活三项上均优于旧版，且没有出现新的自爆。

## 四、局限与风险

1. **自测平局率很高，不能证明正式对局能赢。** 修复版自我对弈 386/400 回合是 150 秒超时平局，修复版与旧版对照也有 375/400 回合平局。说明双方在彼此熟悉的保守打法下很难互相击杀；正式对手如果更敢进攻、或更善于封口，结果可能不同。第 3 轮的实际比分只能等正式对局产生，本文不做预测式“复盘”。
2. **掉落运气可能造成单回合属性鸿沟。** 地图几何是上下、左右镜像对称的，但每个格子的掉落种子是 `seed*31 + round*977 + x*131 + y*17`，不同出生角附近的“可利用掉落”数量并不相同。自测中见过同一回合四个角分别只有约 3/13/13/8 个可用掉落的情况。掉落预测只能帮助优先经营，不能改变随机数；某些回合会被对手在属性上压制。
3. **修复的验证范围仍有限。** 安全修复主要在 seed 1–40 的自我对弈、与旧版的 80 场直接对照、以及对 `aggro_v3` 的 20 场压力测试中验证；没有与正式对手的逐窗口回放可比对（工作区没有对方文件，也没有第 3 轮官方数据）。
4. **紧急分支仍是“单目标校验”。** 保底路径只对当前评分最高的目标做 20 帧 `window_safe` 校验；若它失败，Agent 可能选择等待，而不是自动尝试第二、第三目标。抽样对局中没有观察到 `wait` 决策（seed 1–3 的 2,000 余个窗口里为 0），但不能证明所有极端地图都不会触发。
5. **求战时机是启发式，不是博弈论最优。** “落后提前求战、领先拖时间、最后 30 秒落后则激进”来自自测调参；此前尝试过延后求战（`hunt_start=25`）和全局远征/资源路由，均在基准中退化，未采用。面对未知对手时，这些阈值仍可能偏保守或偏冒进。
6. **掉落预测依赖官方随机数实现完全一致。** 当前 `engine.py` 与 `simulation.js` 的 LCG、掉落权重、软墙掉落顺序已逐帧对照一致；若正式裁判在未公开细节上有差异，预测会失准。但所有安全判断仍基于观测到的炸弹、火焰和地图，不依赖预测，因此预测失准只会降低经营效率，不会直接造成违规或自杀式放弹。
7. **合规边界。** 未读取对方文件，未修改 `RULES.md`、`GAME.md`、`simulation.js`、`catalog.js`、`example.json`，未下载或调用现成引擎；`agent.py` 只依赖标准库，运行时不访问网络或进程外数据。
