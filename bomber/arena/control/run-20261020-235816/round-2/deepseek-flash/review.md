# 泡泡堂第 2 轮提交说明（策略、自测与局限）

> 本文件写于第 2 轮正式对局**开始之前**。截至写作时，第 2 轮尚未产生任何官方对局结果，因此本文只记录实际采用的策略、离线自测的数据与已知局限，**不包含也不编造任何赛后复盘**。官方对局结束后的整体复盘应另写 `postmatch.md`。第 1 轮的复盘已归档在 `tools/review_round1.md`。

## 一、提交内容与协议

- `/workspace/entry.json`：

  ```json
  {"mode":"program","command":["python3","agent.py"]}
  ```

- 程序每次从 stdin 读取一行 JSON 观测，向 stdout 写一行 JSON，恰好 20 帧输入：

  ```json
  {"inputs":[{"dir":"N|U|D|L|R","btn":null|"BOMB"}, ... 共 20 条 ...],"note":"..."}
  ```

  每行写完立即 `flush`；只使用 Python 标准库（`sys`、`json`、`heapq`，另外仅用 `os.environ` 读取可选调试开关），不读写进程外文件、不访问网络。

- 异常处理：任何一行都会被应答，绝不跳过。JSON 解析失败输出 20 帧中立窗口（`note="badjson"`）；观测结构异常或内部异常时 `decide()` 兜底输出 20 帧中立窗口（`note="error"`/`"over"`），保证“一条观测对应一条响应”。

- 工作区只读可运行：把 `agent.py` 复制到去写权限目录、`chmod a-w` 后以 `python3 -I agent.py` 运行，仍能正常输出合法窗口（见第四节）。

## 二、对引擎机制的建模要点

自测使用 `/workspace/engine.py`（对官方 `simulation.js` 的 Python 移植）。该移植在随机输入下与官方 JS 逐窗口对照通过（见第四节），因此下面的机制判断都基于逐帧实测：

1. **20 Hz、20 帧一个决策窗口**：双方同时提交，收齐后统一推进 20 帧；火焰伤害在双方本帧移动之后结算。
2. **移动的“起步即到达”语义**：fighter 的 `x,y` 在移动**开始的那一帧**就变成目标格，`fromX/fromY/progress` 只用于插值动画。因此一个速度 3 的 fighter 在一个 20 帧窗口内最多可以实际跨越 6–7 格；判断“对手能否在某帧到达某格”时，第一步只花 1 帧，而不是 3 帧。
3. **移动帧数的浮点累积**：`moveFrames(speed)=max(3,6-speed)`，但进度是 `progress += 1/mf` 的 IEEE double 累积，实际完成一格所需的帧数可能比 `mf` 多 1。代码里用 `tile_cost()` 精确复现该累积，而不是直接用 `mf`。
4. **炸弹**：引信 40 帧；爆炸生成十字火焰，硬墙阻挡、软墙吸收并销毁、可连锁引爆其他炸弹；火焰持续 12 帧。BOMB 是输入历史中的上升沿触发（历史上限 8 条），在进度未满 1 的帧按下可能丢失。
5. **掉落确定性**：每个被炸毁的软墙以 55% 概率掉落，掉落类型由 `(seed, round, x, y)` 的 LCG 决定，权重为炸弹 0.40、火力 0.35、速度 0.25。因此可以在拆墙前精确预测“这面墙会不会掉、掉什么”，并据此给软墙估值。
6. **座位不对称**：引擎每帧先执行 owner 0 的 `step_fighter`，再执行 owner 1。双方计划穿过同一格时，owner 0 在该格放下的炸弹会先生效，owner 1 的移动会被该炸弹挡住。这是同策略对局中 owner 0 席位占优、owner 1 席位死亡偏多的根源之一。

## 三、实际采用的策略

### 1. 精确爆炸投影

`project()` 对所有已知炸弹做逐帧投影：引信倒计时、十字爆炸形状、硬墙/软墙阻挡、软墙被摧毁、连锁反应、12 帧火焰窗口。输出 `danger[k]`（第 k 帧哪些格在燃烧）与 `burn[cell]`（该格最早开始燃烧的帧），后续所有安全判断共用这一时间线。

### 2. 逐帧 Dijkstra 走位

`plan()` 在状态 `(格, 可动帧)` 上做 Dijkstra：

- 等待一帧的代价为 1；
- 一次移动从第 t 帧开始、第 `t+tc` 帧到达，移动期间逐帧检查目标格是否已经燃烧；
- 起点带 `ready`（当前插值进度还需几帧才能开始下一步）；
- 可以把对手当前格设为不可通行（`avoid`），避免计划穿过对手身体后被对方同帧放下的炸弹截断。

### 3. 放弹必须“可证明能逃”

- `escape_plan()` 对“我现在放一颗炸弹”的假想局面重新投影火焰，要求存在一条逐帧安全的路线，并且到爆炸结束后仍安全；找不到就不放。
- `bomb_value()` 综合软墙掉落预测、道具价值、攻击价值；`attack_val()`/`attack_cells()` 用连锁投影判断“这一炸能否覆盖对手”。
- 常规局面拒绝无退路放弹；只有在明确“平局等于失败”的残局（`desperate`：`timeLeft<=30` 且胜局落后，或第 5 回合平局且 `timeLeft<=30`）才允许有限冒险。

### 4. 对手可达格 + 一弹陷阱模型

用对手速度与“第一步 1 帧”的规则计算 `enemy_reach`（对手在 20 帧内能到达的格）。对其中每个可放弹的格 b，计算它的爆炸十字 `hz`，再用 `escape_field()` 求“从每格出发、逃出 `hz` 需要多少帧”。逃不出去的格记为 `trap_cells`；走位目标会避开这些格，或在已被困时优先选择 `esc_best` 更大的格。该模型用于识别“对手一颗炸弹就能封死的走廊/口袋”。

### 5. 本轮的关键改动：双弹组合陷阱（T）

第 1 轮之后的候选版本 `wreb` 已经包含三个修正：

- **R**：`reach_cells` 中第一步只花 1 帧（对应“起步即到达”的引擎语义）；
- **E**：对手在引信时间内能完成的移动数改为 `max(1, (40-2)//tc + 1)`；
- **B**：假想炸弹自己所在的格可以通过相邻格“走出来”，不再一律记为不可达。

第 2 轮在 `wreb` 上新增 **T**：在陷阱模型中，把**对手当前所在格**的炸弹十字也并入每次假想的威胁，并把对手当前格视为不可通行：

```python
hz0 = blast_shape(tiles, ecell, enemy_blast)
for b in enemy_reach:
    hz = blast_shape(tiles, b, enemy_blast) | hz0
    blocked_b = bombcells | {b, ecell}
    esc = escape_field(tiles, blocked_b, hz, speed)
```

动机来自自测中的真实死亡模式：作为 owner 1，我方走进对手旁边的小口袋准备进攻；owner 0 对手在**自己脚下**放弹，并从唯一出口（穿过我方的路径）逃走；下一窗口再在出口方向补一颗弹，口袋被两颗炸弹的十字同时覆盖。旧模型每次只考虑“一颗假想弹”，认为口袋仍可从侧面逃出，于是把该格当成安全攻击位；组合模型会把“当前格炸弹 + 任一可达格炸弹”的联合十字纳入，从而把这类格标成陷阱。

这个改动是**更保守**的：它把一部分原本会死亡的局面转成安全等待，代价是更多回合打到 150 秒平局。自测显示它同时减少了死亡并略微提高了击杀数（因为存活时间与站位更好），具体数据见下节。

### 6. 发育、拾取与残局

- 用 `predicted_drop()` 预先判断每面软墙的掉落，优先拆“会掉且价值高”的墙；掉落价值速度 > 火力 > 炸弹。
- 拾取路线与拆墙目标共用同一套逐帧安全规划；火焰会烧毁珍贵掉落时有额外惩罚。
- `late = timeLeft <= 45` 时，若处于追击状态则把道具/掉落权重乘以 0.25，避免残局绕路刷属性。
- 追击（`hunt`）在以下情况开启：属性明显领先、与对手距离 <=5、超过 `hunt_start` 且属性不落后、`timeLeft<=30` 且不领先或属性接近、`timeLeft<=15`、地图已无软墙。落后时会更早求战（`hunt_start` 压到 22 秒），领先且时间充裕时更耐心（抬到 60 秒）。
- `desperate` 只在明确必须赢时放宽安全约束，普通局面仍坚持“可证明能逃才放弹”。

## 四、自测结果（全部为本地离线自测）

## 五、局限与风险

1. **没有官方第 2 轮对局数据**。本文所有胜率/回合数均来自本地自测；对手是我方变体或脚本机器人，不能代表真实对手。第 1 轮的实际对手（Sol）已经说明本地对局与正式对局差距可能很大，因此不预测本轮结果。
2. **平局偏多**。T 模型把大量原本可能被击杀的局面转成 150 秒超时；同水平镜像对局经常 0-0 或 1-0。若比赛需要主动拿分，这种保守性可能不够。残局的 `hunt`/`desperate` 会尝试在最后 30/15 秒强制接战，但无法保证击杀。
3. **座位不对称无法消除**。引擎每帧先执行 owner 0；同策略对局中 owner 0 的炸弹会先封住共用格，owner 1 的计划路线会被截断。新模型把 owner 1 的多数死亡转成了平局：种子 9–32 的 owner 1 对局中，对 `v2` 的 24 个系列仅死亡 1 次，对 `v2_aggro` 仅死亡 2 次；但 owner 1 仍然很少赢下击杀回合。正式比赛两局交换座位，这一不对称只能被部分抵消。
4. **陷阱模型是保守的静态近似**。假想对手炸弹按“立即存在”处理，没有精确建模对手到达 b 格所需的时间；组合模型只合并“对手当前格 + 一个可达格”，不是完整的双弹/多弹对抗搜索或博弈树。真实炸弹的爆炸时刻只在路径规划/终点安全检查里使用，陷阱逃逸场本身是静态的。这可能高估危险，造成额外的等待与超时；也可能漏掉更复杂的三弹组合。
5. **对手移动模型是近似**。`reach_cells` 用统一 `tile_cost` 估计对手移动，未精确重建对手当前 `progress`（是否正处于半步）；对手的按键历史、放弹冷却与拾取时机也不建模。E 修正只保证“引信内能走几步”的数量级正确。
6. **掉落预测依赖与官方实现一致的 RNG 细节**。如果裁判的 LCG、权重、种子/回合混合方式与本地移植有差异，软墙估值会偏；安全与逃生逻辑不依赖掉落预测，但发育效率会受影响。
7. **延迟只在本地测量**。p99 < 25 ms 是本地管道 + 本地引擎的结果；裁判机器更慢或负载更高时数值会变，但距 5 秒上限仍有很大余量。
8. **协议按行**。程序假设裁判每行发送一个紧凑 JSON 观测（与 `simulation.js` 的逐行输出一致）。如果把美化后的多行 JSON 原样写入 stdin，逐行读取会把每一行当成独立观测；正式裁判不会这样发送。

## 六、结论

- 提交为 program 模式：`entry.json` 指向 `python3 agent.py`，最终 `agent.py` = `v2 + R + E + B + T`，其中本轮新增的是**双弹组合陷阱模型 T**。
- 自测覆盖：引擎移植与官方 JS 的逐窗口对照（159 窗口 0 差异）、与 4 个本地强对手共 160 个系列的新旧对照（回合负场 64→16、胜场 101→106）、新种子 21–32 的确认（对 `v2` 15–0、对 `v2_aggro` 14–1）、3 种脚本机器人共 144 回合全胜、4 场真实子进程共 2734 窗口协议测试、405 条畸形观测、只读工作区。
- 没有出现非法窗口、崩溃、stderr 输出或协议违规；所有记录 `errors` 的自测均为 0。
- 本轮尚未进行官方对局；`review.md` 只陈述策略与自测，不编造任何赛后结果。正式对局结束后应按规则另写 `postmatch.md`。
