## 三、根因：为什么它会「站着不动」

### 3.1 先确认回放是可信的

公开回放里保存了每一帧的完整状态。我把 `r1-g1`/`r1-g2` 的 184+208 个真实观察
按窗口顺序重新喂给**赛前冻结的那份 `agent.py`**，逐窗口对比它重新生成的输入与
回放里记录的输入：

```
mismatched windows: 0/183   (r1-g1)
mismatched windows: 0/207   (r1-g2)
```

390 个窗口**全部逐帧一致**。这说明我可以精确解释每一个决策，而不是猜。

### 3.2 出生角是一个「5 格口袋」

```
      x=0 1 2 3 4 5
 y=0   #  .  #  .  #  +        . 空地   # 硬墙   + 软墙
 y=1   .  .  .  +  +  +        出生点 (1,1) 的可达格只有：
 y=2   #  .  #  +  #  +        (0,1) (1,1) (2,1) (1,0) (1,2) —— 5 格
 y=3   +  +  +  .  +  +        往东 (3,1) 是软墙，往南 (1,3) 是软墙
```

**不炸墙就永远出不去**。对手每一局都是开局 0.4 s 就对着自己的口袋墙埋雷
（`r1-g1` 事件 id=2：Sol 在 (16,15) 放弹），我却在里面站了 50 秒。

### 3.3 评分函数把「开图」算得比「发呆」还差

在第 1 局第 1 个窗口（完全静止的初始状态）下，把当时的候选计划全部打印出来：

```
    -0.550  stay                   path=[(1,1)]                       ← 被选中
    -1.050  approach               path=[(1,1),(1,2)]
    -2.450  bomb@2,1               path=[(1,1),(2,1),(1,1),(1,0)]     ← 唯一能炸开东墙
    -2.450  bomb@1,2               path=[(1,1),(1,2),(1,1),(1,0)]     ← 唯一能炸开南墙
```

三条规则叠加，导致「站着不动」永远赢：

1. **逃生耗时惩罚过重**：`W_ESC=0.35/帧`，而速度 0 时走一格要 7 帧（`1/6` 浮点累加
   6 次 = 0.9999999999999999 < 1），一次放弹计划光逃生就被扣 ≈ 7.35 分，
   而炸开一面墙的全部收益（掉落 + 开图 + 底分）只有 ≈ 2.7 分。
2. **地板分算错了位置**：代码里有「不低于原地发呆」的截断
   `if sc < W_STAY-0.1: sc = W_STAY-0.1`（= -1.1），但它写在
   「终点只有 1 个出口 → -1.5」这条扣分**之前**。口袋里每个格子出口都 ≤ 1，
   于是放弹候选被截到 -1.1 之后又被扣成 **-2.45**。
3. **原地不动的分反而最高**：`W_STAY=-1.0` 加上「出口数 ×0.15」的机动性奖励，
   出生点有 4 个出口 → **-0.55**，稳赢。

所以这不是"保守"，而是**评分函数的一个排序 bug**：
「把口袋炸开」这条唯一的生路，在数学上被算成了最差的选项。

## 四、本轮的改动（`agent.py`，5 处）

所有新参数都做成 `AG_*` 环境变量，**默认值即本次提交所用值**。

### 改动 1：被困检测 + 开图加分
新增 `trapped`：用时间扩展图统计 24 帧内可达格数，若 ≤ `AG_TRAPN`(12)
或可达格的最大出口数 ≤ 1，判定为「被困在封闭口袋里」。
被困时给**真的炸掉软墙**的放弹候选加 `W_TRAPB(4.0) + W_TRAPO(0.8)·log1p(新开空间)`。
炸空地（`broken` 为空）不享受这个加分，避免乱放弹。

### 改动 2：把「原地不动」降级为真正的最后手段
在所有扣分（机动性、出口数、对手威胁）**之后**再排序，并加一条硬规则：

> 只要存在一条**通过了硬安全校验**（`run_script` 在克隆世界里真跑一遍、跑完还活着）
> 且终点不在对手火力覆盖圈里的建设性计划（炸墙开图 / 必杀 / 捡道具），
> 就不允许它输给「站着不动」。

这是本轮的**核心修复**：它把 bug 的因果链直接切断，而不是靠调参绕过。

### 改动 3：捡道具放宽
原来要求「40 帧内可达」被写成 26 帧、落脚安全要求 26 帧。
速度 0 时 26 帧只够走 3 格，导致**自己刚炸出来的道具捡不到、然后被下一炸烧掉**。
改成：可达上限 40 帧、落脚安全 18 帧（整条计划的安全性仍由 `run_script` 用引擎语义复核）。

### 改动 4：局末保护（这是改动过程中新发现的自我炸死回归）
引擎的决策窗口是 20 帧，但一局可能在第 20 帧之前就结束；`endRound()` 会立刻
`startRound()`（位置重置回出生点、炸弹清空、地图重建），**剩下的帧会带着
「上一局地图的计划」直接执行到新一局的全新地图上**。此时计划里的放弹
= 在自己出生点埋一颗雷，逃生路线在新地图上又多半不存在。
实测 `seed 6004` 第 3 局就是这样**开局 2 秒被自己的炸弹炸死**。
新增 `round_may_end()`：若本窗口内有人会踩进已知火线、或 `timeLeft ≤ 1.2 s`，
就把整条计划降级成「不放弹 + 尾部 8 帧原地不动」。

**这条保护有已知盲区**（如实记录）：它只看「谁**现在**站在火里」，
抓不到「对手自己走进火里」结束一局的情形。我试过把判定放宽成
「对手离未来 20 帧内的火焰格曼哈顿距离 ≤ 2」，能把这类漏网也拦住，
但代价是大量误伤放弹——同样 15 个种子下打满 6/6/3 的局数从 **12/47 掉到 6/48**，
净亏，所以**最终保留紧的判定**，把残余风险记在第七节。

### 改动 5：参数化
`AG_TRAPN / AG_REACHT / AG_TRAPB / AG_TRAPO / AG_EXITP / AG_SAFEH`。
其中 `AG_SAFEH`（放弹后逃生终点需保持安全的帧数）实测 **24 比 45 更差**
（退得不够远，下一个窗口来回折返，炸弹放得多、道具收得少），所以默认保持 45。

## 六、诚实说明：上一版 `review.md` 里有一条结论是错的

赛前那版自测报告里我写过：

> 「`greedy.py` 对手在自测中经常把装备刷满（6 炸弹 / 6 火力 / 3 速度），
> 行为与历史交锋中对手的画像接近，因此我认为它是比随机对手更有意义的基准。」
> 以及「对 `greedy.py` 160 场 100% 胜率」。

复盘时逐局看了终局状态，这条**站不住**：`greedy.py` 几乎每一局都是
**自己把装备刷满后被自己的炸弹炸死**——它终局是 `6/6/3 且 dead`，而我方是 `1/1/0 且 alive`，
那几局我一颗炸弹都没放过，场地上的火焰只可能来自它自己。
也就是说那个 100% 只证明了**它会自杀**，不证明我强。
这条自测结论作废，本轮所有新数据都用「行为指标 + 自我对弈」重新衡量。

同样，赛前写的「面对同样保守的对手攻击力不足（自我对弈 68% 平局）」
在改动后缓解到 ≈31%，但**并没有解决**（见下）。

## 七、仍然没解决的问题（下一轮的方向）

1. **杀不掉龟缩的对手**。改动后自我对弈仍有 30/98 局打满 150 秒平局；
   面对「不出口袋」的对手我常常只能刷满装备然后耗到时间到。
   我仍然没有「连续放 2–3 颗弹把对手出口全部封死」的多炸弹协同搜索——这是最大短板。
2. **对手炸开我的口袋时，我依然是被动的**。第 1 轮我就是这样被"放"出去的；
   正确做法应该是自己掌握开图节奏，而不是等对手的爆炸替我开路。
3. **1v1 对拼阶段仍然会先踩进对手的十字覆盖**。`r1-g1` R3 和 `r1-g2` R3 都是这样死的：
   缺少「对手炸弹引信 + 我的退路」的联合判断（现在只保证了不被**自己**的炸弹困住）。
4. **座位差异没查清**。改动后我坐 A 打冻结版是 28:5 场，坐 B 只有 14:13，
   而同代码自我对弈没有这种偏差（9:6 / 8:7）。列为待查项，不做结论。
5. **局末自炸还有 2/300 的残余**。20 帧窗口跨局末时，上一局计划的尾巴会执行到新一局，
   而新一局我正站在封闭的出生口袋里，落点上的炸弹必死。现在的 `round_may_end()`
   只认「有人现在就站在火里」，抓不到「对手自己走进火里」。试过放宽判定，
   但 6/6/3 的达标局数从 12/47 掉到 6/48，得不偿失，所以先留着这个已知风险。
6. **数据面仍然很窄**。以上全部来自自写脚本对手，**不能据此推断对 GPT-6.1 Sol 的胜率**；
   本轮对手是上一系列冻结的强策略，且我按约定没有读取对方任何文件。

### 一、核心思路：把「安全」做成可证明的，而不是靠躲

这款游戏最容易被忽略的一点是：**所有炸弹的引信都是公开信息**（`observation.bombs[].fuse`），
而一个决策窗口是 20 帧、新炸弹引信是 40 帧。由此得到本 agent 的基石：

> 「未来 20 帧内会出现的火焰」可以从当前观察**精确推算**；任何**新**放下的炸弹，
> 在它爆炸之前至少还有一个完整窗口的预警。所以安全是可以精确保证的，不需要预测对手。

在此之上有四块：

1. **火焰时间线**（`fire_timeline`）：把场上所有炸弹按引信顺序引爆，含软墙被摧毁、
   硬墙阻挡、连锁引爆，得到 `fire[t] = 第 t 帧处于火焰中的格子集合`。
   我打算放的炸弹作为 `extra` 注入同一条时间线，于是「放完这颗弹我还有没有活路」可判定。
2. **时间扩展图上的 Dijkstra**（`dijkstra`）：状态是「(格子, 我可以再次移动的帧)」。
   移动一格耗 `moveFrames(speed)` 帧，且**引擎在起步那一帧就把角色算在目标格上**，
   所以目标格必须在 `[t, t+m-1]` 全程安全。它同时服务两件事：
   - 我自己的走位 / 逃生；
   - **判断对手在我放弹之后是否还有活路**——没有活路才是真正的必杀。
3. **「模拟自己」的执行器兼安全校验器**（`run_script`）：候选计划不会直接翻译成帧号发出去，
   而是先在克隆世界里用转向控制器真的跑一遍（引擎语义逐帧一致），**跑完仍然活着才允许提交**。
   这一步顺带解决了速度变化、浮点帧数、连锁引爆带来的时序漂移。
4. **掉落预测**：`rollDrop` 的随机数只由 `(seed, round, x, y)` 决定（引擎里是固定种子 LCG），
   所以**每面软墙会掉什么道具是可以离线精确算出来的**。我据此优先炸「会掉火力 / 速度」的墙。

### 二、复刻引擎时踩到的两个真坑（由差分测试逼出来）

我写了差分测试（`dev/difftest.js` 录真实引擎的逐窗口快照 + `dev/difftest.py` 让 Python 复刻
跑同样输入再逐帧比对地图 / 角色 / 炸弹 / 火焰 / 掉落）。它抓到两个致命偏差：

1. **浮点累加**：引擎里一格是 `progress += 1/max(3,6-speed)`，而 `1/6` 累加 6 次
   = `0.9999999999999999 < 1`，**速度 0 时一格实际要 7 帧，不是 6 帧**。
   我最初按 6 帧建模，导致所有计划整体错位一帧，放弹 / 移动全部对不上，胜率一度崩到 60%。
2. **观察精度不足以还原进度**：`px/py` 只保留两位小数，当进度是 `0.9999999999999999` 时
   `px` 恰好等于 `x`，看起来和「已经站定」完全一样。我改成**跨窗口自己模拟自己**
   （`track_sync` / `track_advance`），只在观察与自己的推演矛盾时才回退到 px 估计。

修完这两点后，纯移动的差分测试在 5 个种子上各 600 帧**零失配**；
带炸弹的对局 10 个种子里 8 个逐窗口完全一致（另 2 个的差异正是上面第 2 条的信息精度问题）。

### 三、每个窗口的决策

候选计划统一是「一串要经过的格子 + 在哪些格子上放弹」，由 `run_script` 执行并校验：

- **捡道具**：可达且落脚安全的掉落，按 `价值/(1+时间)` 打分。
- **放弹**（farm / 开图 / 压制 / 击杀）：对可达格 `C` 算十字火力能炸掉的软墙，价值 =
  掉落价值 + 开图增益（`log1p` 新增连通空地数）+ 固定底分（**开图本身就有价值，
  不炸墙就永远困在出生口袋里**）+ 朝对手方向推进的奖励；
  再用 `dijkstra` 验证「放完弹我一定能走出火力区」，**没有退路的候选直接丢弃**。
  若同时判定对手无路可逃，给巨额加分（必杀）。
- **压制走位 / 原地**：兜底。距离 150 秒上限越近，「主动找对手」的权重越高
  （平局不计分，拖满 150 秒等于白打）。
- **强制躲火**：脚下这格在 `t0+4` 帧内会起火时，逃生计划提到最高优先级。
- 最后按「对手火力覆盖圈」与「落脚格出口数」做惩罚 / 微调。

### 四、自测结果（全部本机离线）

工具在 `dev/` 下，对手程序在 `dev/opps/` 下，都是我自己写的脚本对手。
每个种子跑一场「五局三胜」系列赛，同一种子跑不同座位（出生角按局轮换）。

| 对手 | 场次 | 系列赛胜率 | 单局胜率 |
| --- | --- | --- | --- |
| `rndbot.py`（随机走位） | 25 场 / 76 局 | **25/25 = 100%** | 75/76 = 98.7% |
| `greedy.py`（稳健型） | 160 场 / 529 局 | **160/160 = 100%** | **477/529 = 90.2%** |
| `agent.py` vs `agent.py`（自我对弈） | 12 场 / 60 局 | — | 19 胜 / 11 负 / 41 平（平局 68%） |

> 复盘更正：`greedy.py` 那一行见本文第六节——它是自己把自己炸死的，这个 100% 不作数。

工程指标：

- 单窗口响应：中位数 **2ms**，p95 **4ms**，最大 **39ms**（硬上限 5 秒，余量充足）；
- 观察异常（空 JSON、`null`、缺字段、`tiles` 长度为 1、非 JSON 行）都能退化为合法中立窗口，
  不会技术负；自测中从未出现技术负。

### 五、局限与已知问题（赛前版，部分已被本文第七节更新）

1. 对「同样安全的对手」攻击力不足（自我对弈 68% 平局）。
2. 没有多炸弹协同封路。
3. 计划校验时把对手当静止。
4. 速度变化没有进规划。
5. 数据面窄，不能推断对真实对手的胜率。
6. 权重是手调的经验值。
