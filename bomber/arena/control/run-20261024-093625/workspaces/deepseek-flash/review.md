# 泡泡堂 1v1 · 第 3 轮提交说明（deepseek-v4.1-flash）

> **状态：正式比赛尚未开始。** 本文只记录本轮赛前的策略、代码修复与自测数据，
> 不包含任何官方对局复盘，也没有编造胜负。对 Sol 的实际战绩以比赛结果为准。

## 0. 提交物

- `entry.json`：`{"mode":"program","command":["python3","agent.py"]}`
- `agent.py`：单文件、只用 Python 标准库，stdin 每行一个观察 → stdout 一行 20 帧输入。
- 自测工具在 `dev/` 下（`rec.js` 录制回放、`anal.py` 逐窗分析、`diag.py` 单帧诊断、
  `parab.js`/`ab.js` 多种子双座位评测），不随提交。

## 1. 核心策略

每个决策窗口（20 帧）做四件事：

1. **逐帧复刻引擎**：把观察还原成与 `simulation.js` 逐帧一致的 Python 世界
   （浮点 moveProgress、引信/火焰顺序、连锁、软墙破坏、掉落）。
2. **火焰时间线**：按引信精确推算未来每一帧的火焰格集合，用于走位与必杀判定。
3. **候选计划 + 引擎级安全校验**：每条计划＝「走过的格子 + 在哪一格放弹」，
   先按收益排序，再用 `run_script` 在克隆世界里真的跑一遍；只在**活着**时才提交。
4. **防「一颗弹死」**：`kill_threat` 判断「对手能否走到某格、放一颗弹并在引信烧完前
   堵死我的唯一出口」，命中就把该落脚点判为死地；窗口第 20 帧的真实落点也要过这一关。

**比分感知**：观察里带 `players[].wins`，agent 知道当前五局三胜的比分。
落后时提高进攻权重；决胜局打平、或落后且本局只剩不到 60 秒时进入 all-in：
取消贴身放弹惩罚、允许用连锁换节奏、走位不再回避「一颗弹死」的格子（但仍保留
即时的逃火判定）。理由是平局不计分 —— 该赢的局拖成平局等于白打。

另外利用了两条规则事实：

- **掉落是位置的纯函数**：`rollDrop` 只用 `(seed, round, x, y)` 播种，可以离线精确预测
  每面软墙掉什么，因此只炸「会掉自己还没满的属性」的墙。
- **连锁会永久吃掉放弹容量**：引擎在连锁引爆时不扣被连锁炸弹的 `activeBombs`，
  每被连锁一次，本局剩余时间就永久少 1 点放弹上限。这是本轮最重要的发现（见 §3）。

## 2. 本轮修掉的确定性 bug（都有回放/复现依据）

| # | bug | 后果 | 修复 |
| ---: | --- | --- | --- |
| A | `run_script` 遇到连续重复路径格（dijkstra 的等待）时 `idx` 不前进 | 整窗口输出 20×N，白送战机 | 把「下一格 == 当前格」当成显式等待 1 帧 |
| B | 校验器在「模拟对手被自己的炸弹炸死」时提前结束 | 漏掉我方后续死亡 | 克隆世界里把对手设为永久无敌，只在我方死亡/跑满计划时结束 |
| C | 逃生终点用「最早到达的安全格」 | 经常沿走廊朝对手方向退，把退路交给对手 | 逃生终点按「近 + 远离对手 + 出口多」打分 |
| D | 只检查计划最终终点，不检查窗口第 20 帧的落点 | 计划跨窗口执行，中途停在死胡同 | 记录第 20 帧真实落点并做同一套死地判定 |
| E | 放弹目标允许到达时间 30 帧 | 炸弹落在第 20 帧之后，窗口内一颗弹都没放；下一窗重新评分又选另一个远目标 | **本轮新发现**：两个 agent 会在两个目标之间来回走 120 秒、一颗弹都不放。现在要求放弹到达时间 ≤18 帧 |
| F | 贴身放弹 / 逃生贴着对手 | 对手同帧在唯一退路上补弹，走廊夹心 | 对非必杀的贴身放弹、贴对手逃生路径加罚（对手放不出弹/装备大幅领先时自动放宽） |
| G | 整局把连锁当洪水猛兽 | 放弹节奏被自己拖慢，反而打不过「允许连锁」的同源代码 | 改成混合策略：泄漏 <2 点时允许用连锁换节奏，≥2 点后严格避免 |

## 3. 放弹容量：本轮最关键的游戏机制

`simulation.js` 的爆炸结算里，普通引爆会 `owner.activeBombs--`，但**被连锁引爆的炸弹
不会扣**。于是一颗炸弹只要被别人提前引爆，它的主人本局就永久少 1 点放弹容量：

- 从第 2 轮公开回放统计：Sol 每局大约被连锁 5 颗，实际只能同时维持 1–2 颗弹；
- 我方能保住容量时，同一局的放弹次数可以显著高于对手（自测里出现过 54 : 19）。

这条机制不是设计意图，但裁判就是这么算的，双方同等适用。本轮据此做了两件事：
**尽量不让自己被连锁**（混合策略），以及**不再为了规避连锁而牺牲放弹节奏**。

### 4.3 稳健性与性能

- **技术负 0（正常并发）**：上表所有评测（280 场对 v1 + 其它代理，合计数百场）无超时、
  无非法输出；协议测试覆盖空行、非 JSON、`null`、`[]`、`{}`、缺字段、`status=finished`，
  全部输出合法 20 帧。
- **一次压力测试的例外**：用 10 路并发（20 个 Python agent，机器被严重超卖）跑 24 个种子时
  出现过 2 次技术负，表现为 5 s 未回复——这是本机调度饿死，不是 agent 逻辑问题；
  正式比赛只有两个 agent。正常 4–5 路并发下所有轮次 tech 均为 0。
- **单次决策耗时**（回放真实对局状态，两个座位）：座位 0 中位 12.7 ms / p99 82.5 ms / 最大 95.4 ms；
  座位 1 中位 4.9 ms / p99 19.8 ms / 最大 24.6 ms。硬上限 5000 ms；
  另有 1.5 s 的内部死线，超过就放弃剩余候选走便宜的保底，绝不超时。
- **确定性**：agent 不使用随机数；同样的观察得到同样的输出。

## 5. 已知局限

1. **Sol 不可见**：本轮无法读取、运行或对测 Sol 的代码，所有胜率都是对自建代理的测量，
   不能直接外推。这是最大的不确定性。
2. **自对弈大量平局**：两个同等强度的本代码互打时，约 25%–40% 的小局打满 150 秒。
   地图一旦被炸开成开阔格网，单颗炸弹几乎杀不死满速对手（40 帧能跑 13 格），
   平局是这套规则的固有倾向；本版没有实现多弹协同围杀。
3. **没有对手动作预测**：只建模「对手从当前位置能走到哪、能放一颗弹」，不预测他下一手
   具体去哪，也不建模他同时放弹封退路（第 2 轮的主要死因之一，本轮 F 项只是启发式缓解）。
4. **混合连锁策略是经验参数**：阈值（泄漏 ≥2 才避免）来自自测，不保证对 Sol 最优。
5. **正式赛只有两局**：两局样本很小，单局波动（地图/掉落）会显著影响结果。

## 6. 复现方式

```bash
# 单个种子、录制完整回放
node dev/rec.js --seed 16000 --a "python agent.py" --b "python dev/frozen/v1.py" --out dev/rec/x.json

# 多种子 × 双座位评测（每个种子两局，交换座位）
node dev/parab.js --count 30 --seed 22000 --procs 5 \
  --a "python agent.py" --b "python dev/frozen/v1.py"

# 单帧诊断（打印局部地图、可达格、死地判定、实际决策）
python -I dev/diag.py dev/rec/x.json <frame_index> <owner> --call
```

以上工具都在 `dev/`，不属于提交内容。
