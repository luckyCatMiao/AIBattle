## 1. 提交内容

- `entry.json`：`{"mode":"program","command":["python","agent.py"]}`
  - 本机（Windows，Git Bash / Node 裁判）实测 **没有 `python3` 可执行文件**：用 Node
    `spawn('python3', …)` 得到 `ENOENT`，而 `spawn('python', …)` 正常（Python 3.14.3）。

    `NoDefaultCurrentDirectoryInExePath=1`），所以把 `python.exe` 复制成工作区内的
    `python3.exe` 也不能被 `spawn('python3')` 找到。因此 entry 使用 PATH 中的 `python`。

- `sim.py`：`catalog.js` + `simulation.js` 物理的逐行 Python 移植（用于窗口内自预测）。
- `planner.py`：赛道重采样、赛车线、曲率。
- `controller.py`：控制器与速度剖面。
- 其余 `mock_referee.js` / `mock_duel.js` / `race.py` / `search.py` / `refine.py` / `sim.py` 校验脚本为自测工具。

## 2. 最终策略

### 2.1 赛道几何
每局从观察的 `track.points` 现场构建，不做任何硬编码：

1. 把中心线按约 1 格弧长重采样；
2. 以“Laplacian 拉直 + 法向偏移限幅”求**最短可行赛车线**（相对中心线约短 6%，并且
   加入折叠保护：向内偏移不超过局部曲率半径的 0.7 倍，避免发夹弯处自交/尖点）；
3. 用 Menger 公式求线曲率并平滑，作为速度剖面的依据。

实测“最短线”明显优于“外抛最小曲率线”（后者长约 +12%，即使弯道曲率更低，总圈速反而慢
10–20%），因此最终采用最短线。

### 2.2 速度与操纵
- **速度剖面**：`v_max = min(46, kappa_k/κ)`，再用刹车距离回推（`brake_decel`）；直线目标速度
  设得很高（46），因此车辆在直线段几乎总是全油门，只有真正需要减速的弯前才刹车。
- **转向**：以曲率前馈的纯追踪为主（`κ_cmd = 2 sin(α)/L`，`steer = κ_cmd·v/ω_max`），
  `L = la_base + la_t·v`。
- **漂移蓄能（直道摆动）**：直道（前方一段曲率 < `cruise_kappa`）时在转向指令上叠加
  ±`wiggle_amp` 的方波，并置 `drift=true`。这样车辆以约 ±10° 的航向摆动前进，侧滑持续
  蓄能；当 `driftCharge` 超过阈值且 `boostEnergy` 未满时松一帧漂移把能量转入 `boostEnergy`。
- **喷火**：能量 > 阈值且不在刹车时持续喷火；弯道出口也允许喷火（`corner_boost`）。
- **弯道**：抓地过弯（实测漂移过弯在本赛道生成器上不稳定，见第 4 节）。
- **窗口内闭环**：每秒收到观察后，用 `sim.py` 精确复刻物理，在窗口的 20 帧里**逐帧重规划**
  （基于自己预测的状态），再一次性提交 20 帧。因此窗口虽然是开环提交，内部仍是 20 Hz 闭环。
- **座位无关**：全部逻辑基于 `yourPlayer` 与 `cars[yourPlayer]`，0/1 号座位使用同一套代码。
- **对手规避**：只在“并排（|横向|<1.3 且 |纵向|<4）”或“正在追上（前方 0–5 格且接近速度>0.8）”
  时给一个 ≤0.25 的转向偏置并临时关闭漂移；避免无谓地互相挤压，同时不在正常跟车时乱打方向。

### 2.3 关键物理发现（影响策略）
1. **喷火速度上限的实现细节**：`vF > cap` 时只执行 `vF = max(cap, vF - 0.9)`，而喷火每帧加速度
   `+1.5`，因此长时间喷火时前进速度会稳定在约 **48 格/秒**，远高于规则文字里的 23。这使
   “漂移蓄能 → 喷火”成为圈速的决定性因素。
2. **漂移的侧滑时间常数约 3.3 秒**（`gripDrift=0.985`）：漂移不是“立刻转得更快”，而是让车身
   与速度方向产生很大夹角；在纯直道/大半径圆上可以靠摆动维持 40+ 速度并自持能量，但在
   连续变化的真实赛道曲率下很难稳定（见局限）。
3. **越野判定只看车辆中心所在格子**；因此可以合法地用满路面宽度，但不能靠车身压线取巧。

## 3. 自测方法与结果

### 3.1 物理一致性
把 `sim.py` 与官方 `simulation.js` 逐帧对拍（随机输入、5 个种子、30 个窗口，含发车倒计时与
车车碰撞）：最大误差 **5.7e-14**，`lap/nextCp/drifting/boosting/offRoad` 完全一致。窗口内
自预测因此是可信的。

### 3.2 端到端协议测试
用 `mock_referee.js`（Node 裁判 + 官方 `simulation.js`）真实跑完整场比赛：观察 → 程序 stdin →
程序 stdout → `submitWindow` → `advanceWindow`。验证：
- 输出恒为一行合法 JSON、20 帧、每帧 1 辆车；
- 单次响应最大 **120 ms**（硬上限 5 s），平均 ~4 ms；
- 倒计时窗口处理正确（前 30 帧不推进物理，第 31 帧起给油）；
- 0 号、1 号座位均能正常完赛；
- **编码鲁棒性**：本机（中文 Windows）管道下 `sys.stdin.encoding` 实测为 GBK，UTF-8 中文
  （如观察里的 `准备发车`）会变成乱码，极端情况下 GBK 双字节规则会“吃掉”后面的 JSON
  语法字符导致整行解析失败。因此程序改为 `sys.stdin.buffer` 读原始字节，按 utf-8 → gbk →
  latin-1 依次尝试解码，stdout 也直接写 UTF-8 字节，避免任何与裁判进程编码相关的技术负。

### 3.3 自对弈（两辆本程序，交换座位）
12 条随机种子，全部跑满 3 圈，**0 次技术失败、0 次超时**，全部在 300 s 内冲线：

| 赛道类型 | 种子（示例） | 3 圈用时 |
| --- | --- | --- |
| K=3（约 460–480 格） | 6011 / 6012 / 6021 / 6022 / 1 / 2 / 3 / 5 / 42 / 777 | 66–70 s（最佳单圈 21.25–22.45 s） |
| K=5（约 585–610 格） | 4 / 9 / 100 | 85–87 s（最佳单圈 27.35–28.05 s） |

- 自对弈中两车全程最近距离约 3.9 格，规避逻辑生效后**碰撞事件 0–2 次**，完赛时间与单车
  独跑基本一致（差异 <1 s）。
- 与“静止对手”对跑时反而会因每圈绕行停在起跑线附近的静止车而慢 1–2 s；真实对手会移动，
  不属于实际情形。

### 3.4 参数搜索
- 先做 250 组随机搜索（4 条种子），再做 240 组坐标细化（6 条种子）。
- 评分函数刻意加入**稳定性项**：`均值 + 0.35×(最慢−均值) + 越野帧惩罚`，避免选出“平均快但
  某条赛道会崩”的参数（搜索中确实出现过某参数在单条种子上从 66 s 恶化到 180 s 的情况）。
- 最终参数在 12 条种子上均值 69.3 s、最慢 86.0 s、越野帧占比 ≤0.1%。

## 4. 局限与未解决问题

1. **未能复现公开战报中第二轮的 16.5 s 级单圈**。在同样的种子（6021/6022，赛道长度/半宽与
   公开战报完全一致）上，本程序最佳单圈约 21.6 s。公开战报显示上一版 deepseek 策略第二轮
   能跑到 16.55 s（3 圈 53.05 s），说明仍存在我们没找到的提速手段。
2. **漂移过弯不稳定**。我们单独验证过：在半径 5–20 的合成圆环路上，使用“速度方向纯追踪 +
   曲率前馈”的漂移控制器可以稳定跑出 17–19 的均速且能量自持；但一旦加入直道↔弯道切换
   （合成椭圆、真实赛道），就会在 1–2 秒内滑出路面。原因是漂移稳态的侧滑角恰好落在
   `|vF| > 4` 的漂移维持阈值附近，形成极限环；这是本轮最大的性能损失点。
3. **能量是主要瓶颈**：直道漂移蓄能的平均速率约 0.2–0.4/s，而喷火消耗 0.6/s，喷火占空比
   约 30–40%；弯道（约一半时间）无法蓄能。若能稳定地“漂移过弯”，占空比可望翻倍。
4. **对手未知**：无法读取、也不应读取对手工作区。上面的时间只能说明本程序自身水平，不能
   推断对 Sol 的胜率；正式对局结果以赛后 `postmatch.md` 为准。
5. **发车/碰撞**：本程序在窗口内不预测对手的加速，只用匀速外推做规避；若对手主动挤压，
   仍可能被撞出赛车线（会通过下一窗口观察重新收敛）。正面碰撞会显著掉速，策略上选择“让”
   而不是“挤”。
