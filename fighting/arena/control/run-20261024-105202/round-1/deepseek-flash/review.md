# 铁拳谱 · deepseek-flash · 第 1 轮自测报告

> 本文件只写**实际采用的控制策略**与**真实跑出来的自测数据**。本轮尚未与对手进行正式对局，
> 因此没有任何"复盘结果"——下面不包含、也不会编造对局过程。

## 一、提交内容

- `entry.json`：`{"mode":"program","command":["python3","agent.py"],"team":["vex","kestrel","aegis"]}`
- `agent.py`：常驻进程，stdin 每行一个 JSON 观察，stdout 输出一行 15 帧输入并 flush。
  全部排程只用 `catalog.js` 的帧数据计算，不写死角色数值；异常时退化为 15 帧中立，保证不判技术负。

## 二、从帧数据里挖出来的、决定胜负的四件事

全部结论都用 `lab/` 下的脚本直接跑真引擎（`simulation.patched.js`，与 `simulation.js` 仅差 require 路径）验证过。

1. **Vex 的超必杀是"一次即秒杀"。**
   多段招式的每一段按 `data.damage` **全额**结算（`hits` 只决定段数与间隔）。Vex 超必杀
   `hits=8, damage=280` 且**没有 knockup**，受击方不会被打飞，于是段段落地：
   实测 5 段 = 280+252+224+196+168 = **1120 > 1000 生命**，满血直接打死。
   它还有 `travel`（12 帧推进 290 px），受击后退躲不掉：实测 **80 / 110 / 140 / 170 / 200 / 240 / 280 / 320 / 360 px 都是 5 段秒杀**，400 px 仍有 952 伤害。射程几乎覆盖半屏。
   Kestrel 超必杀（`hits=7, damage=300`）同样能秒杀，但**没有 travel**，170 px 只剩 3 段（810）、200 px 只剩 1 段；
   Aegis/Nyx/Sable/Torv 的超必杀带 knockup，第一段就把人打飞、后续段落空，秒不掉人。
   → **一号位放 Vex 不是偏好，是算出来的。**

2. **取消窗口的精确帧位。** `canCancelUntil = 命中帧 + 10`，命中后 hitstop 冻结，
   第一个"活帧"是 `命中帧 + hitstop + 1`。把 qcf 指令排在 `命中帧+hitstop-1 … +hitstop+1` 三帧、
   末帧带按钮并保持，就能在解冻的第一帧立刻取消成超必杀。`hitstop >= 10` 的招（Torv hk）来不及取消。
   这条实现成了"普攻命中 → 超必杀"的斩杀确认链。

3. **窗口帧号是"过去帧"。** 观察里的 `frame` 是 f0，本窗口真正推进的是 **f0+1 … f0+15**。
   早期版本把输入排在 f0 起，等于整体晚一帧：抢招永远慢对手一帧，对胜率影响极大（修掉这一条，对固定测试组的胜率从 75.8% 跳到 93.3%）。这是本次最大的一处坑。

4. **防御只看判定帧那一帧按没按 B/DB**，且必须处于 stand/crouch/blockstun；
   `low` 必须蹲防、`overhead` 必须站防、`mid` 通吃。所以：站防的人怕下段 `lk`，蹲防的人怕 overhead
   （Kestrel 的 `hk` 是唯一的 overhead 普通技，其余人只能靠跳入）。同帧互殴由**席位 0** 获胜。

## 三、实际采用的打法

- **攒气（< 100）**：中立时在窗口**第一帧**按最快的 `lp` 抢招（命中 +8 气、被防 +3），
  命中按帧数据接 `lk → lp` 连段；被防就什么都不发生（安全确认），不会白亏。
- **斩杀（= 100）**：只要对手处于 **attack / hitstun / jump**（这三种状态不可能防御），且距离在
  超必杀有效射程内 → 直接超必杀秒杀。其中"对手出招时发超必杀"最稳：超必杀起手 1~10 帧无敌，
  抢得过任何普通技。
- **对手在防御**：先用下段 `lk` 试探。打中 → 取消超必杀秒杀；被蹲防挡下 → 记录"对手蹲防"，
  改用跳入空中重拳（overhead）破防。
- **防御**：按对手**当前招式真实 `guard` 属性**选 B/DB；挡下重招后按 `命中帧 + hitstop + blockstun + 1`
  精确排出反打帧，用够得着的最重普攻起手接满连段。
- **对手气满**：在超必杀射程内默认蹲防——他真放超必杀就挡下来（只吃 288 削防），
  而他收招比我的防御硬直长 20 帧以上，可以完整反打一套。除非**我也气满**，那时改为主动找机会反杀。
- **不走进判定**：前进只在对手收招帧、或对手长时间没出手（> 90 帧）时整窗口推进；
  否则走 8 帧就收住蹲防。

## 四、自测结果（全部为真引擎实跑，非估算）

评测台：`lab/harness.js`（自己写的 20Hz / 15 帧窗口双进程对局循环，直接调用 `simulation.patched.js`）。
每个对手跑 6 套敌方阵容 × 2 个席位 = 12 局。

### 4.2 随机化对手（覆盖攻防倾向 / 超必杀倾向 / 距离 / 时机 / 跳入 / 防御方向）

`lab/randbot.py` 用 `seed` 派生 10 组打法参数，**25 个种子 × 6 阵容 × 2 席位 = 300 局**：

**299/300 = 99.7%**（`err=0`，无技术负）。

### 4.3 席位拆分（两局交换座位，两个座位都要能赢）

不含自博弈：**席位 0 = 60/60 (100%)，席位 1 = 59/60 (98.3%)，合计 99.2%**。
（含自博弈镜像时席位 1 为 92.4%——同策略互打时先手方的同帧优势会显现，属游戏本身的不对称。）

### 4.4 健壮性

`lab/robust.py` 喂了 22 种畸形/边界观察（空 fighters、缺 catalog、catalog 只有 characters、
`yourPlayer=null`、未知角色 id、status=finished/picking、reversed sides、空中对手、
双满气、被投射物逼近……）：**全部输出合法 15 帧，无崩溃、无技术负**。

## 五、局限与已知弱点（不粉饰）

1. **没有与真实对手（冻结的 GPT-6.1 Sol）交过手。** 上述胜率全部是对我自己写的脚本对手测出来的，
   只能说明"在这批打法分布上很强"，**不能直接外推成对 Sol 的胜率**。Sol 的代码与工作区按要求全程未读取。
2. **对手能利用"中立站位"做距离陷阱。** 我专门写了一个针对性压力测试 bot（`lab/ohbot.py`：
   站在自己长招刚够到、我短招够不到的距离反复用 Kestrel `hk` overhead），我的胜率只有 **58%~67%**。
   Vex 的手偏短（lp 125 / hk 154），Kestrel 的 hk 有 175，这个对位天然吃亏。
   我试过"默认站防"和"先走几帧再出招"两种修法：前者因为**按 B 会后退**（`isDown` 才是原地蹲下）
   弄得整体更差（99.2% → 93.3%），后者也只是把 58% 抬到 67% 却把主测试组拉到 95%，都没有采用。
   若 Sol 恰好走这个路子，这是最可能丢分的地方。
3. **中立抢招是固定第一帧，节奏可被读。** 我试过给先手/后手加 1~12 帧延迟，胜率都明显下降
   （最早一帧出招就是最优），所以保持固定。代价是**可预测**：会读节奏的对手可以靠"先防后精确反打"赚。
4. **对纯防御对手赢得慢。** 全程站防的对手要打 6900+ 帧（约 5.8 分钟一场），主要靠下段/overhead
   磨 + 超必杀削防；能赢（100%），但节奏很差，若裁判侧有整场时限会有风险。
5. 只验证了 `python3` 语义下的行为；本机只有 `python`（3.14），本地测试用 `python` 跑，代码不含版本相关语法。
